# Скрипты проекта

Каталог `scripts` содержит корневые команды проекта и общую инфраструктуру для служебных проверок. Скрипты запускаются из корня проекта через `npm run ...` и используют корневой `.env` как единственный источник конфигурации.

## Основные команды

`npm run dev`

Проверяет конфигурацию, проверяет доступность портов и запускает MinIO, backend и frontend в режиме разработки. Все процессы запускаются через `scripts/process/run-parallel.mjs` и завершаются вместе при `Ctrl+C`.

Backend обрабатывает штатные сигналы остановки через Nest shutdown hooks: сначала HTTP-сервер завершает текущие запросы, затем закрываются подключения Prisma и S3. При Ctrl+C в Windows лаунчер даёт дочерним процессам до 10 секунд на завершение, затем принудительно останавливает оставшиеся процессы. Получение SIGTERM самим Windows-лаунчером не передаёт сигнал дочерним процессам: этот путь выполняет принудительную остановку без ожидания graceful shutdown. Аварийное завершение одного процесса также сразу останавливает остальные. Этот лаунчер предназначен для интерактивного dev/preview; он не заменяет production service manager. Принудительное завершение средствами ОС не выполняет shutdown hooks; production-служба должна передавать приложению штатный сигнал остановки и предоставлять время на завершение запросов.

`npm run setup`

Подготавливает проект к локальному запуску. Команда проверяет конфигурацию, PostgreSQL и MinIO, создаёт бакет при необходимости, генерирует Prisma Client, применяет миграции, запускает seed и проверяет обязательные прикладные данные.

`npm run doctor`

Диагностирует состояние проекта в реально запущенном виде. Если компонент не работает, doctor временно поднимает только этот компонент, например MinIO-процесс или PostgreSQL-службу, проверяет его и затем восстанавливает исходное состояние. Команда не должна оставлять после себя временно запущенные процессы или службы.

`npm run start`

Проверяет конфигурацию и запускает собранные backend и frontend: `backend start:prod` и `frontend preview`.

`npm run doctor:prod`

Выполняет восемь read-only проверок: production-конфигурация, PostgreSQL, миграции, бакет MinIO, сборки backend/frontend, HTTP health backend и HTTP-ответ frontend. Backend должен вернуть JSON со статусом `ok` для приложения, PostgreSQL, MinIO и бакета. Frontend должен ответить успешно с `Content-Type: text/html`. Для каждого HTTP-запроса установлен timeout 3 секунды. Сервисы должны быть запущены заранее: команда не запускает процессы, не применяет миграции и не создаёт бакет.

Наличие сборок не заменяет HTTP-проверки: остановленный backend или недоступный frontend приводят к ненулевому коду завершения. Итог сообщает результат перечисленных проверок, а не подтверждает полную настройку production-сервера. Локальный `doctor` проверяет внутренние HTTP listener-адреса из host/port, а `doctor:prod` — публичные адреса из `BACKEND_URL` и `FRONTEND_URL`; доступность с устройств пользователей, правила сети и настройка Windows-служб контролируются отдельно.

`npm run backup` / `npm run restore`

Backup требует `pg_dump` и `pg_restore`. Помимо наличия непустого дампа проверяется читаемость его оглавления через `pg_restore --list`. Restore повторяет эту проверку до подключения к базе и изменения объектов MinIO. Проверка ограничена 30 секундами и не подключается к PostgreSQL. Если `pg_restore` отсутствует в PATH, задайте `PG_RESTORE_PATH`.

Новые копии используют manifest `formatVersion: 2`: SHA-256 и размер дампа, а также ключ, размер и SHA-256 каждого файла MinIO. Суммы вычисляются потоково по сохранённым файлам. Перед финализацией backup и до запуска restore повторно проверяются все файлы и точный набор ключей. Изменение содержимого при прежнем размере, переименование, добавление или удаление файла отклоняют копию.

Формат 1 без контрольных сумм больше не принимается скриптом restore. Старые копии не удаляются и не преобразуются автоматически: вычисление новых сумм уже повреждённой копии не подтверждает её исходную целостность. Создавайте новые копии в формате 2. Если требуется восстановить старую копию, сначала отдельно проверьте её в изолированной среде.

Контрольные суммы обнаруживают расхождение файлов с manifest, но не подтверждают подлинность manifest и не заменяют пробное восстановление. Backup выполняется при остановленном backend, чтобы прикладные изменения не разошлись между дампом БД и копированием файлов.

Backend, backup и restore одной установки используют общую эксклюзивную блокировку `.local/.production-operation.lock` в корне проекта. Backend захватывает её до запуска Nest и удерживает до выхода процесса; при штатной остановке освобождение происходит после завершения HTTP-запросов и shutdown hooks. Для backup/restore сначала остановите backend. Пока операция идёт, повторный запуск скриптов и запуск backend отклоняются. MinIO и PostgreSQL должны оставаться доступны. Скрипты не останавливают и не запускают backend автоматически. После аварийного завершения процесса lock может остаться: не удаляйте его, пока не убедитесь, что указанный процесс и его дочерние команды остановлены. При запуске backend оставшаяся блокировка операции backend снимается автоматически только после проверки, что PID завершён (ESRCH), порт backend свободен и файл блокировки не изменился. Блокировки backup/restore, неизвестного владельца и живого процесса автоматически не снимаются. Блокировка действует для одной установки на файловой системе; другие установки и ручные SQL/S3-операции она не блокирует. На время backup/restore они также должны быть исключены оператором. При первом внедрении этого правила остановите старую версию backend: она ещё не использует блокировку.

Перед изменением данных restore обязательно создаёт проверенную копию текущей БД и MinIO через тот же backup-процесс: дамп, `pg_restore --list`, manifest формата 2 и SHA-256 всех файлов. Копия сохраняется в `BACKUP_DIR/restore-recovery`; если `BACKUP_DIR` не задан — в `.local/restore-recovery` корня проекта. Для restore теперь также нужен `pg_dump` и место для полной копии текущих данных. Ошибка создания защитной копии останавливает restore до изменения данных. Путь завершённой защитной копии выводится до начала изменений и при последующей ошибке; сама копия автоматически не удаляется.

Перед первым изменением restore записывает `.local/.restore-recovery-required.json` с путями исходной и защитной копий. Backend не запускается при наличии этого маркера. При ошибке PostgreSQL, замены MinIO или проверки данных выполняется автоматический откат из защитной копии: повторно проверяются копия и архив, восстанавливаются БД и файлы, сверяются ключи, размеры и SHA-256 объектов непосредственно в MinIO. Исходный restore остаётся неуспешным даже при успешном откате; результат и вывод отдельно указывают исходную ошибку и состояние отката. Маркер удаляется только после успешной проверки восстановления или отката. Ошибка удаления также считается неуспешным завершением.

Общей транзакции между PostgreSQL и MinIO нет. При аварийном завершении процесса или ошибке автоматического отката защитная копия и маркер остаются, backend заблокирован. Устраните причину, убедитесь, что процесс и дочерние команды остановлены, и при необходимости удалите только оставшийся `.production-operation.lock`. Затем восстановите прежнее состояние командой `npm run restore -- --backup "<путь защитной копии>" --confirm` либо повторите исходный restore. Не удаляйте `.restore-recovery-required.json` вручную для обхода блокировки. Перед повторной попыткой также создаётся защитная копия текущего состояния. Сохраните копии до подтверждения успешного восстановления.

`npm run config:validate`

Проверяет корневой `.env`: наличие обязательных переменных, корректность портов, адресов, путей и секретов. При ошибке остальные команды, которые зависят от конфигурации, должны завершаться до запуска процессов.

## Когда использовать

Для первого локального запуска:

```bash
npm ci
npm run setup
npm run dev
```

Для проверки, почему проект не стартует или компонент недоступен:

```bash
npm run doctor
```

Для обычной разработки:

```bash
npm run dev
```

Для проверки конфигурации без запуска сервисов:

```bash
npm run config:validate
```

## Структура каталога

`dev.mjs`

Точка входа для `npm run dev`. Запускает MinIO, backend и frontend через `scripts/process/run-parallel.mjs`.

`start.mjs`

Точка входа для `npm run start`. Запускает backend и frontend из собранного состояния.

`setup.mjs`

Тонкая точка входа для `npm run setup`. Основная логика находится в `scripts/setup/setup.mjs`.

`doctor.mjs`

Тонкая точка входа для `npm run doctor`. Основная логика находится в `scripts/doctor/doctor.mjs`.

`config`

Низкоуровневая загрузка и правила валидации `.env`. Используется инфраструктурным загрузчиком конфигурации и не предназначен для прямого использования новыми скриптами.

`infrastructure`

Переиспользуемые операции для setup, doctor и будущих проверок: запуск команд, OperationResult, PostgreSQL, MinIO, HTTP-проверки, Prisma и обязательные прикладные данные.

`process`

Каталог `scripts/process`: runner для параллельного запуска процессов. Используется командами `dev` и `start`.

`setup`

Оркестрация setup и краткий CLI-отчёт.

`doctor`

Оркестрация doctor, проверки компонентов, управление временными процессами, cleanup и подробный CLI-отчёт.

## `setup` и `doctor`

`setup` изменяет состояние проекта осознанно: применяет миграции, запускает seed и может создать бакет. Это команда подготовки.

`doctor` диагностирует и восстанавливает исходное состояние: если он сам временно изменил состояние системы, например запустил процесс или службу, он должен восстановить только те объекты, которыми управлял сам. Это команда проверки.

## MinIO

В `npm run dev` MinIO запускается напрямую из пути `MINIO_EXECUTABLE`. Каталог данных берётся из `MINIO_DATA_DIR`, API слушает `MINIO_HOST:MINIO_PORT`, консоль слушает `MINIO_HOST:MINIO_CONSOLE_PORT`.

Учётные данные root-пользователя передаются в процесс MinIO через окружение:

```env
MINIO_ROOT_USER
MINIO_ROOT_PASSWORD
```

Отдельная команда для запуска MinIO в `package.json` не нужна.

## PostgreSQL

Обычные команды не управляют службой PostgreSQL. Исключение: `npm run doctor`. На Windows он может временно запустить службу, если она подтверждённо остановлена и задана переменная:

```env
POSTGRES_SERVICE_NAME
```

Если служба уже работает, doctor не перезапускает её. Если подключение к PostgreSQL не проходит при работающей службе, это считается ошибкой подключения, а не поводом перезапускать службу.

## Коды завершения

При обычном завершении `npm run setup` и `npm run doctor` используют такие коды:

```text
0 - команда завершилась успешно, cleanup выполнен
1 - команда завершилась ошибкой проверки или подготовки
2 - cleanup не удалось выполнить полностью
```

Если одновременно есть ошибка подготовки и ошибка cleanup, итоговый код должен быть `2`, а диагностика должна содержать обе причины.

При прерывании команды сигналом сохраняются стандартные коды: `130` для `SIGINT` и `143` для `SIGTERM`. Это относится в том числе к `setup`, `dev` и `start`.

## Правила для новых скриптов

Новые проверки лучше размещать в `scripts/infrastructure`, если они могут пригодиться нескольким командам.

Оркестраторы должны только задавать порядок шагов и собирать отчёт. Низкоуровневые проверки PostgreSQL, MinIO, HTTP, Prisma и прикладных данных должны жить в инфраструктурных модулях.

Операции, которые возвращают результат проверки, должны использовать единый контракт OperationResult:

```js
{
  ok: true,
  code: 'SOME_OPERATION_OK',
  message: 'Operation completed'
}
```

Поле `code` зависит от конкретной операции. При необходимости операция может вернуть `details`. У проекта нет одного универсального набора кодов для всех проверок.

Секреты, пароли, токены, `DATABASE_URL` и секретные ключи нельзя возвращать в публичных `details` и нельзя выводить в отчёты.

Если скрипт временно запускает процесс или службу, он должен хранить это в собственном реестре и выполнять cleanup в `finally`. При `SIGINT`, `SIGTERM`, `uncaughtException` и `unhandledRejection` cleanup должен выполняться один раз.

Все ожидания готовности процессов, служб и HTTP-проверок должны иметь timeout и короткий интервал повторов. Один неответивший сервис не должен вешать CLI навсегда.

## Проверки после изменения скриптов

Минимальный набор для этого проекта:

```bash
node --check scripts/<file>.mjs
npm run lint
npm run check:encoding
```

Для изменений в конфигурации:

```bash
npm run config:validate
```

Для изменений в setup или инфраструктурных проверках:

```bash
npm run setup
```

Для изменений в doctor, cleanup или управлении процессами:

```bash
npm run doctor
```

Если менялись TypeScript-конфиги, которые запускаются вне обычной сборки, дополнительно проверьте их командой, которая фактически использует этот конфиг. Например, для `backend/prisma.config.ts` подойдут Prisma-команды из корневого `package.json`.

## Частые проблемы

Если `npm run dev` сообщает, что порт недоступен, значит один из портов backend, frontend, MinIO API или MinIO Console уже занят. Нужно остановить процесс, который слушает этот порт, или изменить порт в `.env`.

Если `npm run doctor` не может запустить PostgreSQL-службу на Windows, проверьте `POSTGRES_SERVICE_NAME` и права терминала. Управление службами может требовать запуск от имени администратора.

Если MinIO не проходит проверку авторизации, проверьте `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`, `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` и имя бакета.

Если setup проходит миграции и seed, но падает на обязательных прикладных данных, проверьте seed-файл backend и таблицу `countries`.

## Изолированная проверка backup/restore

`tests/scripts/prod/restore-prod.real.integration.test.mjs` проверяет настоящий `pg_dump`/`pg_restore` и MinIO на отдельных временных данных. Тест создаёт собственный PostgreSQL-кластер через `initdb`, проверяет его `data_directory` и запускает отдельный MinIO на loopback-портах. Текущие БД и бакет приложения не используются. Временный PostgreSQL использует trust-аутентификацию и доступен только на `127.0.0.1`; после проверки оба сервиса останавливаются и временный каталог удаляется. При ошибке остановки каталог сохраняется для диагностики.

Проверяются строки, внешние ключи, sequence, бинарные и пустые файлы, удаление лишних объектов и автоматический откат после намеренного сбоя уже выполненной загрузки в MinIO. Это проверка инфраструктурного pipeline на репрезентативной схеме; она не заменяет проверку конкретной производственной копии.

Запуск в PowerShell из корня проекта:

```powershell
$env:ESOFT_REAL_BACKUP_TEST = "1"
try {
  node --test tests/scripts/prod/restore-prod.real.integration.test.mjs
} finally {
  Remove-Item Env:ESOFT_REAL_BACKUP_TEST
}
```

Без `ESOFT_REAL_BACKUP_TEST=1` тест пропускается. Нужны `initdb`, `pg_ctl`, `pg_dump`, `pg_restore` и MinIO. Каталог PostgreSQL можно задать через `ESOFT_TEST_PG_BIN`, путь MinIO — через `ESOFT_TEST_MINIO_EXE`; иначе используются локальные пути конфигурации и PostgreSQL 17 в Windows.

## Профили конфигурации

Общий config core поддерживает `local`, `backend`, `frontend`, `production`, `database` и `storage-operation`. Локальные launcher-команды сохраняют полную проверку MinIO; backend и production-операции не требуют локального executable, data directory, console port или root-реквизитов. Vite проверяет собственные адреса, Prisma — конфигурацию PostgreSQL. CLI `config:validate` выбирает профиль по `NODE_ENV` либо принимает `--profile`; программные загрузчики передают профиль явно. Подробный состав — в `docs/CONFIGURATION.md`.
