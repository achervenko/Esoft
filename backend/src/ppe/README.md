# PPE

Модуль управляет номенклатурой СИЗ и размерными рядами, размерами сотрудников,
нормами выдачи по должностям, планом обеспечения и журналом фактических выдач.
Роли приложения определяют доступ к операциям и не зависят от справочника `positions`.
Frontend описан в `frontend/src/pages/PpePage/README.md`.

База создаётся начальной миграцией с интервальными обязанностями. Перенос старых режимов и истории не поддерживается.

## Права

Все endpoints требуют активную сессию. Глобальный `PermissionsGuard` проверяет
разрешение, явно объявленное на каждом обработчике через `@RequirePermission`.
Связь разрешений с ролями определена в `src/auth/permission-policy.ts`.
Права активных ролей объединяются; роли выключенного модуля не дают доступа.
Контроллеры повторно permission не проверяют. Проверки дат выдачи,
бизнес-ограничений норм и истории выполняются отдельно в сервисах.

| Операция                                    | admin | ppe_specialist | accounting_specialist |
| ------------------------------------------- | ----- | -------------- | --------------------- |
| Чтение карточек, норм, каталога и журнала   | Да    | Да             | Да                    |
| Управление каталогом и размерными рядами    | Да    | Нет            | Да                    |
| Изменение размеров сотрудников              | Да    | Да             | Нет                   |
| Управление нормами и редакциями             | Да    | Да             | Нет                   |
| Нормативная и дополнительная выдача, отмена | Да    | Нет            | Да                    |
| Указание даты выдачи задним числом          | Да    | Нет            | Нет                   |

`ppe_specialist` — специалист по охране труда, `accounting_specialist` —
специалист по учёту. Управление пользователями и должностями через
`api/users/admin` доступно только `admin`. Доступ к другим модулям
определяется их собственными разрешениями.

### Постраничный журнал: GET /api/ppe/issues/page

Основной endpoint для журнала и истории сотрудника. Требует активную сессию и право
чтения СИЗ (`admin`, `ppe_specialist`, `accounting_specialist`).

| Параметр | Допустимые значения и поведение |
| --- | --- |
| `page` | Целое положительное число, по умолчанию 1; максимум 1000000 |
| `limit` | Целое число от 1 до 100, по умолчанию 100 |
| `employeeId`, `positionId`, `ppeItemId` | Необязательные положительные ID для фильтрации |
| `issueType` | `REGULAR` или `EXTRA` |
| `status` | `ISSUED` или `CANCELLED` |
| `dateFrom`, `dateTo` | Включительные границы даты выдачи в формате `YYYY-MM-DD` |
| `search` | Строка до 200 символов; все слова должны встречаться в поисковом тексте выдачи |
| `sort` | `date` (по умолчанию), `employee`, `type`, `actual`, `quantity`, `size` |
| `direction` | `desc` (по умолчанию) или `asc` |

Поиск использует исторические снимки ФИО, должности, названий и артикулов СИЗ,
автора выдачи, комментарий, размер/ростовку, дату `DD.MM.YYYY`, русские подписи
статуса и вида выдачи. Регистр и различие `ё/е` игнорируются; `%` и `_` во вводе
ищутся буквально. Текст поддерживается вычисляемым полем PostgreSQL `journal_search_text`.
Текстовые сортировки employee/actual/size используют `app_registry_order`;
дополнительный ключ всегда `id DESC`. Сортировка type выполняется по строковому
значению enum, quantity — по числовому количеству.

Пример запроса:

```http
GET /api/ppe/issues/page?employeeId=5&page=2&limit=100&sort=date&direction=desc
```

Ответ содержит `items` (массив существующих DTO выдач), `total` (число записей после
применения фильтров и поиска), `page` и `limit`. Например, для пустого результата:

```json
{ "items": [], "total": 0, "page": 2, "limit": 100 }
```

COUNT и чтение страницы выполняются в одной RepeatableRead-транзакции.
Если `(page - 1) * limit >= total`, возвращается пустой массив без `ORDER BY/OFFSET`
и загрузки DTO. Неизвестные параметры и некорректные значения отклоняются с HTTP 400.

### Старый контракт: GET /api/ppe/issues

Принимает только фильтры `employeeId`, `positionId`, `ppeItemId`, `issueType`, `status`,
`dateFrom`, `dateTo`; возвращает массив DTO по `issuedAt DESC, id DESC`.
Параметры page/limit/search/sort/direction в этом контракте не поддерживаются.
Сервис читает не более 101 записи для проверки ограничения. Если подходящих записей
больше 100, он возвращает HTTP 400 с сообщением
«Для больших журналов используйте /api/ppe/issues/page.», а не обрезает массив молча.
Для новых потребителей следует использовать `/api/ppe/issues/page`.

## Бизнес-правила

### Каталог

Физическое удаление позиций каталога и размеров через API не предусмотрено. Редактирование размера не позволяет
перенести его к другому СИЗ. После первого использования артикула в любой норме
или истории выдач его изменение запрещено; для новой номенклатуры создаётся
новая запись. Название и активность остаются редактируемыми. Тип и единица защищены от
изменения после включения позиции в норму или использования в истории выдач.

При создании позиции и замене её размерного ряда разрешено не более 2000
размеров. Неизвестные поля отклоняются. Размеры и ростовки нормализуются
к единому разделителю «–», чтобы одинаковые диапазоны не создавали дубликаты.

### Нормы выдачи

Одна норма — полная редакция для одной должности. POST принимает `positionId`,
`effectiveFrom`, `effectiveTo`, непустой `items` и необязательный `transitionMode`. Для revision и PUT `positionId`
не передаётся: должность неизменна. Каждый item содержит только `ppeItemId`,
`quantity`, `periodCount`, `periodUnit`. Неизвестные поля, в том числе actor,
отклоняются. Повторяющиеся `ppeItemId` запрещены с `PPE_NORM_ITEM_DUPLICATE`.
В БД действует UNIQUE по паре `(norm_id, ppe_item_id)`.

ID и periodCount — положительные числа integer в пределах PostgreSQL INTEGER,
без преобразования строк и boolean. quantity — конечное число больше нуля,
не больше 999999999.999, с максимум тремя знаками после запятой. periodUnit —
`DAY`, `MONTH` или `YEAR`; периодичность не пересчитывается автоматически.
Даты — реальные календарные даты строго YYYY-MM-DD без времени. Конец не может
быть раньше начала; null или отсутствие `effectiveTo` означает открытый период.

Границы периода включительны: 01.01–31.01 и 01.02–... не пересекаются,
а общая дата границы — пересечение (`PPE_NORM_PERIOD_CONFLICT`, HTTP 409).
Для создания и исправления нужны существующая активная должность и активные СИЗ.
Чтение исторических норм и отключённых связей разрешено.

При создании следующей редакции новая дата начала должна быть позже даты начала
исходной нормы и не раньше сегодняшнего дня в Europe/Moscow. Открытая исходная
редакция закрывается днём перед новой датой в той же транзакции; закрытая исходная
редакция не меняется. Полный состав новой редакции передаётся явно. Строки
предыдущей редакции и их ID остаются неизменными; для новой редакции создаются
новые строки `PpeNormItem` с собственными ID. Пересечения с другими редакциями
запрещены. Нельзя закрыть
период так, чтобы уже связанные выдачи оказались после его конца.

PUT разрешён, только если старая и новая дата начала строго позже сегодня и
к строкам нормы нет выдач. Иначе `PPE_NORM_LOCKED` (HTTP 409). PUT принимает полный
состав: ID сохранённых позиций не меняются, отсутствующие строки будущей нормы
удаляются внутри транзакции с аудитом, новые добавляются. Действующую или
завершённую норму нельзя переписать. Действующую норму можно завершить отдельной
операцией end без продления периода и без отсечения уже зарегистрированных выдач.
Удаление разрешено только для будущей нормы без связанных выдач.

Операции норм блокируют `positions` через FOR UPDATE, затем редакцию (при наличии)
и каталог СИЗ по возрастанию ID. Операции выполняются с ReadCommitted в одной транзакции. Блокировка должности сериализует изменения всех её редакций,
включая одновременное создание первых норм; блокировки каталога не позволяют параллельно отключить СИЗ во время операции. Прямые изменения БД вне сервиса
норм не подпадают под контроль пересечения периодов со стороны сервиса.

DTO возвращает название должности, даты строками, quantity числом и полный
состав с article/name/unit/isActive каталога. `findEffectiveNorm(positionId, date)`
доступен через экспортированный `PpeNormsService`, возвращает редакцию или null,
если на дату нормы нет. Он использует включительные границы и не отбрасывает
исторические отключённые должности/СИЗ. Название должности и связанные сведения
каталога читаются из справочников; нормативные название, единица и тип берутся
из снимков строк нормы. Журнал выдач хранит собственные исторические снимки.

### Снимки позиций в нормах

Строка нормы сохраняет название, единицу и тип СИЗ при создании редакции. Переименование справочника не меняет действующие и исторические нормы, таблицу нормативной выдачи и нормативное название в новых выдачах по старой редакции. Новая редакция получает текущие значения справочника; явное редактирование будущей нормы обновляет её снимки. Артикул остаётся уникальным. Тип и единица позиции, включённой в норму, защищены от изменения. API справочника возвращает hasActiveNorm для уведомления в форме редактирования.

## Расчёт норм

Используется только `INTERVAL`: полное quantity выдаётся один раз за periodCount
единиц DAY, MONTH или YEAR. Количество выдаётся целиком. Месяцы и годы
прибавляются календарно с ограничением дня последним днём месяца.

Плановая дата — срок выполнения обязанности. Обычная выдача доступна с
max(даты назначения сотрудника, plannedDate - min(30 дней, длительность периода),
даты предыдущей фактической выдачи). До плановой даты это досрочная выдача;
в саму дату — к выдаче; со следующего дня незакрытая обязанность просрочена.
Следующая дата = max(плановая дата закрытой обязанности, фактическая дата) + период.
Новая обязанность не создаётся за пределами даты окончания нормы или 9999 года.
Мягкий переход сохраняет срок совместимой предыдущей выдачи. Жёсткий начинает
первую обязанность с effectiveFrom новой нормы и не учитывает историю предыдущей
нормы в сроке или досрочном окне; последующие сроки используют собственные выдачи.
Назначение на должность ограничивает начало обеспечения.
Первая обязанность будущей нормы также доступна досрочно. При POST норма выбирается
по запрошенным строкам, включая будущую, а окно проверяется расчётом. Если действующей
нормы ещё нет, план показывает ближайшую будущую норму в пределах 30 дней.
Если текущая норма действует, её позиции остаются в плане. К ним добавляются
только доступные обязанности ближайшей будущей нормы. Каждая строка содержит
normId и normEffectiveFrom, чтобы различать нормы. Набор из текущей и будущей
норм можно подтвердить одной транзакцией; ошибка любой строки откатывает весь набор.

## Выдачи

REGULAR принимает `employeeId` и `items` с `normItemId`, `ppeItemId`, опциональными
`sizeId` и `comment`. Количество и нормативная дата определяются backend.
EXTRA использует отдельный endpoint: item содержит `ppeItemId`,
положительное `quantity` NUMERIC(12,3), опциональные `sizeId` и `comment`.
`normItemId` у EXTRA не принимается; нормативные поля в БД остаются null.
В batch от 1 до 100 строк, комментарий не длиннее 2000 символов. Поля snapshot,
scheduledAt, должность, статус и actor не принимаются от клиента.

По умолчанию issuedAt — сегодня в Europe/Moscow. Только admin может передать
issuedAt в формате YYYY-MM-DD; будущая дата запрещена. Специалист не может
передать это поле даже со сегодняшней датой. Для admin ближайшая обязанность и её
доступность определяются на указанную дату, включая досрочное окно будущей нормы.
Используется текущая должность сотрудника:
история переводов сотрудников в приложении пока не хранится. На чтении плана
необязательный query issuedAt подчиняется тем же правилам.

Для REGULAR backend выбирает ближайшую доступную незакрытую обязанность.
Клиент не задаёт плановую дату или количество. До открытия окна возвращается
PPE_NORM_NOT_DUE. Повторение normItemId в batch разрешено: каждая строка заново
проверяет следующую обязанность. Для периода 7 дней допустимы текущая и следующая
обязанность в один день, но третья ещё недоступна; весь batch откатывается при ошибке.
EXTRA не закрывает норму и не сдвигает её график. Замена должна совпадать по типу и единице.

`scheduledAt` хранит плановую дату закрытой обязанности и может быть позже issuedAt.
Уникальный индекс сотрудника, строки нормы и плановой даты запрещает повторное закрытие обязанности.
Расчёт возвращает одну ближайшую обязанность полным количеством.
План содержит plannedDate, availableFrom, obligationStatus
(NOT_AVAILABLE, EARLY, DUE, OVERDUE, FINISHED), available и nextFuture.
Отменённая текущая обязанность открывается снова, даже если более поздняя уже закрыта.
Записи EXTRA/CANCELLED не засчитываются как выполненные; отменённые даты используются
только для восстановления незакрытой обязанности. История не переписывается.

### История и отмена

Журнал хранит employeeNameSnapshot, positionNameSnapshot, нормативные article/name,
фактические article/name/unit, ppeItemTypeSnapshot, размер и ростовку, issuedByNameSnapshot. DTO строится
из снимков и сохраняет значения после переименования или отключения связей.
REGULAR/EXTRA и исходные данные записи неизменны через API; PUT и DELETE нет.
Новая выдача требует активного сотрудника и активного фактического СИЗ.
Отключённая должность не скрывает историю и сама по себе не запрещает выдачу
активному сотруднику. Нормативный отключённый СИЗ можно заменить активным.

Отмена принимает только reason: обязательная непустая строка после trim,
до 1000 символов. Сохраняются CANCELLED, cancelledAt (timestamp), пользователь,
его имя snapshot и причина. Исходные значения не переписываются. Повторная отмена
запрещена (PPE_ISSUE_ALREADY_CANCELLED), восстановления ISSUED нет. Отмена возможна
для исторической записи даже после отключения сотрудника.

Создание блокирует сотрудника FOR UPDATE, затем должность, редакцию и её строки,
каталог по возрастанию ID и релевантные ISSUED-выдачи. Блокировка должности совместима
со сценарием изменения норм. Size-операции каталога используют ту же блокировку
родительского СИЗ, поэтому размеры не могут быть параллельно отключены во время операции выдачи.
Отмена блокирует сотрудника, затем выдачу. Все записи batch и audit атомарны.

CREATE выдачи фиксируется одним компактным событием AuditLogService.writeEvent()
без копирования snapshot-полей. Отмена создаёт две field-level записи: смена статуса
и причина отмены. Автор хранится в audit_log.user_id; снимок его имени — в
PpeIssue.cancelledByNameSnapshot. Ошибка аудита откатывает бизнес-изменение.

## Размеры

### Размеры сотрудников

Размеры хранятся в отдельной таблице `ppe_employee_sizes` со связью один к одному
на `employees`. Строка создаётся при первом сохранении; без строки API возвращает
`ppeSizes: null`. Общая модель Employee не содержит scalar-полей СИЗ.
Пять размеров возвращаются внутри `ppeSizes`; `shoeSize` — число или null.

Чтение использует явный Prisma select только полей:
`id`, `lastName`, `firstName`, `middleName`, `positionId`, `position`,
`ppeSizes` (пять полей размеров), `isActive`.
`position` возвращается как название должности, `shoeSize` — число или null.
Учётные записи, роли, email, сессии и фотографии в этот DTO не входят.

PATCH принимает только пять полей размеров. Любое неизвестное поле, включая
`positionId`, `isActive`, ФИО и `role`, отклоняется с `UNKNOWN_FIELDS` до записи
в БД. Пустой payload отклоняется. Отсутствующие поля не меняются; явный null
очищает значение. Текстовые размеры ограничены 20 символами, обрезаются по краям,
пустая строка превращается в null. Размер обуви — число от 15 до 60 с максимум
одним десятичным знаком либо null.

Сотрудник блокируется через FOR UPDATE внутри транзакции до определения активности сотрудника.
Просмотр отключённого сотрудника разрешён, изменение его размеров запрещено.

### Размер фактического СИЗ

Обязательный type: OTHER, BODY, FEET, HANDS или HEAD. POST и PUT требуют type;
значения по умолчанию нет. Тип нельзя изменить после включения позиции СИЗ в норму
или после любой выдачи, в том числе если позиция указана в истории как нормативная СИЗ.
После любой выдачи, включая отменённую, изменение запрещено (PPE_ITEM_TYPE_IN_USE).
Учитываются обе роли позиции в журнале: фактический ppeItemId и нормативный normItemPpeItemId.
Изменение типа выполняется под блокировкой позиции в той же транзакции.
Создание и изменение типа фиксируются в PPE audit. BODY использует
clothingSize и clothingHeight для рекомендации пары, FEET — shoeSize, HANDS — gloveSize,
HEAD — headwearSize. Для замены применяется type фактически выдаваемого
СИЗ. OTHER не требует размера.
Для OTHER создание размеров запрещено (PPE_ITEM_SIZES_NOT_ALLOWED).
Переход на OTHER при наличии любых размеров, включая отключённые, запрещён
(PPE_ITEM_HAS_SIZES). Оба ограничения применяются под блокировкой позиции.
Для BODY каждая строка PpeItemSize содержит пару value/heightValue, например
88-92 / 158-164. Рекомендация ищет точное совпадение размера и ростовки сотрудника.
value и heightValue очищаются через trim и ограничены 20 символами каждый;
пустые строки недопустимы. Допустимая длина value и heightValue — не более 20 символов; SQL-поля остаются TEXT.
Один размер может иметь несколько ростовок; одинаковые пары не повторяются.
Для других типов heightValue должен быть null. Изменение типа при несовместимом
размерном ряде запрещено (PPE_SIZE_TYPE_CONFLICT).
Если размеры позиции вообще не заведены, sizeValue и clothingHeightSnapshot остаются null.

Автоматически выбирается соответствующий активный размер каталога; для BODY — пара.
Если совпадения по ростовке нет либо ростовка сотрудника не заполнена, нужен явный sizeId.
В журнале BODY сохраняются value и heightValue выбранной строки каталога,
даже если они отличаются от данных сотрудника. Несовпадение любого заполненного
компонента вызывает информационное предупреждение. Ростовка не выбирается отдельно от размера.
Для обуви
числовые значения 42 и 42.0 считаются соответствующими; в журнале сохраняется
значение каталога.
Выбор другого активного размера разрешён: в ответе POST выдачи каждая строка
содержит warnings с кодом PPE_SIZE_DIFFERS_FROM_RECOMMENDED и текстом
«Выбранный размер отличается от рекомендуемого размера сотрудника.» при несовпадении
с заполненным размером сотрудника. Предупреждение информационное, подтверждение
не требуется; в журнале сохраняется фактически выбранный размер.
Предупреждение формируется только по заполненным у сотрудника компонентам размера;
для BODY независимо сравниваются размер и ростовка. Для обуви 42 и 42.0 эквивалентны.
warnings не хранится в БД и не вычисляется повторно для исторического DTO.
Явный sizeId может переопределить рекомендацию, но должен принадлежать тому же
СИЗ и быть активным. Если размеры заведены, но подходящего активного размера нет,
requiresSelection = true. Если активные размеры есть, требуется явный выбор
(PPE_SIZE_REQUIRED). Если все размеры отключены, выдача остаётся заблокированной
до активации или добавления активного размера. Передача отключённого sizeId
возвращает PPE_SIZE_INACTIVE.
Передача произвольного sizeValue запрещена. Для OTHER или отсутствующего
справочника размеров передача sizeId отклоняется.

## Переходы

### Между редакциями

Расчёт переходов принадлежит сервису норм `PpeNormTransitionService`. План и
создание выдачи вызывают один `evaluate` в транзакции с блокировкой сотрудника
и должности; отдельного модуля и фонового переноса выдач нет.

Редакция хранит `transitionMode` (`SOFT` / `HARD`) и `previousNormId`.
INTERVAL — единственный алгоритм расчёта; отдельного поля выбора алгоритма нет.

Мягкий переход сохраняет следующий срок совместимой предыдущей нормативной
выдачи, рассчитанный по цепочке редакций, но не раньше начала новой нормы.
Сопоставляется та же позиция номенклатуры (тот же артикул через ppeItemId),
дополнительно проверяются тип и единица. Совпадения только по типу недостаточно.
Если предыдущих выдач нет, первая плановая дата — effectiveFrom новой нормы.

Жёсткий переход начинает первую обязанность каждой строки с effectiveFrom
новой нормы. Выдачи предыдущей редакции не влияют ни на плановую дату,
ни на досрочное окно. После первой выдачи учитывается собственная история строки:
следующий срок = max(плановая дата, фактическая дата) + её период.
Количество всегда берётся целиком из новой строки, независимо от прежнего количества.

В обоих случаях закрывается ближайшая доступная незакрытая обязанность.
Плановая дата сохраняется в scheduledAt, включая досрочную выдачу. Месяцы и годы
прибавляются календарно, дни — календарными сутками. История выдач не переписывается.
EXTRA не засчитывается; отмена нормативной выдачи возвращает соответствующую
обязанность в расчёт. Удалённая и затем добавленная позиция не наследует историю
через отсутствующую позицию в цепочке редакций.

Удаление будущей редакции выполняет `PpeNormsService.deleteFuture` под
блокировкой должности: предыдущая редакция продлевается до дня перед следующей
запланированной редакцией или становится бессрочной, если следующей нет.
Связи потомков переключаются на предыдущую редакцию, сохраняя цепочку расчёта
переходов. Удаление, продление и аудит фиксируются одной транзакцией;
состав предыдущей нормы и история выдач не меняются.

При переносе начала будущей редакции автоматически состыкованная предыдущая
редакция меняет окончание на день перед новым началом. Редакции нельзя менять
местами; явно оставленные отдельные периоды не продлеваются автоматически.
Сокращение периода не допускается, если после новой границы уже есть исторические выдачи. Порядок обновлений сохраняет
SQL-ограничение пересечений; обе границы, состав и аудит откатываются вместе.
Новая редакция создаётся только от последней нормы должности. Это сохраняет
последовательную цепочку переходов и не позволяет обходить историю выдач
промежуточной редакции. Будущие редакции доступны для редактирования в интерфейсе;
следующую редакцию можно запланировать и от последней будущей нормы.

### Смена должности

`PpeNormPositionService` внутри блока норм отвечает за зачёт СИЗ, оставшихся
после смены должности. Он строит цепочку только для расчёта и передаёт её в
`PpeNormTransitionService`: арифметика плановых дат и досрочных окон не дублируется.
И план, и создание выдачи используют этот расчёт в одной транзакции под
блокировкой сотрудника. Изменение должности берёт ту же блокировку и сохраняет
`Employee.positionAssignedAt` (дату последнего назначения, без истории должностей).
При создании сотрудника первоначальное назначение также датируется текущим
рабочим днём: обеспечение не начинается раньше назначения.
Редактирование ФИО и размеров эту дату не меняет. Если дата назначения не записана
(null), дополнительное ограничение по этой дате не применяется.

Зачитываются неотменённые нормативные выдачи по той же позиции номенклатуры
(артикул через ppeItemId), дополнительно проверяются тип и единица.
Замена засчитывается по исходной нормативной
позиции. Дополнительные выдачи остаются вне нормативного расчёта. Общие СИЗ
сохраняют срок носки по старой норме; после его окончания применяется новая.
Для нормы, начавшей действовать до назначения или в день назначения, перенос
совместимой выдачи при переводе использует мягкий переход, даже если у нормы HARD.
Редакции, вступившие в силу после назначения, учитывают выбранный SOFT/HARD.
Для новых позиций первая плановая дата — более поздняя из начала нормы и назначения;
досрочное окно не открывается раньше назначения. СИЗ вне новой нормы остаются
в истории, возврат и списание этой операцией не создаются.

## Архитектура сервисов

### Каталог

`PpeCatalogService` — фасад для контроллера: чтение каталога, создание,
редактирование и статус позиции, а также делегирование изменений размерного ряда.
Ограничения на изменение артикула, типа и единицы остаются рядом с обновлением позиции.
`PpeCatalogSizesService` отвечает за создание, замену, редактирование и статус
размеров, контроль принадлежности размера позиции СИЗ и конфликт одинаковых пар размер/ростовка.
`createInitialSizes` принимает транзакцию создания позиции; вложенная
транзакция не открывается, ошибки размеров или аудита откатывают всю операцию.
`ppe-catalog.persistence.ts` содержит общие операции:
транзакционный вызов с преобразованием ошибок и блокировку позиции.
Порядок блокировок при изменении размера остаётся позиция → размер.

### Жизненный цикл норм

`PpeNormsService` сохраняет публичный API чтения, создания и завершения норм
и делегирует изменение и удаление будущих редакций в `PpeNormsFutureService`.
Future-сервис управляет переносом связанных границ, заменой состава,
восстановлением предыдущей нормы и ancestry после удаления.
`PpeNormsPersistenceService` создаёт норму внутри переданной транзакции,
получает снимки номенклатуры и открывает транзакцию через `mutate`.
Каждая операция изменения открывает одну транзакцию; вложенных транзакций нет.
`PpeNormsGuardsService` выполняет блокировки и контролирует пересечение периодов.
Все изменения нормы и записи аудита выполняются в одной транзакции.

### Расчёт переходов

`PpeNormTransitionService` собирает контекст, строит непустую цепочку редакций,
фильтрует историю выдач и делегирует единый интервальный расчёт.
`PpeNormIntervalTransitionService` рассчитывает ближайшую незакрытую обязанность,
её плановую дату, досрочное окно, статус и полное количество.
Общие операции с UTC-датами находятся в `ppe-norm-transition.dates.ts`.
Сам evaluate не обращается к БД и не изменяет историю выдач. Подготовка контекста
читает связанные редакции в существующей транзакции вызывающего сервиса.

### Выдачи

`PpeIssuesService` предоставляет публичные операции, читает журнал и отменяет выдачи.
`PpeIssuePlanService` рассчитывает план, `PpeIssueCreateService` создаёт REGULAR/EXTRA
и обрабатывает batch, включая набор из текущей и будущих норм.
`PpeIssueHistoryService` блокирует и загружает нормативную историю сотрудника
по связанным позициям номенклатуры, включая отменённые записи для восстановления
обязанностей. Его используют план и создание; отбор истории для конкретной строки
и даты выполняет сервис расчёта переходов.
Общая функция `runPpeIssueTransaction` в `ppe-issues.transaction.ts` задаёт параметры
транзакции и преобразует ошибки Prisma в доменные ошибки.
P2002 преобразуется в PPE_NORM_ALREADY_ISSUED только для уникального индекса
uq_ppe_issues_regular_obligation (или точного набора его трёх полей в metadata).
Для PostgreSQL-адаптера без target распознаётся точное имя этого индекса в
originalMessage при коде 23505 и типе UniqueConstraintViolation.
Остальные unique-конфликты, включая ошибки без распознанного target, передаются без подмены.

### Аудит

Все изменения выполняются вместе с общим audit log в одной транзакции.
Модуль — `AuditModule.PPE` (`ppe`), actor берётся из действующей сессии.
Ошибка аудита откатывает изменение. Для каталога, размеров и норм записываются
только изменённые поля; передача того же значения не создаёт записи аудита.
Создание выдачи фиксируется компактным событием, отмена — изменением статуса
и причиной отмены.

Нормы аудируются как `ppe_norm` (должность и даты) и `ppe_norm_item` (редакция,
позиция СИЗ, количество и периодичность). Значения дат и Decimal предварительно
преобразуются в примитивы. При редакции фиксируются закрытие старого периода
и создание новой нормы с каждой строкой; исправление будущей нормы фиксирует
изменённые, добавленные и удалённые строки. Actor — пользователь сессии.

### Ограничения, управляемые SQL

Следующие объекты намеренно определены в `prisma/packages/ppe/migrations/20260725000002_ppe_init/migration.sql`,
а в `prisma/schema/ppe/ppe.prisma` отмечены комментариями:

- `uq_ppe_item_sizes_item_value`: `UNIQUE NULLS NOT DISTINCT (ppe_item_id, value, height_value)`.
  Для одной позиции нельзя повторить размер с одинаковой ростовкой, включая `NULL`.
  Отключение размера не освобождает комбинацию: существующая запись используется повторно.
  Обычный `@@unique` не отражает равенство `NULL` в этом ограничении.
- `uq_ppe_issues_regular_obligation`: уникальность `(employee_id, norm_item_id, scheduled_at)`
  только для `issue_type = 'REGULAR' AND status = 'ISSUED'`. Отменённые и дополнительные
  выдачи не входят в индекс. Безусловный `@@unique` изменил бы бизнес-правило.
- `ck_ppe_norm_transition_mode`: `TEXT CHECK` допускает только `SOFT` и `HARD`.
  Prisma-поле остаётся `String`; PostgreSQL enum здесь не используется.

Prisma-схема не является полным описанием PostgreSQL-объектов проекта.
При генерации миграций и introspection нужно отдельно сохранять эти ограничения
и проверять SQL: отсутствие обычного `@@unique` не означает разрешение дублей в БД.
Создание базы выполняется миграциями, чтобы SQL-ограничения также были установлены.
