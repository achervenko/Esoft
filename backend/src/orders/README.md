# Заказы

Модуль хранит локальное зеркало заказов клиентов 1С, историю обнаруженных изменений и результаты синхронизаций. Предоставляет API чтения и административного запуска обмена. Источник данных — OData 1С.

## Архитектура

`OrdersModule` подключается при включённом пакете `orders`. Зависимости NestJS — `PrismaModule` и `IntegrationsModule`. Справочник работает независимо от склада.

| Компонент                            | Ответственность                                                                   |
| ------------------------------------ | --------------------------------------------------------------------------------- |
| `OrdersController`                   | HTTP-маршруты и проверка разрешений                                               |
| `OrdersService`                      | Поиск, фильтры, карточка, история и состояние источников                          |
| `OrdersFlow`                         | Регистрация потока `orders.customers`, проверка конфигурации                      |
| `OrdersSyncService`                  | Загрузка, транзакционное применение, журнал запусков и перенос между источниками  |
| `OrdersScheduler`                    | Запуск по расписанию и обработка пропущенного ночного запуска                     |
| `orders-snapshot.ts`                 | Чтение страниц OData и проверка входных данных                                    |
| `applyOrders()` в `orders-import.ts` | Сопоставление записей, сохранение состояния и истории, учёт отсутствия в выгрузке |

## Хранение данных

Prisma-схема — `backend/prisma/schema/orders/orders.prisma`. SQL и manifest пакета — `backend/prisma/packages/orders`. Пакет выбирается через `database-packages.json`; миграция `20261030010000_orders_init` использует таблицы интеграций ядра.

| Модель / таблица                                 | Содержимое                                                             |
| ------------------------------------------------ | ---------------------------------------------------------------------- |
| `CustomerOrder` / `customer_orders`              | Последнее состояние заказа и счётчик отсутствия в выгрузке             |
| `CustomerOrderChange` / `customer_order_changes` | Снимки `before`/`after` и время обнаружения изменения                  |
| `OrderSyncRun` / `order_sync_runs`               | Источник, время запуска и завершения, результат, счётчики и код ошибки |

Внутренний `id` заказа — постоянный UUID ESoft. Внешняя уникальность задаётся парой `(sourceId, externalId)`. Поле `externalId` допускает `NULL` во внутреннем контракте хранения; текущий OData-адаптер принимает только записи с `Ref_Key`.

`documentDate` хранит полную локальную дату и время 1С строкой `YYYY-MM-DDTHH:mm:ss`. `checkedAt` — время последней успешной проверки записи; `changedAt` — время обнаружения изменения её значимых полей.

Связи с источником и историей используют `RESTRICT`. Закрытие, пометка удаления и отсутствие в выгрузке сохраняют запись и её историю.

## Подключение к 1С

В разделе «Пользователи → Интеграции» настройте источник `ONE_C` и подключите поток «Заказы клиентов 1С» (`orders.customers`).

- Базовый URL — каталог OData, например `http://server1c/ERP/odata/standard.odata/`.
- Доступ к чтению — через общий механизм авторизации источника. Заголовок `Authorization` хранится зашифрованным; публичные ответы содержат только сведения о подключении.
- Конфигурация потока v1: `collectionPath` — относительный путь коллекции, по умолчанию `Document_ЗаказКлиента`; `previousSourceId` — источник для переноса существующих заказов при смене подключения.

Обмен выполняется исходящими GET-запросами из ESoft.

### Поля ответа

| Поле 1С        | Поле ESoft     | Проверка                                                    |
| -------------- | -------------- | ----------------------------------------------------------- |
| `Ref_Key`      | `externalId`   | Обязательный ненулевой UUID                                 |
| `Number`       | `number`       | Непустая строка до 100 символов                             |
| `IR_Проект`    | `name`         | Строка до 1000 символов, допускается пустое значение        |
| `Date`         | `documentDate` | Корректная дата и время в формате `YYYY-MM-DDTHH:mm:ss`     |
| `Статус`       | `status`       | Непустая строка до 100 символов; значения принимаются из 1С |
| `Posted`       | `posted`       | Boolean                                                     |
| `DeletionMark` | `deletionMark` | Boolean                                                     |

Ответ каждой страницы — объект с массивом `value`. Запрос использует `$select` перечисленных полей, `$orderby=Ref_Key asc`, `$top=200` и `$skip`. Чтение продолжается до пустой страницы, включая запрос после короткой страницы.

## Синхронизация

Расписание задаётся в `orders.constants.ts`: ежедневно в 03:00 `Europe/Moscow`. Планировщик проверяет срок раз в минуту и выполняет пропущенную проверку после запуска приложения. После ошибки следующий автоматический запуск приходится на следующую ночь. Административный API позволяет запустить обмен отдельно от расписания.

Один источник защищён транзакционной advisory-блокировкой PostgreSQL. Конкурирующий запуск возвращает `BUSY`.

Синхронизация удерживает `FOR SHARE` строки `integration_sources` на время чтения и применения. Сервисы изменения источника и настройки потоков берут `FOR UPDATE` этой же строки, поэтому изменение настроек через них ожидает завершения обмена. Прямые изменения конфигурации SQL-запросами в обход сервисов этой гарантией не покрываются.

Все страницы проверяются перед применением. Изменения заказов, история, успешный журнал запуска и состояние потока фиксируются в одной транзакции. Ошибка откатывает импорт; отдельная транзакция сохраняет неуспешный запуск и безопасный код ошибки. Проверка времени защищает состояние потока от перезаписи более старым неудачным запуском.

Лимиты загрузки:

- 200 записей на страницу и 500 запросов на запуск;
- 120 секунд на транзакцию;
- 2 МБ и 10 секунд на отдельный ответ общего HTTP-транспорта.

Отсутствующий или некорректный `Ref_Key`, повтор ID и неверные поля приводят к `ORDERS_RESPONSE_INVALID`. Ссылки продолжения неподдерживаемого формата — к `ORDERS_PAGINATION_UNSUPPORTED`; исчерпание числа страниц — к `ORDERS_RESPONSE_LIMIT`. Частично полученная выгрузка не применяется.

### Идентификация и история

OData-заказы сопоставляются по источнику и `Ref_Key`. Изменение номера, названия или других значимых полей обновляет существующую запись с сохранением внутреннего ID.

Повтор неизменившихся данных обновляет `checkedAt` и сбрасывает счётчик отсутствия. `changedAt` и история сохраняются без изменений. Каждый обнаруженный переход состояния создаёт снимок истории, в том числе закрытие → открытие → повторное закрытие.

Существующие заказы с внешним ключом читаются пакетами до 1000 записей. Для неизменившихся заказов `checkedAt` и счётчик отсутствия обновляются пакетно в той же транзакции. Изменённые записи и снимки истории сохраняются индивидуально; неоднозначность сопоставления или ошибка любой записи откатывает всё применение.

Два последовательных полных успешных обмена без заказа устанавливают `missingChecks=2` — «Отсутствует в 1С». Последние поля заказа и прежний `checkedAt` сохраняются. Возвращение заказа снимает отметку. Установка и снятие отметки входят в историю; ошибки загрузки не увеличивают счётчик.

Внутренний `applyOrders()` также поддерживает сопоставление проведённых записей без внешнего ключа по точному номеру и полной дате со временем. Неоднозначность завершает применение с `ORDERS_IDENTITY_AMBIGUOUS`. Текущий OData-контракт требует `Ref_Key` до передачи записей в этот метод.

### Смена источника

Для переноса подключения к той же базе 1С:

1. Отключите старый поток.
2. Включите `orders.customers` у нового источника и задайте `previousSourceId` старого источника.
3. Выполните синхронизацию нового источника с полным списком ранее сохранённых заказов.

Новый источник должен быть пустым. Успешная синхронизация переносит заказы с сохранением внутренних ID и истории, затем удаляет `previousSourceId` из конфигурации. Некорректный перенос или неполная выгрузка откатывают операцию.

## API и права

Доступ к чтению — `orders.read`; разрешение выдано администратору. Запуск обмена требует `integrations.manage` с повторной проверкой внутри транзакции.

| Метод и маршрут                        | Назначение                                                |
| -------------------------------------- | --------------------------------------------------------- |
| `GET /api/orders`                      | Поиск и фильтрация заказов                                |
| `GET /api/orders/sources`              | Подключённые источники, состояние и последние 10 запусков |
| `GET /api/orders/:id`                  | Карточка заказа                                           |
| `GET /api/orders/:id/history`          | История изменений                                         |
| `POST /api/orders/sources/:id/refresh` | Запуск синхронизации, результат `SUCCESS` или `BUSY`      |

Параметры списка:

| Параметр        | Значение                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------- |
| `search`        | Часть номера или названия, без учёта регистра                                               |
| `statuses`      | JSON-массив выбранных статусов                                                              |
| `deleted`       | `false` по умолчанию, `true` или `all`; фильтрует `DeletionMark`                            |
| `closed`        | `true` / `false`; отдельная выборка по статусу `Закрыт`, несовместима с непустым `statuses` |
| `missing`       | `true` / `false`; фильтрует отметку отсутствия в выгрузке                                   |
| `sourceId`      | UUID источника                                                                              |
| `page`, `limit` | Номер страницы и размер, по умолчанию 1 и 50; максимум 100 записей                          |

Список содержит проведённые заказы (`posted=true`), сортируется по номеру и внутреннему ID. Ответ включает `items`, `total`, `page`, `limit` и `statuses` — значения статусов всех сохранённых проведённых заказов. История сортируется по убыванию ID; размер страницы по умолчанию — 50, интерфейс запрашивает 20.

Уникальные `statuses` вычисляются группировкой в PostgreSQL, сортируются по возрастанию и не ограничиваются фильтрами или страницей списка.

Страница заказов использует последовательную дозагрузку и оконный рендер. Карточка загружает историю при раскрытии соответствующего блока. Состояние потоков и пояснения ошибок отображаются в разделе «Интеграции».

## Тестирование

Команды из корня репозитория, PowerShell:

```powershell
npm run test --workspace backend -- --runInBand orders
npm run build --workspace backend
$env:ESOFT_MODULAR_MIGRATION_TEST = '1'
node --test tests/scripts/infrastructure/prisma/orders.real.integration.test.mjs
```

Unit-тесты покрывают входные данные, фильтры, расписание и права HTTP. Интеграционный тест создаёт один изолированный PostgreSQL и HTTP-имитатор 1С. Группы сценариев находятся в `tests/scripts/infrastructure/prisma/orders/`: импорт, история, отсутствие заказов, идентификация, фильтры, права, откаты и конкурентные операции.

Для проверки JSON-выгрузки задайте `ESOFT_ORDERS_SAMPLE_FILE` с локальным путём. При отсутствии `Date`, `Posted` и `DeletionMark` тест дополняет их условной датой, `true` и `false`. Эти значения используются только в тесте; производственный парсер проверяет полный контракт.

## Эксплуатационные ограничения

Уникальный `Ref_Key` задаёт устойчивый порядок для неизменной коллекции. При изменениях данных 1С между запросами offset-пагинация `$skip/$top` может смещать страницы. Гарантия согласованного снимка требует соответствующего механизма со стороны 1С.

История отражает состояния, обнаруженные при опросах. Промежуточные изменения между синхронизациями из текущего ответа восстановить нельзя.
