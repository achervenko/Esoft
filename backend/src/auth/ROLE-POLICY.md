# Назначение ролей

В проекте используются роли:

- `admin`
- `chief_engineer`
- `engineer`
- `operator`
- `auditor`
- `ppe_specialist` — Специалист по охране труда
- `accounting_specialist` — Специалист по учёту
- `storekeeper` — Кладовщик

Одна учётная запись может иметь несколько ролей. Их права объединяются.
Назначения хранятся в `User.role` как строка с разделителем `,`;
API учётных записей принимает эту строку или массив известных ролей.
Пробелы удаляются, дубликаты исключаются, порядок хранения фиксирован.
Пустой набор, неизвестная роль или пустой элемент назначения отклоняются.

Самостоятельная роль `storekeeper` работает с Catalog склада и читает собственный профиль. Доступ к
оборудованию, СИЗ и управлению пользователями ему не предоставляется.
Catalog доступен только при подключённом модуле `warehouse`.

Роль `admin` предоставляет административные права и в составном наборе ролей. Контракт защиты endpoints и операций Better Auth описан в [PERMISSIONS.md](PERMISSIONS.md).

`ppe_specialist` получает рабочие права только в рамках сценариев модуля СИЗ.
Доступ к сотрудникам и должностям предоставляется только через специализированные
PPE endpoints и только в объёме, необходимом для работы с СИЗ, включая изменение
размеров сотрудников. Универсальные users-admin endpoints ему недоступны.
PPE-разрешения определены в `permission-policy.ts`;
`canBackdatePpeIssue` отдельно разрешает указание даты выдачи только `admin`.
Подробности
и маршруты перечислены в [документации СИЗ](../ppe/README.md).

## Доступность ролей по модулям

Все роли зарегистрированы в auth независимо от состава поставки. Назначение
определяется общей политикой `role-module-policy.ts`:

- `chief_engineer`, `engineer` и `operator` требуют `equipment`;
- `ppe_specialist` и `accounting_specialist` требуют `ppe`;
- `storekeeper` требует `warehouse`;
- `admin` и `auditor` доступны всегда.

Состав модулей читается из `database-packages.json` при запуске backend.
После изменения состава требуется перезапуск. Это не заменяет миграции
и не разрешает исключать уже установленные пакеты из обслуживания БД.

API списка ролей возвращает только доступные варианты. Backend проверяет
создание учётной записи и смену ролей общей функцией `validateRoleTransition()`.
Она строго разбирает запрошенный набор, сравнивает его с назначенным и проверяет
доступность только добавленных ролей. При создании прежний набор пуст,
поэтому проверяются все роли. Недоступное новое назначение отклоняется с кодом
`ROLE_MODULE_DISABLED`; некорректный набор — с `INVALID_ROLE`.

Назначенные роли сохраняются при выключении модуля. Отключается только роль,
которой нужен этот модуль; остальные роли продолжают давать свои права.
Например, `engineer,storekeeper` при выбранном `equipment` и выключенном
`warehouse` сохраняет права инженера. Если активных ролей не осталось,
доступны вход, чтение собственной сессии и публичные служебные маршруты.
API профиля и фото в этом случае также запрещены до появления активной роли.
После повторного подключения модуля его роль снова становится активной.

Better Auth `get-session` и API профиля возвращают `role` с активными ролями,
а `assignedRole` — с сохранёнными назначениями. Фильтрация выполняется до
NestJS guards. Backend использует `role` там, где требуется контекст эффективных
ролей. Frontend принимает решения о доступе только по серверным `permissions`;
`role` и `assignedRole` используются для отображения и управления назначениями.
Профиль показывает назначенный набор отдельно от фактических прав.
Изменение представления сессии не меняет значение в БД.

Форма учётной записи поддерживает выбор нескольких ролей. Ранее назначенную
роль выключенного модуля можно сохранить или снять, но нельзя назначить заново.
При обновлении через административный API доступность проверяется для новых
ролей в наборе. Better Auth `set-role` и `update-user` используют ту же политику:
сохранённая недоступная роль не препятствует нормализации прежнего набора или
добавлению другой доступной роли. Редактирование остальных данных без `role`
сохраняет назначения.

## Транзакционная защита назначений

Проверка перехода и запись выполняются атомарно. API ESOFT блокирует строку
пользователя `FOR UPDATE` в своей транзакции и вызывает общий validator перед
сохранением. Конфликты сериализации при конкурентном обновлении повторяются
в новой транзакции с повторным чтением назначения.

Database hook Better Auth не удерживает транзакцию записи, поэтому в нём
при обновлении выполняется только строгая нормализация. Проверка перехода
перенесена в `roleAwarePrismaAdapter`: адаптер начинает транзакцию, блокирует
строку `User`, читает текущее назначение, вызывает `validateRoleTransition()`
и сохраняет все переданные изменения до снятия блокировки. Этот же адаптер
используется внутри транзакций Better Auth и обеспечивает проверку обновления
ролей перед записью.

Изменения ролей через Better Auth поддерживаются для одного пользователя по ID.
Массовый `updateMany` ролей запрещён, чтобы не обходить проверку перехода каждой
учётной записи. Hooks нормализуют строковый или массивный ввод до проверки
реестра ролей самим Better Auth; при создании без роли используется `operator`.
При выключенном `equipment` такое создание отклоняется с `ROLE_MODULE_DISABLED`:
нужно явно выбрать доступную роль. Форма выбирает варианты из доступного состава ролей.

Доступ не зависит от проверки URL namespace. Пользователь с
`storekeeper,accounting_specialist` получает объединение складских и PPE
permissions; `engineer,storekeeper` — прав оборудования и склада.

Защита последнего администратора, определение необходимости первоначальной
настройки и выбор ответственных также учитывают отдельные роли в наборе,
а не сравнивают всю строку с одним именем роли.

## Доступность ответственных оборудования

Список ролей ответственных вычисляется с учётом `ACTIVE_MODULES`.
При выключенном `equipment` кандидатов нет, и назначение ответственного
отклоняется также при прямом вызове сервисов. При включённом модуле учитываются
активные роли с `equipment.read`, кроме самой роли `admin`; пользователь
`admin,engineer` может подходить благодаря `engineer`. Дополнительно требуются
активный сотрудник и неблокированная учётная запись.

## Связанные компоненты

- `role-module-policy.ts` — разбор назначений, доступность и проверка перехода.
- `effective-session.ts` — представление назначенных и активных ролей в сессии.
- `role-aware-prisma-adapter.ts` — транзакционная проверка записи Better Auth.
- `role-availability.hooks.ts` — нормализация запроса и проверка создания.
- `role-sql.ts` — проверка отдельных ролей в составном значении SQL.
