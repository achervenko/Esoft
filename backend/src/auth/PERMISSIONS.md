# Разрешения и защита запросов

## Защита NestJS endpoints

`PermissionsGuard` зарегистрирован единственным глобальным guard приложения.
Сначала он вызывает проверку сессии Better Auth, затем проверяет metadata
конкретного обработчика. Отдельный автоматический Better Auth global guard
отключён параметром `disableGlobalAuthGuard: true` верхнего уровня `forRootAsync()`.
Аутентификация вызывается через провайдер `AUTHENTICATE_REQUEST` внутри `PermissionsGuard`.

Каждый бизнес-обработчик обязан объявить `@RequirePermission(...)`.
Отсутствие decorator, неизвестное разрешение или неподходящие права приводят к
403, включая запрос администратора к неразмеченному endpoint. Разрешения
и публичность, объявленные на классе, не открывают новые методы автоматически.
Одновременная публичная пометка и permission на методе запрещены.

Модули объявляют действия в собственных `*.permissions.ts`.
`permission-policy.ts` связывает их строковые ID с ролями; он не импортирует
реализацию необязательных модулей. Действие доступно после явной привязки к ролям; неизвестные permissions
не предоставляются администратору через wildcard.

После аутентификации guard повторно фильтрует `user.role` по активным модулям
и передаёт копию эффективного пользователя в `request.session.user` и
`request.user`. `assignedRole` не участвует в выдаче доступа.
Объединение permissions вычисляется по всем активным ролям.

Публичные NestJS обработчики имеют явный `@AllowAnonymous()` на методе:
health, статус setup, список сотрудников первоначальной настройки и создание
первого администратора. Последние два сохраняют проверки состояния setup,
а создание администратора также проверяет origin и ограничивает частоту запросов.
Список публичных обработчиков контролируется тестом покрытия разметки.
Входящие машинные endpoints интеграций помечаются `@AllowAnonymous()`, поскольку
пользовательская сессия для этих запросов не используется. `MachineApiKeysService`
проверяет Better Auth API Key и его разрешение для запрошенного потока. Общий контур
интеграций дополнительно проверяет привязку ключа к источнику и его актору, а также
активность источника и потока. Маркер не отменяет машинную аутентификацию.
Login, get-session и остальные endpoints Better Auth обслуживаются его
middleware с собственной аутентификацией, permissions и hooks.

## Машинная аутентификация

Машинные ключи хранятся в таблице ядра `api_key` и обслуживаются плагином
`@better-auth/api-key` (конфигурация `machine`). `enableSessionForAPIKeys: false`:
права технического пользователя не превращаются в права HTTP-сессии ключа.
Проверка требует явные permissions ключа; выдачей scopes и metadata управляет
владеющий обменом серверный компонент. Штатные HTTP-методы `/api-key/create`,
`get`, `list`, `update`, `delete` отключены через `disabledPaths`; серверные методы
Better Auth доступны через общий сервис. Пользовательские складские permissions
и permissions API-ключа — независимые контракты.

`MachineApiKeysService.list(actorUserId, scope)` требует `scope.purpose` и `scope.sourceId`, фильтрует ключи по владельцу, конфигурации и metadata. Пустой scope запрещён; отсутствующая, повреждённая или чужая metadata не попадает в ответ. Возвращается только публичная информация о ключе. Отзыв доступен только через `revokeInTransaction(tx, id, actorUserId, scope)`, с той же проверкой источника; отзыва только по actorUserId нет. Один actor может обслуживать несколько источников без смешивания их ключей.

## Проверки объекта и владельца

`users.profile.read` — обычное permission, включённое во все известные роли.
Guard сначала требует это право от активных ролей, затем проверяет ownership:
свой профиль и фото либо чужой профиль и фото при наличии `users.manage`.
Если активных ролей нет, permission отсутствует и запрос запрещён.
Проверка ID выполняется в guard и не дублируется контроллером.
`checklists.work` допускает к рабочим маршрутам, но не заменяет проверку
назначенного исполнителя в сервисе. Аналогично сохраняются проверки владельца
файла и состояния изменяемых записей.

`role-permissions.ts` содержит локальные helpers поверх той же permission-политики.
Они не поддерживают отдельные списки ролей и не заменяют глобальную разметку.

## Административные операции Better Auth

Better Auth access control в `better-auth-access.ts` защищает собственные endpoints
Better Auth. Бизнес-разрешения NestJS описаны отдельно в `permission-policy.ts`.
Право `users.manage` не заменяет проверку разрешений плагина Better Auth.

Только роль `admin` предоставляет управление учётными записями: создание,
просмотр, изменение ролей и данных, блокировку, смену пароля, просмотр и завершение
сессий. Остальные роли административных разрешений Better Auth не имеют.

`impersonate`, `impersonate-admins` и `user.delete` отсутствуют у всех ролей:
вход от имени другого пользователя и физическое удаление пользователей запрещены.

## Первоначальная настройка

Создание первого администратора ограничено пятью попытками с одного IP за
10 минут. Общие счётчики находятся в таблице ядра `setup_rate_limits`; попытка
фиксируется отдельной транзакцией до валидации DTO и создания администратора.
Проверка Origin выполняется первой. Ошибка DTO или создания пользователя
не отменяет уже учтённую попытку.

IP нормализуется и хранится как SHA-256. IPv4 и его IPv4-mapped IPv6 форма
используют один счётчик. Источник IP — Express `request.ip` с fallback на адрес
сокета; backend самостоятельно не читает `X-Forwarded-For`. При настройке
reverse proxy доверять следует только адресам своих прокси.

Таблица ограничена 4096 ключами. Истёкшие записи удаляются при следующем запросе.
При заполнении таблицы новые IP получают `429 SETUP_RATE_LIMITED`, существующие
счётчики продолжают работать. Некорректный или отсутствующий IP также даёт 429.
Если PostgreSQL недоступен, запрос завершается ошибкой, создание администратора
не запускается. Проверка состояния setup и транзакционная блокировка создания
первого администратора остаются отдельными условиями.

## Контракт frontend

Сессия Better Auth и API профиля возвращают `permissions: string[]` — объединение
прав активных ролей, вычисленное по `permission-policy.ts`. Описание полей сессии приведено в [ROLE-POLICY.md](ROLE-POLICY.md#доступность-ролей-по-модулям).

Frontend использует `permissions` для маршрутов, навигации, кнопок и описания
доступов. Он не содержит собственной привязки ролей к разрешениям. Если permissions
отсутствуют или пусты, права не выводятся из названия роли. При обогащении сессии
данными профиля права текущего пользователя берутся из сессии.

Backend независимо проверяет каждый запрос глобальным guard. Скрытая кнопка
или клиентский маршрут не заменяют серверную авторизацию. После изменения
назначений или конфигурации модулей клиент получает новые права при обновлении сессии.

## Связанные компоненты

- `permission-policy.ts` — известные бизнес-разрешения и их привязка к ролям.
- `require-permission.ts` — metadata разрешений обработчика.
- `permissions.guard.ts` — порядок аутентификации, авторизации и проверки профиля.
- `better-auth-access.ts` — права административного плагина Better Auth.
- `machine-api-keys.service.ts` — проверка, ограничение области и отзыв машинных ключей.
- `../setup/setup-rate-limit.service.ts` — ограничение первоначальной настройки.
