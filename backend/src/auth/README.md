# Auth

Модуль отвечает за вход пользователей, сессии Better Auth и общие проверки ролей для backend.

## Основные файлы

- `auth.config.ts` — конфигурация Better Auth, Prisma adapter, env-проверки, trusted origins, login hook.
- `auth.module.ts` — подключение Better Auth к NestJS и parser для auth-запросов.
- `better-auth-access.ts` — access control Better Auth admin plugin.
- `role-permissions.ts` — helpers бизнес-прав и проверки владельца профиля.
- `permission-policy.ts` — привязка бизнес-permissions к ролям и объединение разрешений.
- `permissions.guard.ts` — глобальная аутентификация и обязательная проверка разрешения обработчика.
- `require-permission.ts` — явный decorator разрешения endpoint.
- `role-module-policy.ts` — разбор наборов ролей, доступность назначения и вычисление активных ролей.
- `role-aware-prisma-adapter.ts` — атомарная проверка перехода ролей при записи через Better Auth.
- `role-availability.hooks.ts` — нормализация входа Better Auth и проверка назначения при создании.
- `effective-session.ts` — представление активных ролей в сессии без изменения назначений в БД.
- `role-sql.ts` — проверка отдельных ролей внутри составного значения в SQL.
- `auth-login.service.ts` — обновление `lastLoginAt` после успешного создания пользовательской сессии.
- `better-auth-access.spec.ts` — unit-проверки конфигурации Better Auth access control.

## Роли

В проекте используются роли:

- `admin`
- `chief_engineer`
- `engineer`
- `operator`
- `auditor`
- `ppe_specialist` — Специалист по охране труда
- `accounting_specialist` — Специалист по учёту
- `storekeeper` — Кладовщик

Одна учётная запись может иметь несколько ролей. Их права объединяются.
Назначения хранятся в `User.role` как строка с разделителем `,`;
API учётных записей принимает эту строку или массив известных ролей.
Пробелы удаляются, дубликаты исключаются, порядок хранения фиксирован.
Пустой набор, неизвестная роль или пустой элемент назначения отклоняются.

Самостоятельная роль `storekeeper` работает с Catalog склада и читает собственный профиль. Доступ к
оборудованию, СИЗ и управлению пользователями ему не предоставляется.
Catalog доступен только при подключённом модуле `warehouse`.
Допуск к каждому endpoint определяет глобальный `PermissionsGuard`.
Наличие роли или сессии само по себе не открывает неразмеченные обработчики.

Роль `admin` — единственная роль, предоставляющая права управления учётными записями. Наличие других ролей у того же пользователя эти права не отменяет. Остальные роли не получают административных разрешений Better Auth.

`ppe_specialist` получает рабочие права только в рамках сценариев модуля СИЗ.
Доступ к сотрудникам и должностям предоставляется только через специализированные
PPE endpoints и только в объёме, необходимом для работы с СИЗ, включая изменение
размеров сотрудников. Универсальные users-admin endpoints ему недоступны.
PPE-разрешения определены в `permission-policy.ts`;
`canBackdatePpeIssue` отдельно разрешает указание даты выдачи только `admin`.
Подробности
и маршруты перечислены в `../ppe/README.md`.

## Better Auth

Самостоятельная регистрация отключена:

```ts
emailAndPassword: {
  enabled: true,
  disableSignUp: true,
}
```

Административный plugin Better Auth остаётся включённым, но его права переопределены в `better-auth-access.ts`.

Администратор может:

- создавать пользователей;
- просматривать пользователей;
- менять роль;
- блокировать и разблокировать;
- устанавливать или менять пароль;
- менять email и данные пользователя;
- просматривать и завершать сессии.

Администратор не может:

- физически удалять пользователя;
- создавать сессию от имени другого пользователя через impersonation.

Права `impersonate`, `impersonate-admins` и `user.delete` не должны добавляться ни одной роли.

## Env

Обязательные переменные:

- `BETTER_AUTH_SECRET` — обязателен во всех средах.
- `BETTER_AUTH_URL` — обязателен в production.
- `FRONTEND_URL` — обязателен в production.

URL проходят строгую проверку:

- только `http:` или `https:`;
- только origin без path, query и hash.

В development разрешены:

- `http://127.0.0.1:5173`
- `http://localhost:5173`

В production localhost не добавляется в trusted origins.

## NestJS permissions

### Доступность ролей по модулям

Все роли зарегистрированы в auth независимо от состава поставки. Назначение
определяется общей политикой `role-module-policy.ts`:

- `chief_engineer`, `engineer` и `operator` требуют `equipment`;
- `ppe_specialist` и `accounting_specialist` требуют `ppe`;
- `storekeeper` требует `warehouse`;
- `admin` и `auditor` доступны всегда.

Состав модулей читается из `database-packages.json` при запуске backend.
После изменения состава требуется перезапуск. Это не заменяет миграции
и не разрешает исключать уже установленные пакеты из обслуживания БД.

API списка ролей возвращает только доступные варианты. Backend проверяет
создание учётной записи и смену ролей общей функцией `validateRoleTransition()`.
Она строго разбирает запрошенный набор, сравнивает его с назначенным и проверяет
доступность только добавленных ролей. При создании прежний набор пуст,
поэтому проверяются все роли. Недоступное новое назначение отклоняется с кодом
`ROLE_MODULE_DISABLED`; некорректный набор — с `INVALID_ROLE`.

Назначенные роли сохраняются при выключении модуля. Отключается только роль,
которой нужен этот модуль; остальные роли продолжают давать свои права.
Например, `engineer,storekeeper` при выбранном `equipment` и выключенном
`warehouse` сохраняет права инженера. Если активных ролей не осталось,
доступны вход, чтение собственной сессии и публичные служебные маршруты.
API профиля и фото в этом случае также запрещены до появления активной роли.
После повторного подключения модуля его роль снова становится активной.

Better Auth `get-session` и API профиля возвращают `role` с активными ролями,
а `assignedRole` — с сохранёнными назначениями. Фильтрация выполняется до
NestJS guards. Backend использует `role` там, где требуется контекст эффективных
ролей. Frontend принимает решения о доступе только по серверным `permissions`;
`role` и `assignedRole` используются для отображения и управления назначениями.
Профиль показывает назначенный набор отдельно от фактических прав.
Изменение представления сессии не меняет значение в БД.

Форма учётной записи поддерживает выбор нескольких ролей. Ранее назначенную
роль выключенного модуля можно сохранить или снять, но нельзя назначить заново.
При обновлении через административный API доступность проверяется для новых
ролей в наборе. Better Auth `set-role` и `update-user` используют ту же политику:
сохранённая недоступная роль не препятствует нормализации прежнего набора или
добавлению другой доступной роли. Редактирование остальных данных без `role`
сохраняет назначения.

Проверка перехода и запись выполняются атомарно. API ESOFT блокирует строку
пользователя `FOR UPDATE` в своей транзакции и вызывает общий validator перед
сохранением. Конфликты сериализации при конкурентном обновлении повторяются
в новой транзакции с повторным чтением назначения.

Database hook Better Auth не удерживает транзакцию записи, поэтому в нём
при обновлении выполняется только строгая нормализация. Проверка перехода
перенесена в `roleAwarePrismaAdapter`: адаптер начинает транзакцию, блокирует
строку `User`, читает текущее назначение, вызывает `validateRoleTransition()`
и сохраняет все переданные изменения до снятия блокировки. Этот же адаптер
используется внутри транзакций Better Auth; замена его обычным `prismaAdapter`
уберёт обязательную проверку обновления ролей.

Изменения ролей через Better Auth поддерживаются для одного пользователя по ID.
Массовый `updateMany` ролей запрещён, чтобы не обходить проверку перехода каждой
учётной записи. Hooks нормализуют строковый или массивный ввод до проверки
реестра ролей самим Better Auth; при создании без роли используется `operator`.
При выключенном `equipment` такое создание отклоняется с `ROLE_MODULE_DISABLED`:
нужно явно выбрать доступную роль. Форма не выбирает недоступного оператора по умолчанию.

Доступ не зависит от проверки URL namespace. Пользователь с
`storekeeper,accounting_specialist` получает объединение складских и PPE
permissions; `engineer,storekeeper` — прав оборудования и склада.

Защита последнего администратора, определение необходимости первоначальной
настройки и выбор ответственных также учитывают отдельные роли в наборе,
а не сравнивают всю строку с одним именем роли.

### Permissions для frontend

Сессия Better Auth и API профиля возвращают `permissions: string[]` — объединение
прав активных ролей, вычисленное по `permission-policy.ts`. Поля `role` и
`assignedRole` сохраняются для отображения и управления назначениями.

Frontend использует `permissions` для маршрутов, навигации, кнопок и описания
доступов. Он не содержит собственной привязки ролей к разрешениям. Если permissions
отсутствуют или пусты, права не выводятся из названия роли. При обогащении сессии
данными профиля права текущего пользователя берутся из сессии.

Backend независимо проверяет каждый запрос глобальным guard. Скрытая кнопка
или клиентский маршрут не заменяют серверную авторизацию. После изменения
назначений или конфигурации модулей клиент получает новые права при обновлении сессии.

### Явные разрешения endpoint

`PermissionsGuard` зарегистрирован единственным глобальным guard приложения.
Сначала он вызывает проверку сессии Better Auth, затем проверяет metadata
конкретного обработчика. Отдельный автоматический Better Auth global guard
отключён, чтобы порядок аутентификации и авторизации был однозначным.

Каждый бизнес-обработчик обязан объявить `@RequirePermission(...)`.
Отсутствие decorator, неизвестное разрешение или неподходящие права приводят к
403, включая запрос администратора к неразмеченному endpoint. Разрешения
и публичность, объявленные на классе, не открывают новые методы автоматически.
Одновременная публичная пометка и permission на методе запрещены.

Модули объявляют действия в собственных `*.permissions.ts`.
`permission-policy.ts` связывает их строковые ID с ролями; он не импортирует
реализацию необязательных модулей. Новое действие нужно явно связать с ролями:
администратор не получает неизвестные permissions через wildcard.

После аутентификации guard повторно фильтрует `user.role` по активным модулям
и передаёт копию эффективного пользователя в `request.session.user` и
`request.user`. `assignedRole` не участвует в выдаче доступа.
Объединение permissions вычисляется по всем активным ролям.

Публичные NestJS обработчики имеют явный `@AllowAnonymous()` на методе:
health, статус setup, список сотрудников первоначальной настройки и создание
первого администратора. Последние два сохраняют проверки состояния setup,
а создание администратора также проверяет origin и ограничивает частоту запросов.
Новые публичные исключения требуют явного изменения списка в тесте покрытия.
Login, get-session и остальные endpoints Better Auth обслуживаются его
middleware с собственной аутентификацией, permissions и hooks.

`users.profile.read` — обычное permission, включённое во все известные роли.
Guard сначала требует это право от активных ролей, затем проверяет ownership:
свой профиль и фото либо чужой профиль и фото при наличии `users.manage`.
Если активных ролей нет, permission отсутствует и запрос запрещён.
Проверка ID выполняется в guard и не дублируется контроллером.
`checklists.work` допускает к рабочим маршрутам, но не заменяет проверку
назначенного исполнителя в сервисе. Аналогично сохраняются проверки владельца
файла и состояния изменяемых записей.

`role-permissions.ts` содержит локальные helpers поверх той же permission-политики.
Они не поддерживают отдельные списки ролей и не заменяют глобальную разметку.
Better Auth access control остаётся отдельным от бизнес-авторизации:

- разрешения ролей описываются декларативно в `permission-policy.ts`;
- `users.manage` — управление учётными записями через глобальный guard;
- `users.profile.read` — глобальный guard проверяет permission и через
  `assertCanViewUserProfile()` ограничивает доступ своим профилем или наличием `users.manage`;
- `equipment.edit` (глобальный guard) — редактирование оборудования;
- `files.manage` (глобальный guard) — работа с файлами;
- `equipment.events.manage` (глобальный guard) — события оборудования;
- `events.manage` / `events.read` (глобальный guard) — события;
- `calendar.read` / `calendar.manage` — доступ к календарю через глобальный guard;
- `checklists.manage` / `checklists.work` — доступ через глобальный guard.

Не смешивать этот файл с `better-auth-access.ts`: Better Auth permissions и бизнес-права NestJS живут отдельно.

Создание первого администратора ограничено пятью попытками с одного IP за
10 минут. Общие счётчики находятся в таблице ядра `setup_rate_limits`; попытка
фиксируется отдельной транзакцией до валидации DTO и создания администратора.
Проверка Origin выполняется первой. Ошибка DTO или создания пользователя
не отменяет уже учтённую попытку.

IP нормализуется и хранится как SHA-256. IPv4 и его IPv4-mapped IPv6 форма
используют один счётчик. Источник IP — Express `request.ip` с fallback на адрес
сокета; backend самостоятельно не читает `X-Forwarded-For`. При настройке
reverse proxy доверять следует только адресам своих прокси.

Таблица ограничена 4096 ключами. Истёкшие записи удаляются при следующем запросе.
При заполнении таблицы новые IP получают `429 SETUP_RATE_LIMITED`, существующие
счётчики продолжают работать. Некорректный или отсутствующий IP также даёт 429.
Если PostgreSQL недоступен, запрос завершается ошибкой, создание администратора
не запускается. Проверка состояния setup и транзакционная блокировка создания
первого администратора остаются отдельными условиями.

## Login hook

После создания обычной пользовательской сессии `AuthLoginService` обновляет `lastLoginAt`.

Impersonation запрещён на уровне Better Auth access control, поэтому login hook не содержит исключений для `impersonatedBy`.

## Правила изменений

Команды выполняются из корня репозитория. При изменении auth-контура проверить:

```bash
npm run build
npm run lint
npm test
```

Целевые unit-проверки auth, назначения ролей, первоначальной настройки
и выбора ответственных:

```bash
npm run test --workspace backend -- --runInBand auth user-accounts-admin.service setup.service events-access.assertions events-query.service
```

`role-module-policy.spec.ts` проверяет доступность назначения по составу модулей.
`multi-role.spec.ts` проверяет разбор наборов, объединение бизнес-прав и
`effective-session.ts`, включая сохранение назначений без изменения исходной сессии.
`permissions.guard.spec.ts` проверяет запрет неразмеченных маршрутов,
multi-role, отключённые роли, публичные исключения и собственный профиль.
`endpoint-permissions.spec.ts` проверяет явную разметку всех контроллеров и
фиксирует ограниченный список публичных обработчиков.

Реальные проверки Better Auth, guards и SQL выполняются отдельно на временном
PostgreSQL. Рабочая БД не используется:

```powershell
npm run build:backend
$env:ESOFT_MODULAR_MIGRATION_TEST = '1'
try {
  node --test tests/scripts/infrastructure/prisma/role-availability.real.integration.test.mjs
} finally {
  Remove-Item Env:ESOFT_MODULAR_MIGRATION_TEST
}
```

Эта проверка покрывает `create-user`, `set-role`, `update-user` и database hooks,
эффективные роли при чтении настоящей сессии, HTTP-доступ к оборудованию и складу,
сохранение и снятие недоступной роли через административный API, запрет её
повторного назначения, SQL-проверку составного `admin`, защиту последнего
администратора, initial setup и проверку ответственных.
Требования к тестовому PostgreSQL:
[DATABASE-PACKAGES.md](../../../docs/DATABASE-PACKAGES.md#проверка-пакетов).

Перед расширением прав Better Auth отдельно проверить, что:

- impersonation остаётся запрещённым;
- физическое удаление пользователей остаётся запрещённым;
- только наличие роли `admin` предоставляет права управления аккаунтами.

### Доступность ответственных оборудования

Список ролей ответственных вычисляется с учётом `ACTIVE_MODULES`.
При выключенном `equipment` кандидатов нет, и назначение ответственного
отклоняется также при прямом вызове сервисов. При включённом модуле учитываются
активные роли с `equipment.read`, кроме самой роли `admin`; пользователь
`admin,engineer` может подходить благодаря `engineer`. Дополнительно требуются
активный сотрудник и неблокированная учётная запись.
