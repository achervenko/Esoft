# Архитектура складского модуля

WarehouseModule подключает компоненты склада. Он не регистрирует их контроллеры
и внутренние сервисы. Новый внутренний сервис добавляется в модуль своего
компонента; корневой файл меняется при подключении нового компонента.

## Компоненты и зависимости

```text
WarehouseModule
  ├─ StorageStructureModule   склады и места
  ├─ ProjectsModule           чтение проектов
  ├─ CatalogModule            номенклатура
  ├─ StockModule              физические остатки
  ├─ ReservationsModule ───── StockModule
  ├─ IssueSheetsModule        задания и их исполнение
  ├─ IssuesModule ─────────── StockModule + ReservationsModule + IssueSheetsModule
  ├─ ReceiptsModule ───────── StockModule
  ├─ StockAdjustmentsModule ─ StockModule
  └─ TransfersModule ───────── StockModule + ReservationsModule
```

Все имена классов компонентов имеют префикс Warehouse. Каждый компонент явно
импортирует необходимую инфраструктуру PrismaModule/AuditModule. ProjectsModule
использует только PrismaModule. Документы корректировок используют глобальную
инфраструктуру StorageModule, зарегистрированную ядром в AppModule; локальная
регистрация хранилища с отдельной конфигурацией не создаётся.

Модули используют обычные imports/exports NestJS. Циклических DI-зависимостей,
forwardRef и глобальных складских провайдеров нет. Повторные импорты StockModule
используют один экземпляр его сервисов.

## Публичные сервисы

- StockModule экспортирует WarehouseStockService. Его HTTP controller и
  WarehouseStockQueryService остаются внутренними.
- ReservationsModule экспортирует WarehouseReservationsService для расхода
  резервов при выдаче. CRUD API резервов остаётся внутренним.
- IssueSheetsModule экспортирует WarehouseIssueSheetsService — контракт
  жизненного цикла и транзакционного исполнения строк. Внутренние сервисы строк,
  запросов, блокировок и переходов не экспортируются.
- ReceiptsModule экспортирует WarehouseReceiptsService для ручного прихода
  и будущего обработчика импорта.
- Catalog, Issues, Transfers, StockAdjustments, StorageStructure и Projects пока не
  экспортируют свои сервисы: существующие потребители используют их HTTP API
  либо чистые контракты данных.

Корневой WarehouseModule реэкспортирует StockModule, IssueSheetsModule и
ReceiptsModule, сохраняя прежний внешний DI API из трёх сервисов. Внутренние
компоненты импортируют нужные компоненты напрямую, не WarehouseModule.
Не добавляйте приватные сервисы соседнего компонента в собственный providers:
это создаёт другой экземпляр и обходит его публичную границу.

## Общие контракты данных

Контракт принадлежит компоненту, который определяет соответствующий справочник:

- catalog/catalog.dto.ts — select и DTO номенклатуры;
- storage-structure/storage-structure.dto.ts — select и DTO склада и места;
- stock/stock.types.ts — остаток, фильтры и контекст мутации Stock.

Потребители используют эти select и DTO вместо повторного перечисления полей
и самостоятельной сериализации bigint. В контрактах нет Nest-сервисов, чтения БД
или импорта модулей: их можно использовать без подключения DI-компонента.

У номенклатуры три существующих представления: identity (id, article, name, unit)
в истории выдачи, summary (identity + isActive) в остатках и резервах, полная
карточка (summary + comment) в каталоге. Они построены друг на друге. Изменение
общего поля задаётся в контракте владельца; разные представления не получают
чужие поля автоматически.

DTO явно перечисляют публичные поля. Добавление scalar-колонки Prisma-модели
само по себе не публикует её через API. Warehouse/location bigint ID
сериализуются в строки одинаково во всех потребителях.

Исторические snapshots приходов, перемещений, выдач и позиций выдач хранятся
в самих операциях; их нельзя пересобирать из текущих справочников. GET выдач
читает собственные снимки, включая расход резервов, без зависимости от аудита
или сохранённых ответов идемпотентности. Последние остаются техническим контрактом replay. Валидация
разных payload/query остаётся у соответствующих операций; одинаково названные
поля не означают одинаковые требования или ошибки HTTP.

## Общие проверки и транзакции

storage-structure/storage-structure.policy.ts содержит lockWarehouse и
warehouseNotFound. Это чистый транзакционный контракт, который принимает tx
вызывающего компонента. Приходы, выдачи и листы не импортируют CRUD-сервис склада
ради блокировки.

Stock отвечает за количество и блокировки остатков. Бизнес-компонент отвечает
за допустимость операции, документ, резервы, идемпотентность и общую транзакцию.
Выделение NestJS-модулей не создаёт новые транзакции и не меняет порядок locks.
Механизм расхода резервов не импортирует DTO/ошибки компонента Issues.
Коды бизнес-ошибок, маршруты и формат ответов сохранены.

## Проверки границ

warehouse.module.spec.ts собирает реальные модули через Nest TestingModule с
подменой только инфраструктуры БД/Storage. Он проверяет внешнюю инъекцию трёх
публичных сервисов, единый экземпляр Stock, наличие контроллеров и недоступность
внутреннего Stock query-сервиса для импортирующего модуля.

warehouse-contracts.spec.ts проверяет совместимость представлений справочников
и остатков, точность bigint ID, JSON-сериализацию и отсутствие полей каталога
в сокращённых DTO. Бизнес-интеграции продолжают проверять поведение операций
на временном PostgreSQL.
