# Адаптер обмена приходов

Общая инфраструктура вынесена в `IntegrationsModule`. Этот компонент регистрирует `WarehouseReceiptIntegrationHandler` для `warehouse.receipts`: проверка versioned config, контракта документа 1С и вызов публичного API импорта прихода. Ядро не импортирует склад.

Импорт сохраняет идемпотентность по sourceCode/objectId и нормализованному содержимому, даже при повторной доставке уведомлений. Перед загрузкой и применением обработчик берёт advisory lock объекта внутри доменной транзакции; HTTP и импорт ограничены timeout. Проверка полномочий автора выполняется в той же транзакции. Физические остатки импорт документа не меняет — только последующее размещение.

Входящие события принимаются только общим `POST /api/integrations/sources/:code/flows/warehouse.receipts/events`. Источники, ключи, очередь, повторы и журнал принадлежат ядру интеграций. Отдельных складских очередей и административных адаптеров нет.

## Склады обмена

В «Интеграциях» кнопка «Склады 1С» открывает административное сопоставление идентификатора склада 1С со складом ESoft. Чтение и сохранение выполняются через `GET/PUT /api/warehouse/integrations/sources/:code/warehouses`, требуют `integrations.manage` на HTTP-уровне и внутри транзакции. Сопоставления изолированы по коду источника, создание аудируется атомарно. Повтор той же связи идемпотентен; переназначение на другой склад отклоняется конфликтом. Действующие приходы не изменяются.

Публичный API импорта Receipts сам проверяет сопоставление и активность склада до записи и идемпотентного выхода; строки связи и склада блокируются через `FOR SHARE` до конца транзакции. Обработчик преобразует доменные ошибки в коды интеграции. Неизвестный склад даёт `ONE_C_WAREHOUSE_UNMAPPED`, выключенный склад ESoft — `ONE_C_WAREHOUSE_INACTIVE`. Для нового документа событие переходит в `SKIPPED` без прихода и автоматических повторов; сохраняются только краткие реквизиты и причина. Пропущенные события удаляются через 30 дней. Для ранее импортированного документа остаётся `FAILED`. После исправления настройки администратор повторяет событие из журнала. Изменение/отмена уже известного документа с посторонним складом тоже остаётся ошибочным событием для администратора, а не молча отбрасывается.

Уведомление 1С содержит только `{ "objectId": "..." }`. Общий inbox создаёт внутренний eventId для каждой доставки. Каждая доставка делает GET полного актуального документа; статус берётся из ответа. Проверка склада выполняется до идемпотентного выхода. `applySnapshot()` сравнивает нормализованное содержимое с последним рассмотренным снимком и назначает внутреннюю редакцию ESoft только при изменении. Внешняя версия документа не требуется и не используется для этого пути. GET одного документа сериализован блокировкой до запроса, чтобы более ранний параллельный ответ не перезаписал поздний. Различить устаревшую реплику без версии невозможно: 1С должна гарантировать актуальный согласованный GET.
