# Адаптер обмена приходов

Общая инфраструктура вынесена в `IntegrationsModule`. Этот компонент регистрирует `WarehouseReceiptIntegrationHandler` для `warehouse.receipts`: проверка versioned config, контракта документа 1С и вызов публичного API импорта прихода. Ядро не импортирует склад.

Импорт сохраняет идемпотентность по sourceCode/objectId и нормализованному содержимому, даже при повторной доставке уведомлений. Перед загрузкой и применением обработчик берёт advisory lock объекта внутри доменной транзакции; HTTP и импорт ограничены timeout. Проверка полномочий автора выполняется в той же транзакции. Физические остатки импорт документа не меняет — только последующее размещение.

Входящие события принимаются только общим `POST /api/integrations/sources/:code/flows/warehouse.receipts/events`. Источники, ключи, очередь, повторы и журнал принадлежат ядру интеграций. Отдельных складских очередей и административных адаптеров нет.

## Склады обмена

В «Интеграциях» кнопка «Склады 1С» открывает административное сопоставление идентификатора склада 1С со складом ESoft. Чтение и сохранение выполняются через `GET/PUT /api/warehouse/integrations/sources/:code/warehouses`, требуют `integrations.manage` на HTTP-уровне и внутри транзакции.

Сопоставления сохраняют код технического источника. Для складов одной базы 1С внешний UUID является общей идентичностью независимо от подключения. Повторное сопоставление с тем же складом допускается, назначение того же UUID другому складу ESoft отклоняется. Создание сопоставления аудируется атомарно. Действующие приходы не изменяются.

Публичный API импорта Receipts сам проверяет сопоставление и активность склада до записи и идемпотентного выхода; строки связи и склада блокируются через `FOR SHARE` до конца транзакции. Обработчик преобразует доменные ошибки в коды интеграции. Неизвестный склад даёт `ONE_C_WAREHOUSE_UNMAPPED`, выключенный склад ESoft — `ONE_C_WAREHOUSE_INACTIVE`. Для нового документа событие переходит в `SKIPPED` без прихода и автоматических повторов; сохраняются только краткие реквизиты и причина. Пропущенные события удаляются через 30 дней. Для ранее импортированного документа остаётся `FAILED`. После исправления настройки администратор повторяет событие из журнала. Изменение/отмена уже известного документа с посторонним складом тоже остаётся ошибочным событием для администратора, а не молча отбрасывается.

Уведомление 1С содержит только `{ "objectId": "..." }`. Общий inbox создаёт внутренний eventId для каждой доставки. Каждая доставка делает GET полного актуального документа; статус берётся из ответа. Проверка склада выполняется до идемпотентного выхода. `applySnapshot()` сравнивает нормализованное содержимое с последним рассмотренным снимком и назначает внутреннюю редакцию ESoft только при изменении. Внешняя версия документа не требуется и не используется для этого пути. GET одного документа сериализован блокировкой до запроса, чтобы более ранний параллельный ответ не перезаписал поздний. Различить устаревшую реплику без версии невозможно: 1С должна гарантировать актуальный согласованный GET.

## Загрузка накладных за период

`one-c-invoices.ts` загружает страницы `GET /ERP/hs/docs/invoices` через общий HTTP-клиент с базовым адресом `/ERP/hs/docs/`. `one-c-invoices.validation.ts` проверяет период, метаданные и согласованность выборки. `one-c-invoice-snapshot.ts` нормализует документ и строки, сохраняя внешние UUID. Загрузчик возвращает снимки в память.

`dateFrom` и `dateTo` передаются как локальные даты `YYYY-MM-DDTHH:mm:ss` без преобразования часового пояса. Начальные и конечные значения могут совпадать. Первая страница запрашивается с `start=1`, следующая — с позицией после всех принятых документов. В ответе ожидаются `data`, `Start_number` и `Total_number`. Применяются пределы 50 документов на страницу, 100 страниц и 5000 документов на период. Размер ответа ограничен общим клиентом до 2 МиБ на запрос, отдельный лимит строк накладной пока не вводится. Автоматическое разбиение больших периодов остаётся отдельной задачей перед подключением расписания.

Общий дедлайн загрузки — 45 секунд, тайм-аут HTTP-клиента — 10 секунд на запрос. Внешняя отмена прерывает текущий запрос и ожидание повтора. Ошибки соединения, тайм-аут запроса и HTTP 408/502/503/504 допускают до трёх попыток на страницу с паузами 200 и 400 мс в пределах общего дедлайна. Общий транспорт не обрабатывает `Retry-After`, поэтому HTTP 429 возвращается вызывающему коду для повторного запуска позже. Некорректные данные и отмена повторов не запускают.

| Код                               | Условие                                                                                |
| --------------------------------- | -------------------------------------------------------------------------------------- |
| `ONE_C_INVOICES_PERIOD_INVALID`   | Некорректная дата или порядок границ                                                   |
| `ONE_C_INVOICES_RESPONSE_INVALID` | Некорректная структура страницы, документа или строки                                  |
| `ONE_C_INVOICES_INCOMPLETE`       | Счётчик изменился, количество превышено, страница неожиданно пуста или UUID повторился |
| `ONE_C_INVOICES_RESPONSE_LIMIT`   | Превышен лимит периода или числа страниц                                               |
| `ONE_C_INVOICES_TIMEOUT`          | Истёк общий дедлайн                                                                    |
| `INTEGRATION_HTTP_ABORTED`        | Внешняя отмена                                                                         |

Остальные ошибки общего HTTP-клиента сохраняют свой код. Любая ошибка прерывает загрузку периода целиком. Счётчик `Total_number` используется как получен. Даже при совпадении числа уникальных UUID с ним изменение данных или порядка между запросами может привести к пропуску. Для надёжного обмена нужен подтверждённый стабильный порядок и согласованный снимок 1С на весь период.

Внешние статусы `POSTED`, `CREATED` и `CANCELED` сохраняются как получены. Загрузчик допускает пустые `lines` для всех трёх статусов до уточнения контракта. Действующий импорт требует положительное количество и непустые строки у проведённого документа. В загрузчике `stockQuantity(value, true)` допускает от 0 до 99999999999.999 с точностью до трёх знаков. JSON-число передаётся в валидатор через `String()`. Точность, потерянную при разборе JSON-числа, восстановить нельзя. Если 1С передаёт значения, для которых важна исходная десятичная запись, количество следует отдавать строкой.

1С отбирает накладные по времени последнего изменения. Поле `date` содержит дату документа. Поэтому старая накладная попадает в новое окно после изменения. Повтор с тем же нормализованным содержимым сохраняет номер редакции.

Для приёмки сохраните исходные JSON-ответы за один и тот же период с более чем 50 документами. Начинайте с `start=1`, затем запрашивайте `start=51`, `start=101` и далее до конца выборки. Проверьте, что `Total_number` одинаков на всех страницах и совпадает с числом уникальных UUID во всех массивах `data`. На последней странице допустимо от 1 до 50 документов. Отдельно сохраните ответы за пустой период, за период прежней ошибки `ЗаписатьJSON` и за соседние интервалы с общей границей. Включите в проверку накладную с датой документа раньше окна запроса и временем изменения внутри окна.

## Импорт периода

`OneCInvoicePeriodImportService.importPeriod(code, period, signal)` — внутренняя точка входа для планировщика. Код источника берётся из настроек интеграции, используются его действующий поток `warehouse.receipts`, системный актор и общий клиент 1С. Базовый URL источника должен оканчиваться на `/hs/docs/`. Сервис полностью проверяет выборку до первой записи.

Каждая накладная сохраняется в `warehouse_invoice_snapshots` по ключу `invoice_id`. В записи остаются все строки, актуальный снимок, номер его редакции, хеш, время начала и окончания получения, последний результат. Повторы с тем же содержимым не создают копий. Отдельный срок очистки снимков пока не задан. `reprocess(code, invoiceId)` применяет сохранённый снимок после настройки связей. Ошибка записи оставляет снимок доступным для повторной обработки. Результат и изменения приходов фиксируются одной транзакцией на накладную. При потере подтверждения COMMIT снимка сервис повторяет сохранение того же наблюдения под блокировкой накладной. Совпадение хеша и времени наблюдения подтверждает сохранение снимка, после чего запускается импорт. При потере подтверждения COMMIT импорта сервис сверяет сохранённый результат.

Строки группируются по внешнему UUID склада. Допускаются только активные склады с однозначной связью в базе 1С. Разные внешние склады сохраняют отдельные группы даже при общем внутреннем складе. Ключ существующего импортёра — `ONE_C` и `invoice:<uuid накладной>:<uuid склада>`. Если под исходным UUID в базе 1С уже есть приход старого формата, обработка возвращает `ONE_C_INVOICE_LEGACY_RECEIPT_EXISTS`. Такой документ требует отдельной сверки перед переходом на новый поток.

Номенклатура сопоставляется через существующий каталог по внешнему UUID. Несопоставленный товар остаётся в ожидаемом приходе со своими внешними реквизитами. Для сопоставления заказов используется глобальный внешний UUID. Связь с не найденным заказом сохраняет внешний UUID и возвращает диагностику по группе. Сервер блокирует размещение такой строки. После штатного обновления заказов следующая попытка размещения пересроверяет связь и использует действующий сценарий размещения под заказ. Сопоставление с ручным приходом для новых строк заказа заблокировано, поскольку оно само по себе не формирует резерв.

`CREATED` и `CANCELED` сохраняются технически. Существующие ожидаемые приходы приостанавливаются, а при фактическом размещении фиксируется конфликт. Последующий `POSTED` повторно проверяется по текущим данным и размещениям. Перенос или изменение идентичности строки с размещением блокирует обработку групп накладной. `row_no` используется вместе с внешними UUID товара и заказа, единицей и типом. Изменение количеств у неразличимых строк с размещением рассматривается как конфликт. Возврат к совместимой редакции допускает повторную проверку. Обновление или отмена накладной не проводит складские движения.

Результат периода разделяет число полученных накладных, сохранение снимка и результаты обработки групп. Пропуски и конфликты сохраняются с причиной. Аудит складских приходов остаётся в действующем журнале. Пустой новый документ сохраняется в снимке. Группы с нулевым количеством или сверх лимита действующего импортёра требуют исправления данных 1С. Источник 1С должен отдавать согласованную выборку и актуальные редакции документов. Без версии со стороны 1С сервис может отсечь результат более раннего запроса, но не может распознать устаревшие данные, возвращённые в более позднем запросе.

Если складская группа получила `UNMAPPED`, `INACTIVE` или `AMBIGUOUS`, импорт периода возвращает ошибку `ONE_C_INVOICE_WAREHOUSE_GROUPS_PENDING`. Планировщик сохраняет границы окна для повтора и оставляет контрольную точку на месте. Уже созданные приходы сохраняются, а повтор использует те же идентификаторы групп.

### История редакций

`warehouse_invoice_snapshot_versions` хранит неизменяемые полные снимки всех обнаруженных изменений. Ключ редакции — `(invoice_id, version)`. Первая редакция получает номер 1. При изменении хеша нормализованного документа номер увеличивается на единицу. Возврат к прежнему содержимому создаёт следующую редакцию с прежним хешем. Повтор того же содержимого и повторная обработка после настройки связей сохраняют текущий номер.

Актуальный снимок и редакция записываются атомарно под существующей блокировкой накладной. PostgreSQL запрещает изменение, удаление и очистку строк истории. Бизнес-импорт выполняется после сохранения снимка. Ошибка импорта меняет результат обработки актуального снимка, а полученная редакция сохраняется. История включает состояния, реально полученные ESoft. Промежуточные правки в 1С между успешными загрузками из неё восстановить невозможно.

Контрольную точку можно продвигать только при результате периода `SUCCESS`. `PARTIAL_FAILURE` означает, что часть документов обработана, а `FAILED` означает, что подтверждённых документов нет. `errorCount` включает ошибки и документы, вытесненные более новым запуском без подтверждения обработки в текущем запуске. При любом из этих двух результатов период можно безопасно повторить. Ошибка полной загрузки из 1С или прерывание операции отклоняет вызов целиком.

### Расписание

В настройках существующего источника в разделе «Интеграции» включите «Автоматический импорт накладных». Параметры сохраняются в конфигурации потока `warehouse.receipts`. Новый источник создаётся с выключенным расписанием. Для включения укажите `initialFrom` с секундами и явным смещением или `Z`, например `2026-11-18T08:00:00+03:00`. Часовой пояс API по умолчанию `Europe/Moscow`. Интервал проверки (`intervalSeconds`) составляет 30 секунд, размер окна 60 минут, перекрытие 15 минут. Перекрытие должно быть меньше окна.

Планировщик проверяет источники при старте и раз в секунду. Один экземпляр Backend обрабатывает до двух источников одновременно. При заполнении слотов источники получают доступ по очереди. При отставании он выполняет по одному окну на источник за проверку. Верхняя граница отстаёт от текущего времени на минуту. Контрольные точки хранятся как однозначные моменты времени, а границы для 1С передаются в часовом поясе источника с точностью до секунды. Соседние окна используют общую границу даже при нулевом перекрытии. При превышении лимита текущая попытка делит окно, сохраняя общую границу частей. Точка продвигается только после успеха каждой части. Если минимальное окно превышает лимит, прогресс останавливается и в журнале остаётся ошибка.

Таблица `warehouse_invoice_sync_state` хранит одну запись на источник и поток. В ней сохраняются контрольная точка, границы последнего окна, время повтора, счётчик ошибок и время последнего успеха. После обрыва незавершённое окно повторяется с прежними границами. Advisory-блокировка PostgreSQL сериализует запуски. Обновление состояния проверяет токен владельца, а хеш конфигурации защищает от завершения по устаревшим настройкам. Состояние и запись о результате фиксируются в одной транзакции.

Журнал `warehouse_invoice_sync_runs` хранит диагностические записи попыток. Для очистки используется индекс по `finished_at`. Можно удалять завершённые записи по выбранной дате, оставляя строки с `finished_at IS NULL`. Очистка журнала сохраняет контрольную точку, повторы, настройки и историю редакций. Автоматической очистки нет. Повторы идут через 1, 2, 4 минуты и далее с пределом 30 минут. Ошибки авторизации и адреса приостанавливают попытки до изменения настроек.

Обе таблицы создаёт `warehouse_init`. Если эта миграция уже применена с прежней контрольной суммой, подготовьте отдельную БД штатным развёртыванием текущих миграций. После резервного копирования перенесите пользовательские данные в новую схему с учётом различий, проверьте связи, количества записей и последовательности. История `_prisma_migrations` в новой БД формируется штатным развёртыванием. Переключайте приложение только после сверки, сохранив исходную БД для отката.

Маршрут `GET /api/warehouse/integrations/sources/:code/invoice-schedule` возвращает состояние расписания для `integrations.manage`. Запуск произвольного периода через HTTP отсутствует.
