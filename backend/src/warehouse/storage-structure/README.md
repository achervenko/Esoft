# Склады и места хранения

Обязательная принадлежность выдач и листов складу, warehouseId-фильтры и состав DTO описаны в [контракте границ складов](WAREHOUSE-BOUNDARIES.md).

Единый `WarehouseStorageStructureModule` подключается внутри `WarehouseModule`.
Два контроллера и два сервиса обслуживают один справочник структуры хранения:
склад и принадлежащие ему места. Отдельных модулей для каждой сущности нет.

Место хранения не имеет фиксированного типа или уровня: это может быть ячейка,
палетоместо, угол, помещение или ангар. Вложенность мест и правила складских
процессов в этот компонент не входят.

## Модель

- `Warehouse` (`warehouses`): `id`, `code`, `name`, `isActive`.
- `WarehouseStorageLocation`: те же поля и обязательный `warehouseId`.
- Код склада уникален глобально; код места уникален только внутри склада.
- Склад места задаётся при создании и не меняется через PATCH: перенос места
  вместе с остатками и историей не является редактированием справочника.
- Остатки и документы по-прежнему ссылаются на ID места; второй `warehouseId`
  в остатках не хранится.
- Склады не создаются автоматически. Сначала создайте склад через API,
  затем создавайте его места с полученным `warehouseId`.

Исходная миграция ещё не установленного пакета warehouse обновлена вместе с
контрольной суммой manifest. Это схема для новой установки, не миграция обновления
ранее установленного пакета. На рабочую БД изменения автоматически не применяются.

## API

Для обоих ресурсов доступны GET списка, GET `/:id`, POST и PATCH `/:id`:

- `/api/warehouse/warehouses` — склады;
- `/api/warehouse/storage-locations` — места хранения, прежний путь сохранён.

DELETE отсутствует. Нужна активная сессия. Оба ресурса используют общие существующие
разрешения `warehouse.storage-locations.read` и `warehouse.storage-locations.manage`
(admin/storekeeper). Названия разрешений сохранены для совместимости с текущими
ролями и интерфейсом. Мутации повторно проверяют пользователя, banned и manage
под `FOR SHARE` в своей транзакции.

Создание склада:

```json
{ "code": "PROJECTS", "name": "Проектный склад" }
```

Создание места:

```json
{ "warehouseId": "1", "code": "A-01", "name": "Угол ангара" }
```

`isActive` необязателен при создании, по умолчанию true.
PATCH обоих ресурсов принимает непустое подмножество `code`, `name`, `isActive`.
Передача `warehouseId` в PATCH места запрещена, даже если значение не изменяется.
Строки обрезаются по краям: code 1–100, name 1–255 символов. NUL, неизвестные поля,
null и некорректные типы отклоняются. ID — канонические положительные bigint-строки.

DTO склада содержит `id`, `code`, `name`, `isActive`.
DTO места дополнительно содержит `warehouseId` и вложенный `warehouse` с DTO склада.
GET места `/:id` также возвращает `hasStock`: наличие положительного остатка.
Все ID в JSON строковые, включая вложенные объекты.

Оба списка возвращают `{items,total,page,limit}` и принимают:

- `search`: поиск по коду и названию, до 255 символов, без учёта регистра;
  `%`, `_`, `\` трактуются буквально;
- `isActive`: строго `true` или `false`, без фильтра возвращаются оба состояния;
- `page`: от 1; `limit`: от 1 до 100, по умолчанию 50;
- `sortBy`: `code`, `name`, `isActive`; `sortOrder`: `asc`, `desc`.

Список мест дополнительно принимает `warehouseId`. Фильтры объединяются через AND.
Список и total читаются в одном RepeatableRead-снимке. Сортировка по умолчанию —
code ASC, дополнительный ключ — id ASC.

## Активность и конкурентность

Нельзя создать место на неактивном складе или активировать место такого склада.
Деактивация склада запрещена, пока у него есть хотя бы одно активное место.
Это предотвращает появление активных мест у отключённого склада без каскадного
изменения мест и истории. После повторной активации склада места не активируются
автоматически.

Деактивация места, как и ранее, допускается при ненулевом остатке. Количества,
резервы и документы сохраняются. Неактивное место можно переименовать.

Порядок блокировок мутации места: пользователь → склад FOR SHARE → место FOR UPDATE.
Изменение склада берёт склад FOR UPDATE; создание/активация места и деактивация
склада поэтому согласованы. Stock по-прежнему блокирует место при складских
операциях; существующие правила активности мест в Issues и Reservations сохранены.
Сам внутренний Stock не принимает решений об активности справочников.

Аудит и изменение атомарны. Для склада `entityType=warehouse`, для места
`warehouse_storage_location`; `entityStringId` содержит строковый ID. Склад места
фиксируется в аудите создания. Передача прежних значений не создаёт ложного аудита.

## Ошибки

- 404 `WAREHOUSE_NOT_FOUND`, `WAREHOUSE_STORAGE_LOCATION_NOT_FOUND`.
- 409 `WAREHOUSE_CODE_CONFLICT`, `WAREHOUSE_STORAGE_LOCATION_CODE_CONFLICT`.
- 409 `WAREHOUSE_INACTIVE`, `WAREHOUSE_HAS_ACTIVE_LOCATIONS`.
- 400 `INVALID_WAREHOUSE_ID`, `INVALID_STORAGE_LOCATION_FIELD`, `INVALID_QUERY`,
  `INVALID_PAYLOAD`, `UNKNOWN_FIELDS`, `EMPTY_PAYLOAD`.

`INVALID_STORAGE_LOCATION_FIELD` используется общей валидацией обоих справочников.

## Проверка

```powershell
npm run db:generate
npm run build:backend
npm run test --workspace backend -- --runInBand warehouse optional-warehouse
$env:ESOFT_MODULAR_MIGRATION_TEST = '1'
try {
  node --test tests/scripts/infrastructure/prisma/storage-locations.real.integration.test.mjs
} finally {
  Remove-Item Env:ESOFT_MODULAR_MIGRATION_TEST
}
```

Интеграционные проверки используют временный PostgreSQL с core + warehouse.
Проверяются уникальность в пределах склада, фильтрация, запрет перепривязки,
доступ, атомарный аудит и гонки деактивации склада с созданием/активацией места.
В существующем frontend справочника мест добавлены выбор склада при создании
и колонка склада. Отдельная страница управления складами пока не добавлена.
