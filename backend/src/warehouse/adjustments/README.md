# StockAdjustments

Компонент оформляет административную корректировку физического остатка.

`WarehouseStockAdjustmentsService` — тонкий фасад для controller. Реализация разделена:

- `adjustment-access.service.ts` — проверка прав и блокировка пользователя в транзакции;
- `adjustment-query.service.ts` — карточка и список корректировок;
- `adjustment-document.service.ts` — загрузка документов и правила форматов;
- `adjustment-command.service.ts` — цельная транзакция проведения корректировки;
- `adjustments.mapper.ts` — общий Prisma include и преобразование в DTO;
- `adjustments.constants.ts` — scope владельца документов `ADJUSTMENT_OWNER`.

Доступ предоставляет отдельное permission `warehouse.adjustments.manage`,
выданное только `admin`. Проверяется глобальным guard и повторно в сервисе:
текущая запись пользователя блокируется `FOR SHARE` внутри транзакции проведения,
проверяются permission и отсутствие блокировки аккаунта. Кладовщик доступа не имеет.

## API

- `POST /api/warehouse/adjustments/documents`: multipart `file`, один документ
  до 25 МБ. Возвращает `uploadId`, имя, размер, SHA-256 и срок действия 24 часа.
  Допускаются PDF, JPEG, PNG и WebP с проверкой содержимого.
- `POST /api/warehouse/adjustments`: провести корректировку с 1–10 `uploadId`.
- `GET /api/warehouse/adjustments`: список, фильтры `itemId`, `locationId`, `type`,
  `page` (по умолчанию 1), `limit` (по умолчанию 50, максимум 100).
  Сортировка — время и ID по убыванию. Ответ `{ items, total, page, limit }`.
- `GET /api/warehouse/adjustments/:id`: карточка проведённой корректировки.
- `GET /api/warehouse/adjustments/:id/documents/:fileId/download`: скачивание
  документа только в контексте этой корректировки и с правами администратора.

Редактирования и удаления проведённых корректировок и их документов нет.
Неверную корректировку исправляют новой операцией с отдельным основанием.
Отдельного frontend-интерфейса компонент пока не предоставляет.

```json
{
  "requestKey": "da0ec99c-a7c0-4948-88ec-4aaf8155dd5f",
  "itemId": "15",
  "locationId": "8",
  "type": "WRITE_OFF",
  "quantity": "4",
  "reason": "Недостача при пересчёте",
  "comment": "Акт инвентаризации",
  "attachments": ["05f8264c-53a4-499e-aee5-b44416979ed3"]
}
```

`WRITE_OFF` уменьшает, `SURPLUS` увеличивает количество. `quantity` — положительная
десятичная строка с точностью до трёх знаков либо Decimal при внутреннем вызове.
Для JSON используется строка. ID склада — строки bigint. Причина обязательна,
обрезается по краям, до 1000 символов; комментарий необязателен, до 4000 символов.
Неизвестные поля отклоняются. `attachments` содержит именно ID временных загрузок,
а не ID существующих файлов, URL, пути или ключи MinIO. Документы должны принадлежать
автору запроса и scope `warehouse / stock_adjustment`.

Вместо `type` и `quantity` можно передать `actualQuantity` и `expectedQuantity`:

```json
{
  "requestKey": "7fd8d33c-958e-409d-9f73-eab577427270",
  "itemId": "15",
  "locationId": "8",
  "actualQuantity": "16",
  "expectedQuantity": "20",
  "reason": "Фактический пересчёт",
  "attachments": ["05f8264c-53a4-499e-aee5-b44416979ed3"]
}
```

Backend под блокировкой сравнивает текущий остаток с `expectedQuantity` и вычисляет
дельту. Несовпадение даёт `409 WAREHOUSE_ADJUSTMENT_STALE_BALANCE`. При нулевой
дельте ответ `{ changed: false, quantity, adjustment: null }`, корректировка
и аудит не создаются, загрузки остаются временными. Для отсутствующего остатка
при подсчёте фактического количества исходное количество считается нулём;
саму нулевую запись Stock при этом не создаёт.

При изменении ответ `{ changed: true, adjustment }` содержит ID операции,
идентификаторы номенклатуры (`itemId`), места (`locationId`) и остатка (`balanceId`),
тип, количество, до/после, основание, комментарий, ID пользователя, дату,
ключ запроса (`requestKey`) и сведения о прикреплённых файлах.

## Проведение и резервы

StockAdjustments не присваивает `WarehouseBalance.quantity` напрямую. Используются
только `Stock.issueStock` / `Stock.receiveStock`. Нулевой остаток сохраняется,
отрицательный и превышение `numeric(14,3)` запрещены.

Списание может уменьшить физическое количество ниже суммы резервов. Резервы
**не изменяются**: это сохранённая потребность проектов. Например, physical=16
и reserved=18 означают shortage=2, available=0. Дефицит вычисляется как
`MAX(reserved - physical, 0)`, свободное количество — `MAX(physical - reserved, 0)`.
Компонент не распределяет недостачу между проектами и не оформляет дозаказ.
Активность номенклатуры и места автоматически не меняется.

Порядок проведения: блокировка пользователя → advisory-блокировка ключа запроса →
временные документы по UUID → блокировки Stock → изменение физического остатка →
создание корректировки → привязка неизменяемых файлов → общий аудит.
Используется одна PostgreSQL-транзакция `ReadCommitted`; ошибка откатывает
остаток, корректировку, привязки, удаление временных записей и аудит.

MinIO не является участником PostgreSQL-транзакции. Файлы загружаются заранее,
а неиспользованные объекты удаляет общий обработчик просроченных `StorageUpload`.
При ошибке проведения документы доступны для повторной попытки до истечения срока.

`requestKey` — UUID, уникальный в пределах пользователя. Повтор того же запроса
возвращает прежнюю корректировку без повторного изменения остатка. Иное содержимое
с тем же ключом даёт `409 WAREHOUSE_ADJUSTMENT_REQUEST_CONFLICT`.
Клиент сохраняет ключ и ID загрузок при повторе после сетевой ошибки;
для новой операции создаёт новый ключ. Нулевая дельта не резервирует ключ.

## Аудит и ошибки

Кроме аудита физического остатка Stock, сохраняется снимок корректировки:
номенклатура, единица, место, тип, количество до/после, сумма резервов и дефицит,
основание, комментарий, ID и имена документов с SHA-256. Общий аудит хранит автора
и время. Идентификатор операции записывается в `entityStringId`, модуль — `WAREHOUSE`,
тип сущности — `warehouse_stock_adjustment`. SQL CHECK согласует направление
операции, положительное количество и значения до/после.

Ошибки используют `{ code, message, details? }`:

- `403 FORBIDDEN`: нет административного permission или аккаунт заблокирован.
- `400 WAREHOUSE_ADJUSTMENT_INVALID`: неверный payload или обязательные документы.
- `409 WAREHOUSE_ADJUSTMENT_STALE_BALANCE`: устаревший ожидаемый остаток.
- `409 WAREHOUSE_ADJUSTMENT_REQUEST_CONFLICT`: повторный ключ с другим содержимым.
- `404 WAREHOUSE_ADJUSTMENT_NOT_FOUND`: корректировка не найдена.
- `409 STORAGE_UPLOAD_UNAVAILABLE`: чужая, использованная, истёкшая или отсутствующая загрузка.
- `409 STORAGE_FILE_IMMUTABLE`: попытка изменения документа проведённой операции.
- `503 STORAGE_UPLOAD_FAILED`: загрузка не завершена; Stock не изменён.

Ошибки существования номенклатуры/места, достаточности и формата количества
передаются из Stock. Ошибки инфраструктуры не подменяются бизнес-причинами.

## Проверка

```powershell
npm run db:generate
npm run build:backend
npm run test --workspace backend -- --runInBand warehouse storage
$env:ESOFT_MODULAR_MIGRATION_TEST = '1'
try {
  node --test tests/scripts/infrastructure/prisma/warehouse-adjustments.real.integration.test.mjs
} finally {
  Remove-Item Env:ESOFT_MODULAR_MIGRATION_TEST
}
```

Интеграционная проверка использует изолированный PostgreSQL с `core + warehouse`;
объектное хранилище в ней заменено управляемым тестовым адаптером, позволяющим
воспроизводить ошибки загрузки и очистки. Рабочая БД и MinIO не используются.
