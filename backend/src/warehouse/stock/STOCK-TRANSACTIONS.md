# Stock: транзакции и блокировки

Контракт для сервисов, изменяющих физические остатки.
[Обзор Stock](README.md) · [API и форматы данных](STOCK-API.md).

## Внутренний API изменения остатков

- `receiveStock(context, itemId, locationId, quantity)` увеличивает остаток,
  создавая запись при необходимости; возвращает обновлённый остаток.
- `issueStock(context, itemId, locationId, quantity)` уменьшает свободное
  количество; возвращает обновлённый физический остаток.
- `moveStock(context, itemId, fromLocationId, toLocationId, quantity)` возвращает
  `{ from, to }`. Уменьшение и увеличение проходят в одной транзакции.
  На исходном месте расходуется только свободное количество.

В `context` обязательны `tx: Prisma.TransactionClient` и `actorUserId: string`.
Методы изменения не открывают и не фиксируют собственных транзакций.
Ошибка должна выйти из callback транзакции: её нельзя перехватить и затем
зафиксировать частично выполненную операцию. Повтор всего документа и обработка
конфликтов транзакций выполняются вызывающим компонентом.

`lockBalances(tx, itemId, locationIds)` блокирует полный набор мест одной
номенклатуры перед проверкой или изменением количества. Форматы ID и количества
описаны в [STOCK-API.md](STOCK-API.md#id-количества-и-dto-баланса).
`lockAvailability(tx, itemId, locationId)` блокирует одну пару и возвращает
`physical`, `reserved` и `free` как `Prisma.Decimal`.

## Запись, блокировки и границы ответственности

Пара `(item_id, storage_location_id)` уникальна в БД. При достижении нуля строка
сохраняется. Stock не удаляет остатки и не принимает отрицательные количества.
Уменьшать или увеличивать физическое количество следует только через Stock.

Порядок блокировок для одной номенклатуры:

1. `warehouse_items FOR SHARE` — согласование с `FOR UPDATE` в Catalog,
   запрещающее смену единицы одновременно с созданием первого остатка.
2. Места хранения `FOR SHARE` по числовому ID по возрастанию.
3. Для каждой пары в том же порядке: транзакционная advisory-блокировка
   `hashtextextended('warehouse:stock:<itemId>:<locationId>', 0)`, затем
   существующий остаток `FOR UPDATE`. Advisory-блокировка защищает и ещё
   отсутствующую строку, которую невозможно заблокировать через `FOR UPDATE`.

Проверки достаточности и переполнения выполняются до записи количества.
Мутации и `lockAvailability()` требуют `ReadCommitted`. После ожидания
блокировки сумма размещений должна читаться из актуального снимка.
Свободное количество равно `max(physical - reserved, 0)`, где `reserved` —
сумма размещений всех заказов на месте. Расчётный дефицит заказа в эту сумму
не входит.

- `409 WAREHOUSE_STOCK_RESERVED` — физического количества достаточно, но
  запрошено больше свободного. Ответ содержит `physical`, `reserved`, `free` и
  `requested`.
- `409 WAREHOUSE_RESERVATION_STOCK_MISMATCH` — физический остаток не покрывает
  размещения. Списание и перемещение отклоняются. Приход допустим и при
  существующей недостаче. Он увеличивает физический остаток без изменения
  размещений и расчётного дефицита.
- `400 WAREHOUSE_STOCK_ISOLATION_REQUIRED` — вызывающая транзакция использует
  другой уровень изоляции.

Внешний компонент вызывает `lockBalances(tx, itemId, locationIds)` для всех мест
операции до изменения количества. Блокировки удерживаются до завершения tx.
Нельзя сначала блокировать баланс, а затем брать блокировки Stock. Для нескольких
товаров полные наборы берутся по числовому itemId по возрастанию. Изменения Catalog
выполняются до Stock, без последующего повышения SHARE до UPDATE.

При расходовании или перемещении резерва `WarehouseReservationManager`
берёт блокировки Stock, затем блокировку логического резерва. Менеджер уменьшает
выбранное размещение до физической операции. При перемещении он добавляет
целевое размещение после увеличения целевого остатка. Все изменения и аудит
фиксируются вместе.

При документированной недостаче вызывающий сервис может заранее заблокировать
все затронутые остатки и явно вызвать `reduceCoverage()` для выбранных резервов.
Затем он вызывает обычный `issueStock()` в том же `tx`. Stock проверяет,
что после списания оставшиеся размещения обеспечены. Обычная отрицательная
корректировка использует только свободный остаток.

Stock проверяет существование позиции и мест, но не решает, допустима ли операция
для неактивных записей, и не активирует их. Политика активности и изменения
номенклатуры принадлежат вызывающему компоненту и Catalog.
`Catalog.create(payload, actorUserId, tx?)` поддерживает переданную транзакцию.
Остальные операции Catalog необходимо вызывать согласно их собственному контракту;
нельзя считать независимую транзакцию частью атомарной операции Stock.

Выдача и перемещение отвечают за документы, разрешения и защиту повторных
команд. `receiveStock` увеличивает количество; ожидающий документ прихода
и транспорт 1С реализуются вызывающими компонентами.

Каждое изменение количества записывается в общий аудит с `module=WAREHOUSE`,
`entityType=warehouse_balance`, строковым `entityStringId` и пользователем операции
в том же `tx`. Новая строка — `CREATE`, существующая — `UPDATE`. Для перемещения
записываются оба остатка; бизнес-документ и связь между его действиями принадлежат
вызывающему компоненту. Ошибка аудита должна откатить общую транзакцию.

```typescript
await prisma.$transaction(async (tx) => {
  const context = { tx, actorUserId };
  await stock.lockBalances(tx, itemId, [fromLocationId, toLocationId]);
  // Проверить разрешения и документ в этом tx.
  const balances = await stock.moveStock(
    context,
    itemId,
    fromLocationId,
    toLocationId,
    '8.125',
  );
  // Сохранить бизнес-документ и его аудит в этом tx.
  return balances;
});
```
