# Склад: Stock

Обязательная принадлежность выдач и листов складу, warehouseId-фильтры и состав DTO описаны в [контракте границ складов](../storage-structure/WAREHOUSE-BOUNDARIES.md).

`WarehouseStockService` хранит и изменяет физическое количество номенклатуры
по местам хранения. Сервис экспортируется из `WarehouseModule` и подключается
вместе с пакетом `warehouse`. HTTP API предоставляет только чтение; права операций
изменения остатков проверяет вызывающий бизнес-компонент.

## HTTP API

Все маршруты требуют сессию и `warehouse.stock.read` (admin/storekeeper).
При выключенном `warehouse` маршруты отсутствуют.

- `GET /api/warehouse/stock` — `{items,total,page,limit}` с фильтрами ниже.
- `GET /api/warehouse/stock/items/:itemId/total?warehouseId=...` — `{itemId,quantity}`.
  Необязательный query-параметр `warehouseId` ограничивает сумму местами выбранного склада;
  без него считается сумма по всем складам. Неактивные места также учитываются.
  Формат ответа не меняется: `itemId` и `quantity` — строки, `warehouseId` в ответ не добавляется.
  Для существующей номенклатуры без подходящих остатков — `"0"`,
  для отсутствующей — 404 `WAREHOUSE_ITEM_NOT_FOUND`.
- `GET /api/warehouse/stock/items/:itemId/locations/:locationId` — `{balance}`;
  при отсутствии записи `{balance:null}`, сохранённый нулевой остаток возвращается
  полноценным объектом с `quantity:"0"`.

ID строго канонические положительные decimal bigint strings: ведущие нули,
знаки и пробелы запрещены (400 `WAREHOUSE_STOCK_ID_INVALID`).
HTTP query преобразуется отдельно через `parseStockHttpQuery`: `page/limit` —
целые строки, `itemActive/locationActive` — строго `true|false`, количества —
десятичные строки. `itemIds/locationIds` принимают повторённые параметры или
один список через запятую. Неизвестные, некорректные и конфликтующие фильтры
отклоняются с 400. По умолчанию выдаются положительные остатки без фильтра активности.
Это физические остатки; доступность с учётом резервов предоставляет Issues.
POST/PATCH/DELETE остатков не предоставляются; чтение не аудируется.

## Контракт

- `getBalances(filters?)` возвращает `{ items, total, page, limit }`.
- `getBalance(itemId, locationId)` возвращает остаток или `null`. Отсутствующая
  запись не подменяется объектом с нулевым количеством.
- `getItemTotal(itemId, warehouseId?, tx?)` возвращает сумму строкой: по всем складам
  или по выбранному `warehouseId`. Для фильтра без транзакции передайте
  `getItemTotal(itemId, warehouseId)`. Для существующей номенклатуры
  без подходящих остатков — `"0"`, для отсутствующей — `WAREHOUSE_ITEM_NOT_FOUND`.
- `receiveStock(context, itemId, locationId, quantity)` увеличивает остаток,
  создавая запись при необходимости; возвращает обновлённый остаток.
- `issueStock(context, itemId, locationId, quantity)` уменьшает существующий
  остаток; возвращает обновлённый остаток.
- `moveStock(context, itemId, fromLocationId, toLocationId, quantity)` возвращает
  `{ from, to }`. Уменьшение и увеличение проходят в одной транзакции.

В `context` обязательны `tx: Prisma.TransactionClient` и `actorUserId: string`.
Методы изменения не открывают и не фиксируют собственных транзакций.
Ошибка должна выйти из callback транзакции: её нельзя перехватить и затем
зафиксировать частично выполненную операцию. Повтор всего документа и обработка
конфликтов транзакций выполняются вызывающим компонентом.

Все ID принимаются и возвращаются десятичными строками PostgreSQL bigint,
без преобразования в JS number. В DTO остатка есть `id`, `itemId`, `locationId`,
`quantity`, `item` (артикул, название, единица, активность) и `location`
(id/code/name/isActive/warehouseId/warehouse). Вложенный `location.warehouse`
содержит `id`, `code`, `name`, `isActive`; используется общий `locationWithWarehouseDto`.
Все ID вложенных объектов, включая `warehouseId` и `warehouse.id`, также строковые.

Количество принимается строкой или `Prisma.Decimal`, возвращается строкой.
JS number не принимается. Количество операции строго положительно, до трёх
знаков после запятой, максимум `99999999999.999`. Лишняя точность отклоняется,
а не округляется. Итог отдельного остатка ограничен тем же максимумом;
сумма по нескольким местам может его превышать. Все количества выражены
в базовой единице номенклатуры, конвертаций нет.

## Чтение и фильтры

`BalanceFilters` поддерживает:

- `warehouseId`: каноническая положительная bigint-строка; ограничивает остатки
  местами выбранного склада. Без фильтра возвращаются остатки всех складов.
  Совмещается с остальными фильтрами через AND.

- `itemId` либо `itemIds`, `locationId` либо `locationIds`. Одиночный и множественный
  фильтры одной сущности одновременно запрещены. Массивы содержат 1–1000 ID,
  дубликаты нормализуются; разные фильтры объединяются через AND.
- `quantityState`: `POSITIVE` (по умолчанию, `> 0`), `ZERO` (`= 0`), `ALL`.
- `minQuantity`, `maxQuantity`: включительные границы, допускают ноль,
  применяются вместе с `quantityState`; минимум не может превышать максимум.
- `itemActive`, `locationActive`: boolean; без них активность не фильтруется.
- `sortBy`: `item` (артикул, по умолчанию), `location` (код места), `quantity`.
- `sortOrder`: `asc` (по умолчанию) или `desc`; дополнительный ключ — ID остатка
  по возрастанию, в том числе при одинаковых артикулах, местах или количествах.
- `page`: положительное целое, по умолчанию 1; `limit`: 1–100, по умолчанию 50.
  Смещение ограничено 2147483647. Неизвестные поля отклоняются.

Это внутренний TypeScript-контракт: boolean и параметры страницы передаются
типизированными значениями, количества — строкой или Decimal.
HTTP-контроллер отдельно разбирает строковые query-параметры через
`parseStockHttpQuery` перед передачей фильтров во внутренний контракт
`parseBalanceFilters`.

Без переданной транзакции список с количеством записей и сумма с проверкой
существования номенклатуры читаются в `RepeatableRead`. Методы чтения принимают
необязательный `tx`: `getBalances(filters?, tx?)`, `getBalance(itemId, locationId, tx?)`,
`getItemTotal(itemId, warehouseId?, tx?)`. Тогда используется снимок и уровень
изоляции вызывающей транзакции, в том числе её незавершённые изменения.

## Запись, блокировки и границы ответственности

Пара `(item_id, storage_location_id)` уникальна в БД. При достижении нуля строка
сохраняется. Stock не удаляет остатки и не принимает отрицательные количества.
Уменьшать или увеличивать физическое количество следует только через Stock.

Порядок блокировок для одной номенклатуры:

1. `warehouse_items FOR SHARE` — согласование с `FOR UPDATE` в Catalog,
   запрещающее смену единицы одновременно с созданием первого остатка.
2. Места хранения `FOR SHARE` по числовому ID по возрастанию.
3. Для каждой пары в том же порядке: транзакционная advisory-блокировка
   `hashtextextended('warehouse:stock:<itemId>:<locationId>', 0)`, затем
   существующий остаток `FOR UPDATE`. Advisory-блокировка защищает и ещё
   отсутствующую строку, которую невозможно заблокировать через `FOR UPDATE`.

Проверки достаточности и переполнения выполняются до записи количества.
Stock не задаёт уровень изоляции переданной транзакции. Для обычных складских
операций рекомендуемый уровень вызывающей транзакции — `ReadCommitted`.
При использовании более строгой изоляции возможны конфликты сериализации;
вызывающий компонент при необходимости повторяет всю транзакцию целиком,
а не отдельный вызов Stock.

Внешний компонент, проверяющий резервы, должен сначала вызвать
`lockBalances(tx, itemId, locationIds)` для **всех** мест операции, затем прочитать
и изменить резервы и вызвать Stock в том же `tx`. Блокировки удерживаются до
завершения транзакции. Нельзя сначала блокировать резерв/остаток, а затем брать
блокировки Stock. Для документов с несколькими позициями нужно заранее брать
полные наборы блокировок по числовому `itemId` по возрастанию, не добавляя
позднее пары в обратном порядке. Изменения Catalog, если они нужны документу,
также выполняются до блокировок Stock, без последующего повышения SHARE до UPDATE.

Stock проверяет существование позиции и мест, но не решает, допустима ли операция
для неактивных записей, и не активирует их. Подтверждённый приход из 1С должен
выполнять необходимую активацию через Catalog на уровне интеграции/прихода.
Совместное использование потребует поддержки переданной транзакции в Catalog;
нынешний Catalog открывает собственные транзакции.

Stock не проверяет и не изменяет резервы. Выдача и перемещение отвечают
за доступное количество, правила расходования резервов и существующий дефицит,
документы, разрешения и защиту от повторной обработки. `receiveStock` — увеличение
количества, а не документ прихода и не готовая интеграция с 1С.
Административная корректировка может выявить дефицит `MAX(reserved - physical, 0)`:
Stock допускает это состояние, резервы проектов сохраняются.

Каждое изменение количества записывается в общий аудит с `module=WAREHOUSE`,
`entityType=warehouse_balance`, строковым `entityStringId` и пользователем операции
в том же `tx`. Новая строка — `CREATE`, существующая — `UPDATE`. Для перемещения
записываются оба остатка; бизнес-документ и связь между его действиями принадлежат
вызывающему компоненту. Ошибка аудита должна откатить общую транзакцию.

```typescript
await prisma.$transaction(async (tx) => {
  const context = { tx, actorUserId };
  await stock.lockBalances(tx, itemId, [fromLocationId, toLocationId]);
  // Проверить разрешения, документ и резервы; изменить резервы в этом tx.
  const balances = await stock.moveStock(
    context,
    itemId,
    fromLocationId,
    toLocationId,
    '8.125',
  );
  // Сохранить бизнес-документ и его аудит в этом tx.
  return balances;
});
```

## Ошибки

Ошибки содержат `{ code, message, details? }`. ID и количества в `details` строковые.

- `400 WAREHOUSE_STOCK_ID_INVALID`: неверный ID.
- `400 WAREHOUSE_STOCK_QUANTITY_INVALID`: неверное количество.
- `400 WAREHOUSE_STOCK_FILTER_INVALID`: неверные фильтры или пагинация.
- `400 WAREHOUSE_STOCK_SAME_LOCATION`: одинаковые места перемещения.
- `400 WAREHOUSE_STOCK_TRANSACTION_REQUIRED`: не передан транзакционный клиент.
- `400 WAREHOUSE_STOCK_ACTOR_REQUIRED`: не указан пользователь аудита.
- `404 WAREHOUSE_ITEM_NOT_FOUND`, `WAREHOUSE_LOCATION_NOT_FOUND`,
  `WAREHOUSE_BALANCE_NOT_FOUND`: отсутствует нужная запись.
- `409 WAREHOUSE_STOCK_INSUFFICIENT`: физически не хватает количества;
  `details` содержит `itemId`, `locationId`, `requested`, `available`.
- `409 WAREHOUSE_STOCK_QUANTITY_OVERFLOW`: превышен максимум отдельного остатка.

Ошибки инфраструктуры и конфликтов транзакций не маскируются под бизнес-ошибки.
