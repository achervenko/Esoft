# Резервы проектов

Обязательная принадлежность выдач и листов складу, warehouseId-фильтры и состав DTO описаны в [контракте границ складов](../storage-structure/WAREHOUSE-BOUNDARIES.md).

Один `WarehouseProjectReservation` связывает конкретный `WarehouseBalance`
(номенклатура + место) с `projectId` и положительным количеством.
`quantity` — потребность проекта; `borrowedQuantity` — не восстановленная часть заимствований. Обеспеченный резерв равен `quantity - borrowedQuantity`. Изменения схемы включены в исходный warehouse-пакет (модуль ещё не был в production).

## API

Префикс `/api/warehouse/reservations`. Все маршруты требуют сессию.
Обычные CRUD-маршруты (`GET /`, `POST /`, `PATCH /:id`, `DELETE /:id`) требуют
`warehouse.reservations.manage` (admin/storekeeper). Административные маршруты
`POST /documents` и `POST /:id/operations` требуют отдельного права
`warehouse.reservations.admin` (только admin).
При выключенном warehouse контроллер не подключается. `warehouse.reservations.override` остаётся отдельным
правом только admin и используется Issues, а не обычным управлением резервами.

- `GET /` — список `{items,total,page,limit}`. Фильтры `warehouseId`, `balanceId`, `projectId`,
  `itemId`, `locationId` объединяются через AND. `page=1`, `limit=50`, максимум 100.
  Стабильная сортировка id ASC, список и total читаются одним RepeatableRead-снимком.
- `POST /` — `{balanceId,projectId,quantity}`. Создаёт резерв, возвращает DTO.
  Существующая пара balance/project даёт 409 `WAREHOUSE_RESERVATION_EXISTS`.
- `PATCH /:id` — только `{quantity}`. Переназначение balance/project запрещено.
- `DELETE /:id` — снимает текущий резерв, возвращает `{released:true,id}`.
  Повторное снятие отсутствующего резерва даёт 404 `WAREHOUSE_RESERVATION_NOT_FOUND`.

DTO содержит `id`, `balanceId`, `projectId`, `quantity`, `item`
(id/article/name/unit/isActive), `location` (id/name/isActive/warehouseId/warehouse), `project`
(id/projectNumber/name/isActive). Вложенный `location.warehouse` содержит
`id`, `name`, `isActive`; место сериализуется общим `locationWithWarehouseDto`.
Фильтр `warehouseId` применяется через место остатка; без него возвращаются резервы всех складов.
ID — канонические bigint decimal strings,
количества — decimal strings до трёх знаков, максимум `99999999999.999`.
Ноль запрещён: для полного освобождения используется DELETE.
Неизвестные поля и некорректные значения отклоняются с 400.

## Проверки и конкурентность

Создание и увеличение требуют активных проекта, номенклатуры и места.
Количество не может превышать `max(physical - SUM(other reservations), 0)`;
при создании остальные резервы — все существующие. Нарушение даёт 409
`WAREHOUSE_RESERVATION_INSUFFICIENT` с physical/maximum/requested в details.
Неактивные или отсутствующий проект — 409 `WAREHOUSE_RESERVATION_UNAVAILABLE`;
отсутствующий balance — 404 `WAREHOUSE_BALANCE_NOT_FOUND`.

Снижение количества и снятие допускаются при дефиците и неактивных связанных
объектах, чтобы можно было освободить ранее созданный резерв.
PATCH тем же количеством успешен и не создаёт аудит.

Мутации выполняются в одной ReadCommitted-транзакции:

1. Пользователь под FOR SHARE: существование, banned и актуальное permission.
2. Проект под FOR SHARE — тот же порядок, что в Issues.
3. Чтение неизменяемых ключей balance, затем Stock.lockBalances.
4. Существующий WarehouseReservationsService.getLocked: резервы FOR UPDATE.
5. Повторное чтение состояния, проверка количества, запись резерва и аудита.

Первое чтение резерва для PATCH/DELETE не блокирует его: блокировки резервов
берутся только после Stock. Если Issues успел полностью израсходовать резерв,
повторная проверка возвращает 404. Параллельные POST/PATCH и выдачи сериализуются
на том же balance, включая защиту создания нового резерва.

ReservationsApiService — HTTP-сценарии, список и оркестрация транзакции;
существующий WarehouseReservationsService остаётся общим механизмом блокировки
и расходования резервов для API и Issues. Отдельного протокола блокировок нет.

Изменения пишутся через AuditLogService в WAREHOUSE,
entityType `warehouse_project_reservation`, entityStringId — ID резерва.
Снимки до/после содержат balanceId/projectId/quantity; снятие — DELETE.
Ошибка аудита откатывает всю мутацию. Физический остаток API не меняет.

warehouse_projects используется как текущий справочник-заглушка. CRUD проектов,
импорт 1С, сроки и статусы резервов, история отдельной таблицей и автоматическое
распределение по местам не входят в этот API.

## Административное управление резервом

В интерфейсе остатков администратор открывает «Управлять резервом» у конкретного проекта.
Новое право `warehouse.reservations.admin` выдано только admin; кладовщику действия недоступны.

- **Снять резерв**: частично или полностью уменьшить потребность, без изменения физического остатка. Сначала списывается необеспеченная часть заимствования. Например quantity=10, borrowed=3; снятие 2 даёт quantity=8, borrowed=1.
- **Заимствовать из резерва**: забрать обеспеченный товар на другие нужды. Физический остаток уменьшается, quantity сохраняется, borrowedQuantity увеличивается. Проект-получатель не требуется. Заимствование не является обычным перемещением: при перемещении резерв сохраняется за товаром.
- **Восстановить резерв**: закрепить уже поступивший свободный товар вместо заимствованного. Физический остаток и quantity не меняются, borrowedQuantity уменьшается. Новое поступление само по себе заимствование не закрывает.

Комментарий обязателен для всех трёх действий; для снятия резерва документ обязателен, для заимствования и восстановления — необязателен (PDF/JPEG/PNG/WebP).
POST `/api/warehouse/reservations/documents` загружает временный документ. POST `/:id/operations` принимает:

```json
{
  "action": "BORROW",
  "quantity": "3",
  "expectedQuantity": "10",
  "expectedBorrowedQuantity": "0",
  "comment": "Собственные нужды",
  "attachments": [],
  "requestKey": "11111111-1111-4111-8111-111111111111"
}
```

`action`: RELEASE/BORROW/RESTORE. Количества проверяются под блокировкой Stock и резервов; ожидаемые значения защищают от устаревшей формы. Проект и пользователь блокируются в том же порядке, что в выдачах/перемещениях. Повтор сохраняет исходный результат в `warehouse_reservation_operations` даже после полного снятия резерва; другое содержимое с тем же ключом даёт 409. Сохранение резервов, физического остатка, вложений и аудита атомарно.
Форма сохраняет неподтверждённый запрос в sessionStorage и восстанавливает его при возвращении на страницу остатков. Повтор под другим пользователем блокируется.

Распределение показывает нехватку и заимствованное количество. Свободный остаток считается после вычета обеспеченной части резервов; перемещать/выдавать заимствованное количество повторно нельзя. При физическом дефиците остальных резервов максимальное перемещение ограничивается консервативно, чтобы не забирать товар соседних проектов. Консолидация блокируется при дефиците физического обеспечения; заимствованная потребность остаётся на исходном месте при переносе обеспеченного товара.

### Что требуется для прихода под проект

Связь `Заказ 1С → проект ESoft` отсутствует. Ручной приход также пока не сохраняет назначение проекта. Справочник warehouse_projects остаётся заглушкой только для чтения. Поэтому нельзя автоматически считать приход с заказом 1С возвратом заимствования или новой потребностью.

Согласованный следующий этап: при размещении под известный проект показывать два количества — **восстановить резерв** и **дополнительно зарезервировать**; по умолчанию предлагать восстановление в пределах нехватки, остальное — новую потребность. Пользователь подтверждает распределение; без нехватки весь проектный приход увеличивает резерв. Размещение и выбранное изменение резерва должны сохраняться в одной транзакции с одним безопасным повтором.

До появления этой связи восстановление выполняется явно из свободного остатка в том же месте. Если новый товар положили в другое место, сначала переместить свободный товар к месту резерва. Нельзя автоматически связывать заказ и проект по совпадению номера или названия.
Создание новых проектов, выбор проекта для ручного прихода и экран автоматического распределения прихода в этой итерации не реализованы. Просмотр истории операций и скачивание вложений через UI также остаются отдельной задачей; документы уже сохранены за операцией и неизменяемы.

Обычные DELETE и уменьшение количества через PATCH запрещены при ненулевом borrowedQuantity, в том числе для администратора. Используйте административную операцию RELEASE с комментарием и документом.
