# Reservations

Модуль управляет потребностью заказа и её обеспеченными размещениями. Заказ — канонический `CustomerOrder` из Orders; физические остатки принадлежат Stock. Все количества передаются строковыми decimal с точностью до трёх знаков, UUID и bigint не преобразуются через JavaScript number.

## Хранение и инварианты

- `WarehouseReservation`: UUID, `orderId`, `itemId`, `quantity`. Пара заказ + товар уникальна; UUID сохраняется при полном снятии и последующем увеличении.
- `WarehouseReservationAllocation`: UUID, `reservationId`, `locationId`, `quantity`. Пара резерв + место уникальна; пустые размещения удаляются.
- Количества неотрицательны. Сумма размещений не превышает потребность; `deficitQuantity = quantity - SUM(allocations.quantity)`.
- Создание и восстановление размещений ограничены свободным физическим остатком соответствующего товара и места. Логический дефицит и физическое расхождение Stock — разные показатели.
- Ссылки на заказ, товар, резерв и место защищены FK с удалением RESTRICT.

## Внутренний менеджер

`WarehouseReservationManager` — публичный транзакционный фасад. Контекст содержит `tx`, необязательные `actorUserId`, `comment` и метаданные прихода `receipt`; для физического перемещения и расходования автор обязателен.

| Метод               | Результат                                                                         |
| ------------------- | --------------------------------------------------------------------------------- |
| `reserve()`         | Создаёт или увеличивает потребность и размещение на выбранном месте               |
| `decrease()`        | Снимает явно указанные размещения и/или необеспеченную потребность                |
| `reduceCoverage()`  | Уменьшает размещение, сохраняя потребность и увеличивая дефицит                   |
| `restoreCoverage()` | Восстанавливает размещение из свободного остатка, не меняя потребность            |
| `move()`            | Атомарно перемещает размещение и физический товар, сохраняя потребность и дефицит |
| `consume()`         | Атомарно уменьшает размещение, потребность и физический остаток                   |

Реализации разделены по операциям. Менеджер не открывает транзакцию и не заменяет прикладную проверку прав. Вызывающий сервис проверяет права, ограничения документа и активность справочников. Исключение менеджера должно выйти из транзакции, чтобы откатить все изменения.

## Транзакции и конкурентный доступ

Используется ReadCommitted. Сначала берутся общие блокировки Stock по товару и местам в стабильном порядке, затем логическая advisory-блокировка пары заказ + товар. Состояние резерва и размещений перечитывается после блокировки. Пакетные операции предварительно блокируют все затронутые Stock-пары, затем резервы в согласованном порядке.

Изменение резерва и AuditLog атомарны. Физические изменения выполняются через Stock в той же транзакции. Создание и восстановление не расходуют чужое обеспеченное количество; перемещение и расходование проверяют физическое покрытие. Полный протокол физических операций описан в [STOCK-TRANSACTIONS.md](../stock/STOCK-TRANSACTIONS.md).

## HTTP API

Корень: `/api/warehouse/reservations`. Требуется сессия ESoft; сервисы повторно проверяют актуальные права внутри транзакции.

| Метод и путь                                         | Permission                                                     |
| ---------------------------------------------------- | -------------------------------------------------------------- |
| GET `/`, `/:id`, `/:id/history`                      | `warehouse.reservations.read`                                  |
| GET `/orders/:orderId/summary`                       | `warehouse.reservations.read`                                  |
| GET `/orders/:orderId`                               | `warehouse.reservations.manage`                                |
| POST `/`, `/:id/decrease`                            | `warehouse.reservations.manage`                                |
| POST `/:id/coverage/reduce`, `/:id/coverage/restore` | `warehouse.reservations.coverage.manage`                       |
| POST `/:id/move`                                     | `warehouse.reservations.manage` и `warehouse.transfers.manage` |

DTO, фильтры и строгая валидация находятся в `reservations.dto.ts` и `reservations.validation.ts`. Чтение списка и истории использует один RepeatableRead-снимок с пагинацией. История читается из общего AuditLog по `entityType=warehouse_reservation` и UUID резерва. Закрытый заказ допускается; DTO возвращает предупреждение `ORDER_CLOSED`.

`GET /` принимает `search` (до 255 символов) для поиска по артикулу и названию номенклатуры без учёта регистра. Поиск буквальный: `%` и `_` не являются шаблонами. Условие сочетается с `orderId`, `quantityState`, `deficit`, `covered` и `itemId`, применяется до подсчёта `total` и пагинации. Пустая страница сохраняет полный `total` совпадений; распределения входят в DTO списка и не требуют отдельных запросов.

Перемещение через HTTP создаёт существующий документ Transfers и сохраняет результат с `requestKey`; replay возвращает исторический результат без повторного перемещения. Внутренний менеджер идемпотентность сам не реализует: ключами и документом управляет вызывающий прикладной сервис.

## Список заказов с резервами

`GET /api/warehouse/reservations/orders/:orderId/summary` возвращает `{order,positionsCount,deficitPositionsCount}` по праву `warehouse.reservations.read`. Счётчики охватывают положительные резервы заказа; дефицит определяется сравнением полной потребности с суммой распределений. Заказ и счётчики читаются в одной RepeatableRead-транзакции. Заказ без резервов возвращает нулевые счётчики, отсутствующий заказ — `404 WAREHOUSE_RESERVATION_ORDER_NOT_FOUND`.

`GET /api/warehouse/reservations/orders` требует `warehouse.reservations.read`. Параметры: `search` (до 255 символов), `coverage=ALL|DEFICIT|COVERED`, `page` и `limit` (до 100). Без параметров возвращается первая страница из 50 заказов.

В выборке участвуют только резервы с `quantity > 0`. Заказ без положительных резервов, в том числе после полного снятия потребности, не включается. Закрытые заказы не исключаются; их статус и `ORDER_CLOSED` возвращаются обычным DTO заказа.

Ответ: `{items:[{order,positionsCount,deficitPositionsCount}],total,page,limit}`. Поиск нечувствителен к регистру и проверяет номер/название заказа и артикул/название номенклатуры его положительных резервов. Символы `%` и `_` трактуются буквально. Поиск отбирает заказ, но не уменьшает его счётчики до совпавших товаров. Фильтр дефицита применяется к заказу целиком: DEFICIT означает хотя бы одну позицию с дефицитом, COVERED — отсутствие таких позиций.

Счётчики не суммируют количества разных единиц. Сортировка — номер заказа ASC, затем UUID ASC. SQL вычисляет статистику и `total` в одном запросе; пустая страница сохраняет полный `total`. Права и чтение выполняются в одной RepeatableRead-транзакции. Запрос реализован в `reservation-orders-query.ts`.

## Приход под заказ

`WarehouseReceiptOrderPlacementService` использует внутренний `CustomerOrder.id`, переданный в ручной строке прихода. Создание ожидающего документа не меняет резерв и Stock. При фактическом размещении весь новый материал закрепляется на месте поступления:

- Без дефицита вызывается `reserve()` на полное количество.
- При дефиците требуется явное распределение `restoreQuantity + increaseQuantity = receivedQuantity`.
- Восстановление вызывает `restoreCoverage()`, увеличение — `reserve()`. Нулевые составляющие пропускаются.

Распределение проверяется по текущему дефициту после Stock- и Reservation-блокировок. `receiveStock()`, операции менеджера, размещение документа, ключ запроса и аудит фиксируются одной транзакцией. Полномочие `warehouse.receipts.place` даёт только это ограниченное следствие размещения, а не произвольное управление резервами.

AuditLog резервирования дополнен необязательными метаданными `receipt: {receiptId,receiptLineId,restoredQuantity,increasedQuantity}`. Прежний формат остальных операций сохранён. Исторический результат прихода с UUID резерва и снимком заказа хранится в размещении. Подробный HTTP-контракт — в [README Receipts](../receipts/README.md#размещение-под-заказ).
