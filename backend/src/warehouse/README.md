# Склад: Catalog

Catalog ведёт локальную номенклатуру по текущей модели `WarehouseItem`.
Физическое количество изменяет отдельный внутренний компонент [Stock](stock/README.md).
Административные списания и излишки оформляет [StockAdjustments](adjustments/README.md).
Задания на выдачу и их исполнение описывает [IssueSheets](issue-sheets/README.md).
Интеграция с 1С, внешние идентификаторы, владение полями и отдельный справочник
единиц в компонент не входят. `unit` — строка до 50 символов.

## Подключение и доступ

`WarehouseModule` подключается только при наличии `warehouse` в
`database-packages.json`. Иначе код модуля не загружается и маршруты отсутствуют.
При включении нужны установленные миграции склада и перезапуск backend.
Зависимости — Prisma и общий аудит ядра, без оборудования и СИЗ.
Подготовка БД: [WAREHOUSE-DATABASE.md](../../../docs/WAREHOUSE-DATABASE.md).

Активная сессия обязательна. Чтение и изменение доступны при наличии активной
роли `admin` или `storekeeper` («Кладовщик»). Сами роли
`accounting_specialist` и `ppe_specialist` прав склада не предоставляют.
Назначение роли — административная операция.
Разрешение `warehouse.catalog.manage` единое: оно включает чтение, создание, изменение,
активацию и деактивацию номенклатуры. Отдельных прав на чтение и управление пока нет.

Глобальный `PermissionsGuard` требует явного `@RequirePermission(...)`
на каждом обработчике. Нет разрешения, оно неизвестно или права не подходят —
запрос запрещён, в том числе для администратора. Разрешение на классе
не наследуется обработчиками. Склад объявляет действия в
`warehouse.permissions.ts`, auth связывает их с ролями в `permission-policy.ts`.
Catalog требует `WAREHOUSE_PERMISSIONS.CATALOG_MANAGE`.
`engineer,storekeeper` объединяет права оборудования и склада;
проверок доступа по префиксу URL нет.
Новые endpoints Stock, резервов, выдач и административных действий автоматически
прав не получают; для них потребуется отдельная политика. Проверку разрешения
Catalog выполняет глобальный guard.

Сама роль кладовщика не получает административных прав Better Auth, доступа к оборудованию,
СИЗ или чужим профилям. Пока страницы склада нет, его стартовая страница —
собственный профиль. Этот компонент предоставляет backend API.

## API

- `GET /api/warehouse/items`: поиск и список.
- `GET /api/warehouse/items/:id`: карточка, включая неактивные позиции.
- `POST /api/warehouse/items`: создание активной позиции.
- `PATCH /api/warehouse/items/:id`: частичное изменение полей.
- `PATCH /api/warehouse/items/:id/status`: установка `isActive`.

Физического удаления через API нет.

Создание требует `article`, `name`, `unit`; `comment` необязателен.
Артикул — до 100 символов, наименование — до 255, единица — до 50.
Строки обрезаются по краям. Пустой комментарий сохраняется как `null`.
Пустые обязательные поля, NUL и неизвестные поля отклоняются.
Уникальность артикула регистрозависимая, согласно текущему индексу БД.

```json
{
  "article": "BRG-685",
  "name": "Подшипник 685",
  "unit": "шт",
  "comment": "Для редуктора"
}
```

PATCH изменяет только переданные `article`, `name`, `unit` и `comment`.
Другие поля в payload запрещены. Пустой PATCH отклоняется.
Для изменения активности используется отдельный endpoint с `{ "isActive": false }`
или `{ "isActive": true }`.

Ответ карточки содержит `id`, `article`, `name`, `unit`, `comment`, `isActive`.
ID — положительная десятичная строка в пределах PostgreSQL bigint. Backend
преобразует её в `bigint` без промежуточного JavaScript `number`; JSON содержит строку.

Параметры списка:

- `q`: до 255 символов, поиск без учёта регистра по артикулу, названию и комментарию;
  `%`, `_` и `\` рассматриваются как обычные символы и не работают как шаблоны поиска.
- `isActive`: строка `true` или `false`; без фильтра возвращаются оба состояния.
- `limit`: от 1 до 100, по умолчанию 50.
- `offset`: от 0 до 2147483647, по умолчанию 0.

Ответ — `{ items, total, limit, offset }`. Сортировка — артикул и ID по возрастанию;
список и количество читаются в одном снимке транзакции.
Для подбора в новые обычные складские операции нужно запрашивать `isActive=true`.

## Изменения и аудит

Записи изменяются с блокировкой строки номенклатуры `FOR UPDATE`.
Смена единицы запрещена, если на позицию ссылается хотя бы один остаток
(в том числе нулевой) или строка листа. Название и комментарий менять можно.
Деактивация сохраняет остатки, резервы и историю; повторная активация разрешена.
Stock согласует блокировки с Catalog. Правила использования неактивной номенклатуры
проверяют вызывающие Stock компоненты; сам Stock активность не меняет и движение
только из-за неё не запрещает.

Создание, изменение и статус записываются в общий журнал с модулем `WAREHOUSE`
и `entityType=warehouse_item`. Складской ID хранится в `entityStringId`,
а `entityId` остаётся `null`. Изменение и аудит атомарны: ошибка аудита откатывает
операцию. Передача прежних значений не создаёт ложных строк аудита.

Основные ошибки: `WAREHOUSE_ITEM_NOT_FOUND` (404), `WAREHOUSE_ARTICLE_EXISTS` (409),
`WAREHOUSE_UNIT_IN_USE` (409), `INVALID_WAREHOUSE_ID`, `INVALID_CATALOG_FIELD`,
`INVALID_CATALOG_STATUS`, `INVALID_CATALOG_QUERY`, `UNKNOWN_FIELDS`, `EMPTY_PAYLOAD`
и `INVALID_PAYLOAD` (400). Ошибки инфраструктуры не маскируются под конфликт артикула.
Отказ по правам возвращает `FORBIDDEN` (403), отсутствие допустимого разрешения
обработчика — `PERMISSION_NOT_DECLARED` (403).

## Проверка

```powershell
npm run db:generate
npm run build:backend
npm run test --workspace backend -- --runInBand warehouse optional-warehouse
$env:ESOFT_MODULAR_MIGRATION_TEST = '1'
try {
  node --test tests/scripts/infrastructure/prisma/warehouse-catalog.real.integration.test.mjs
} finally {
  Remove-Item Env:ESOFT_MODULAR_MIGRATION_TEST
}
```

Реальная проверка использует временный PostgreSQL с пакетами `core` и `warehouse`,
не подключаясь к рабочей БД. Требования к PostgreSQL описаны в документации пакета.
