# Перемещения

Компонент Transfers оформляет немедленное перемещение одной номенклатуры между
двумя местами: внутри склада или между складами. Этапа «в пути» и подтверждения
принимающей стороны пока нет. Разные товары проводятся отдельными операциями.

## Архитектура

- `WarehouseTransfersService` сохраняет публичные команды и методы чтения. Командная часть управляет транзакцией, проверкой прав, ключом повтора, записью документа и AuditLog.
- `transfers-execution.ts` проверяет резерв, последовательно блокирует склады и балансы, проверяет номенклатуру и места, исполняет перемещение и формирует снимок. Функции получают текущий `tx` и не создают транзакции.
- `transfers-distribution.ts` исполняет явное распределение между свободной частью и резервами; вызывается из исполнения перемещения.
- `WarehouseTransfersQueryService` выполняет `findOne()` и `list()`. Основной сервис делегирует чтение без изменения маршрутов и DTO. Список и его `total` читаются в одной RepeatableRead-транзакции.
- `transfers.dto.ts` содержит единое преобразование сохранённого документа для команд и запросов.

## API

- POST /api/warehouse/transfers — проведение, HTTP 201 и при первом запросе, и при повторе.
- `POST /api/warehouse/transfers/consolidate` собирает товар с нескольких мест текущего склада в одно место, в том числе на другом складе. Команда содержит `requestKey`, `itemId`, `fromWarehouseId`, `toLocationId` и до 500 строк `moves`. Каждая строка содержит `fromLocationId`, `quantity` и при необходимости `distribution` в том же формате, что и одиночное перемещение. Строка без распределения переносит свободный остаток. При наличии резервов требуется `warehouse.reservations.manage`. Место назначения не включается в исходные строки.
  Все строки выполняются в одной транзакции. Ошибка любой строки откатывает весь пакет. Ответ содержит `{ids}` проведённых перемещений. Повтор возвращает прежние идентификаторы независимо от порядка строк и резервов. Изменение количества или распределения с тем же ключом отклоняется. Связь группы хранится в `snapshot` первого перемещения.
- GET /api/warehouse/transfers — список: warehouseId, itemId, fromLocationId,
  toLocationId, page (1), limit (50, максимум 100). Ответ {items,total,page,limit}.
  warehouseId выбирает операции, где склад является исходным или целевым.
  Остальные фильтры объединяются через AND. Сортировка createdAt DESC, id DESC.
- GET /api/warehouse/transfers/:id — карточка.

Чтение требует warehouse.transfers.read, проведение — warehouse.transfers.manage.
Оба permission выданы admin/storekeeper. Текущие права и блокировка пользователя
проверяются в транзакции, включая повтор проведённого запроса.

Пример JSON:

```json
{
  "requestKey": "e650f09a-d037-43ba-9195-437241b14e0e",
  "itemId": "15",
  "fromLocationId": "8",
  "toLocationId": "9",
  "quantity": "3.125",
  "comment": "Переложили на соседнюю полку"
}
```

ID — канонические положительные bigint-строки, количество — положительная
десятичная строка с точностью до трёх знаков. requestKey — UUID, уникальный в
пределах пользователя; комментарий необязателен, trim/null, до 4000 символов.
Неизвестные поля отклоняются. Исходное и целевое места должны различаться.

## Правила и атомарность

Оба склада, места и номенклатура должны быть активными. Исходный остаток должен
существовать; целевой создаётся при необходимости. Нулевая исходная запись
сохраняется. Общая сумма по всем складам не меняется.

Stock под блокировкой рассчитывает свободное количество исходного места:
физический остаток за вычетом обеспеченных размещений резервов.
Одиночные и пакетные перемещения без `distribution` расходуют только свободный
остаток. При наличии `distribution` перемещаются указанные свободные и
зарезервированные количества с сохранением привязки резервов к заказам.
Все изменения выполняются атомарно.

Порядок блокировок: пользователь → ключ запроса → склады в порядке ID →
Stock для обоих мест в стабильном порядке. Обе стороны Stock.moveStock,
запись операции и аудит выполняются в одной ReadCommitted-транзакции.
Любая ошибка откатывает всё, включая новый баланс.

Повтор с тем же ключом и нормализованными данными возвращает прежнюю операцию
без нового движения и аудита; другие данные дают 409 WAREHOUSE_TRANSFER_REQUEST_CONFLICT.
Replay выполняется до проверки текущих справочников, но после проверки текущих прав.

## История и ошибки

Ответ содержит id, itemId, fromLocationId, toLocationId, quantity, comment,
createdByUserId, createdAt, requestKey и snapshot. ID и количества — строки.
Snapshot хранит item (id/article/name/unit), from/to (общие DTO места со складом)
и fromQuantityBefore/After, toQuantityBefore/After. Переименования справочников
не меняют карточку, список или replay старого перемещения. Активность в снимке
также отражает момент проведения. requestHash не публикуется.

- 400 WAREHOUSE_TRANSFER_INVALID — payload/query; формат ID/количества может
  возвращать соответствующие WAREHOUSE_STOCK_ID_INVALID/QUANTITY_INVALID.
- 403 FORBIDDEN — недостаточно прав или пользователь заблокирован.
- 404 WAREHOUSE_TRANSFER_NOT_FOUND — карточка не найдена.
- 404 WAREHOUSE_ITEM_NOT_FOUND / WAREHOUSE_LOCATION_NOT_FOUND / WAREHOUSE_BALANCE_NOT_FOUND.
- 409 WAREHOUSE_INACTIVE / WAREHOUSE_TRANSFER_INACTIVE_REFERENCE — неактивные справочники.
- 409 WAREHOUSE_STOCK_INSUFFICIENT — физического остатка недостаточно.
- 409 WAREHOUSE_STOCK_RESERVED — запрошено больше свободного количества.
- 409 WAREHOUSE_RESERVATION_STOCK_MISMATCH — физический остаток не покрывает размещения.

- 409 WAREHOUSE_STOCK_QUANTITY_OVERFLOW — превышение ёмкости целевого остатка.

## Перемещение размещения резерва

`POST /api/warehouse/reservations/:id/move` принимает `requestKey`,
`fromLocationId`, `toLocationId`, строковое `quantity` и необязательный
`comment` до 4000 символов. Требуются одновременно
`warehouse.reservations.manage` и `warehouse.transfers.manage`.
Разрешён перенос между активными складами и местами активной номенклатуры.

Прикладной сервис открывает транзакцию ReadCommitted и вызывает
`createInTransaction()` с контекстом конкретного резерва. В этом варианте
физическое движение выполняет `WarehouseReservationManager.move()`.
Transfers сохраняет документ и аудит документа в том же tx.

Порядок блокировок — пользователь, ключ запроса, склады по ID, Stock по ID мест,
логический резерв. Проверка текущих прав предшествует возврату сохранённого
результата. Повтор не зависит от переименований и активности справочников.

Область ключа общая с обычными перемещениями — пользователь и requestKey.
Хеш команды учитывает тип операции и UUID резерва. Изменение резерва, маршрута,
количества или комментария при прежнем ключе даёт
`409 WAREHOUSE_TRANSFER_REQUEST_CONFLICT`.

Снимок документа дополнен `reservationId`, снимком `order` и
`reservationResult` — результатом резервирования на момент переноса.
Ответ содержит `reservation` и стандартный DTO `transfer`, дополненный
`reservationId`. При повторе возвращается сохранённый результат операции.
Событие MOVE в истории резерва содержит комментарий. Документ связан с этой
историей через постоянный UUID резерва.

## Свободная и зарезервированная части одного перемещения

`POST /api/warehouse/transfers` принимает необязательный `distribution`:

```json
{
  "freeQuantity": "4",
  "reservations": [
    { "reservationId": "873e93da-fa3b-4d4e-b90f-fff6eb6731c3", "quantity": "4" }
  ]
}
```

Сумма должна совпадать с `quantity` основного запроса. Количества положительные, свободная часть может быть нулевой. До 1000 резервов; повтор UUID и несоответствие номенклатуры отклоняются. Резервы сортируются по UUID при нормализации, поэтому перестановка строк не меняет идентичность запроса. Команды без `distribution` сохраняют прежний контракт и хеш.

Если выбраны резервы, дополнительно проверяется `warehouse.reservations.manage`. После общих блокировок Transfers свободная часть проводится через Stock, а каждая выбранная часть — через существующее ядро перемещения Reservations. Все вызовы используют исходную транзакцию, без вложенных транзакций. Создаётся один документ Transfers на полное количество; его snapshot содержит состав и заказы. Общая потребность и сумма размещений каждого резерва сохраняются. Любая ошибка откатывает физические изменения, размещения, аудит и документ. Ключ повтора защищает весь состав.

Распределение по заказам для формы возвращается в `reservations` каждого места `GET /api/warehouse/stock-overview/items/:itemId/warehouses/:warehouseId` в согласованном снимке вместе с физическим, свободным и зарезервированным количеством.
