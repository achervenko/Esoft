# Приход: документы, размещения и интеграция

Документ (`WarehouseReceipt`) описывает ожидаемый товар. **Создание или импорт документа не меняет Stock.** Единственный источник движения в этом модуле — `WarehouseReceiptPlacement`, записываемый атомарно с `Stock.receiveStock` и аудитом.

## Границы ответственности

WarehouseReceiptsModule владеет документами, строками, размещениями, сопоставлением складов и связями между приходными документами. Внешние связи номенклатуры принадлежат Catalog. Он не делает HTTP-запросы и не запускает обработчик очереди. Транспорт 1С находится в отдельном [ReceiptIntegrationModule](../receipt-integration/README.md), который импортирует публичный API прихода; обратной зависимости нет. Чтение товара выполняется через lockItemsForOperation, создание — через WarehouseCatalogService.create, а чтение и подтверждение внешних связей — через WarehouseCatalogExternalLinksService. Все вызовы используют транзакцию вызывающего компонента; права и аудит создания/привязки товара проверяет Catalog. Прямых запросов к warehouse_items и warehouse_item_external_links в приходе нет. Физические остатки изменяет только Stock.

## Рабочие сценарии

Прикладные операции разделены на три внутренних сервиса:

- `WarehouseReceiptItemMappingService.mapItem()` — подтверждение связи номенклатуры через Catalog.
- `WarehouseReceiptReconciliationService.reconcile()` — связывание ручного прихода с документом 1С.
- `WarehouseReceiptConflictResolutionService.resolve()` — решение конфликта версии или отмены.

Контроллер получает эти сервисы напрямую. Они не экспортируются из компонента; публичный DI-контракт включает WarehouseReceiptsService, WarehouseReceiptImportService и ReceiptIntegrationWarehousesService для административной настройки складов до обмена. Внутренний `WarehouseReceiptOrderPlacementService` объединяет физическое поступление с резервированием через `WarehouseReservationManager`; модуль импортирует `WarehouseReservationsModule`.

1. 1С прислала документ: он сохраняется со строками и исходными значениями. Неизвестную номенклатуру пользователь может сопоставить в карточке прихода, затем разместить количество по местам. Склад должен быть административно сопоставлен до начала обмена: его сопоставление относится к настройке интеграции и не является рабочей операцией кладовщика. Карточка прихода не предлагает ручной выбор неизвестного склада.
2. Товар приехал раньше 1С: создаётся ручной документ, затем выполняются обычные размещения. После импорта пользователь явно сопоставляет строки полностью размещённого ручного документа со строками 1С. Связь учитывает уже сделанные размещения, но **не вызывает Stock**.
3. Частичный приход: сколько разместили, столько доступно в остатках. Неразмещённое количество не выдаётся.

Переподключение документа 1С к ручному приходу по номеру или артикулу автоматически не выполняется. Несколько ручных документов можно связать с одним документом 1С в пределах ожидаемого количества. Одна ручная строка целиком относится к одной строке 1С; если ручной приход ещё не завершён, сначала завершите его или дождитесь уточнения процесса. Ручная строка после связывания не размещается повторно.

## HTTP API пользователя

Для всех методов нужна сессия ESoft. BigInt ID и decimal передаются строками. Неизвестные поля отклоняются.

| Метод                                                       | Назначение                                     | Permission                                                  |
| ----------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------- |
| POST `/api/warehouse/receipts`                              | Ручной ожидающий документ                      | `warehouse.receipts.manage`                                 |
| GET `/api/warehouse/receipts`                               | Рабочий список / история                       | `warehouse.receipts.read`                                   |
| GET `/api/warehouse/receipts/:id`                           | Документ, строки, размещения, проблемы         | `warehouse.receipts.read`                                   |
| POST `/api/warehouse/receipts/:id/cancel`                   | Отмена ручного документа до первого размещения | `warehouse.receipts.manage`                                 |
| POST `/api/warehouse/receipts/:id/lines/:lineId/placements` | Разместить часть строки                        | `warehouse.receipts.place`                                  |
| POST `/api/warehouse/receipts/:id/lines/:lineId/item-link`  | Подтвердить связь номенклатуры                 | `warehouse.receipts.map` + `warehouse.catalog.links.manage` |
| POST `/api/warehouse/receipts/:id/reconcile`                | Связать фактический ручной приход с 1С         | `warehouse.receipts.map`                                    |
| POST `/api/warehouse/receipts/:id/resolve-conflict`         | Явное решение конфликта                        | `integrations.manage`                                       |

Read/manage/place/map назначены admin/storekeeper. Integration — только admin в текущем RBAC. Подтверждение внешней связи дополнительно требует `warehouse.catalog.links.manage`. Создание номенклатуры из строки дополнительно требует `warehouse.catalog.manage`; назначать разрешения сервисным пользователям автоматически модуль не будет.

### Ручной документ

```json
{
  "warehouseId": "1",
  "requestKey": "acbf4fd4-89c4-4f5d-b8f2-150665d3c680",
  "documentNumber": "Накладная 42",
  "documentDate": "2026-10-29",
  "comment": null,
  "newItems": [
    {
      "draftId": "acbf4fd4-89c4-4f5d-b8f2-150665d3c681",
      "item": {
        "article": "NEW-6204",
        "name": "Подшипник 6204",
        "unit": "шт"
      }
    }
  ],
  "lines": [
    {
      "itemId": "15",
      "quantity": "20.125",
      "orderId": "67cadf73-38a4-45d7-b9ac-c0eb95e39cb2"
    },
    { "draftId": "acbf4fd4-89c4-4f5d-b8f2-150665d3c681", "quantity": "3" },
    { "draftId": "acbf4fd4-89c4-4f5d-b8f2-150665d3c681", "quantity": "2" }
  ]
}
```

От 1 до 100 строк. Место хранения здесь не передаётся. Номер/дата/комментарий необязательны. Для существующей номенклатуры строка содержит `itemId`, для новой — `draftId` из массива `newItems`; одновременно указывать оба поля нельзя. `newItems` необязателен, содержит до 100 черновиков с уникальными UUID `draftId`. Данные `item` проверяются по правилам Catalog.

Необязательный `lines[].orderId` — UUID внутреннего `CustomerOrder.id`. Проверяется существование заказа; поиск по номеру, дате или внешнему ID не выполняется. Каждая строка независимо назначается заказу либо остаётся без него, включая строки с `draftId`. В строке сохраняются FK `orderId` и исторический `orderSnapshot` с номером, названием, статусом и предупреждениями. Закрытый заказ допускается с `ORDER_CLOSED`. Создание ожидающего документа не создаёт резерв; выбранный заказ участвует в hash запроса.

Одну новую позицию можно использовать в нескольких строках через одинаковый `draftId`. В примере создаётся один подшипник в каталоге и две отдельные строки прихода с количествами 3 и 2; существующая позиция 15 остаётся отдельной строкой. Разные товары с одинаковым артикулом автоматически не объединяются: занятый артикул даёт `409 WAREHOUSE_ARTICLE_EXISTS`.

В форме новая номенклатура хранится как черновик до отправки прихода. Закрытие формы ничего не создаёт. При сохранении Catalog создаёт используемые новые товары в той же транзакции, что приход и аудит. Дополнительно требуется `warehouse.catalog.manage`; для самого прихода — `warehouse.receipts.manage`. Ошибка любого шага откатывает товары, приход и аудит целиком. Создание документа не меняет физические остатки.

Ключ UUID (RFC variant, версии 1–8) ограничен автором. Повтор нормализованного запроса возвращает тот же документ без повторного создания товаров; изменение содержания — `409 WAREHOUSE_RECEIPT_REQUEST_CONFLICT`. При повторе после потери ответа сохраняются прежние `requestKey`, `draftId`, данные новых товаров и строки. Перестановка строк не меняет hash ручного запроса. POST создания и повтора возвращает 201. Документ не редактируется; неразмещённый ручной документ можно отменить и создать исправленный.

### Размещение

```json
{
  "requestKey": "12ef8e5a-8ac9-4f28-9c51-f65a6b8c5d18",
  "storageLocationId": "8",
  "quantity": "5.125"
}
```

Quantity > 0, numeric(14,3), JSON number запрещён. Проверяются документ, отсутствие отмены/конфликта, принадлежность строки документу, сопоставление, GOODS, совпадение единицы, активные товар/склад/место и принадлежность места складу. Превышение remaining запрещено.

Порядок блокировок: автор FOR SHARE → advisory actor+requestKey → документ FOR UPDATE → склад FOR SHARE → общие Stock locks → логическая блокировка резерва по заказу и номенклатуре, если строка назначена заказу. Запись размещения, изменение остатков, резерв, статус и аудит — одна транзакция ReadCommitted. Параллельные размещения одного документа сериализуются; stock-протокол защищает гонки с выдачей/перемещением/корректировкой. Вложенных транзакций нет.

Повтор ключа возвращает первоначальное размещение до проверки активности справочников; права автора перепроверяются. Другие параметры с тем же ключом — 409. Snapshot товара и места сохраняется в размещении и не меняется после переименования.

### Размещение под заказ

Для ручной строки с `orderId` новое физическое количество полностью резервируется на месте фактического размещения. При отсутствии дефицита вызывается `reserve()`; существующий резерв для пары заказ + товар сохраняет UUID. Без заказа поступление меняет только Stock и не восстанавливает чужие дефициты.

При существующем дефиците запрос размещения должен содержать решение пользователя:

```json
{
  "requestKey": "12ef8e5a-8ac9-4f28-9c51-f65a6b8c5d18",
  "storageLocationId": "8",
  "quantity": "20",
  "reservationAllocation": { "restoreQuantity": "7", "increaseQuantity": "13" }
}
```

`restoreQuantity` и `increaseQuantity` — строковые decimal, неотрицательные, точность до трёх знаков. Их сумма равна количеству **этого размещения**, восстановление не превышает текущего дефицита. Решение задаётся для каждого частичного размещения отдельно. Допустимы чистое восстановление, чистое увеличение и комбинация. Внутренние операции с нулевым количеством не вызываются. Распределение без заказа отклоняется с 400.

Без решения при дефиците возвращается `409 WAREHOUSE_RECEIPT_RESERVATION_ALLOCATION_REQUIRED` с `details: {orderId,itemId,deficitQuantity,receivedQuantity}`. Дефицит читается под блокировкой; превышение актуального дефицита даёт `409 WAREHOUSE_RESERVATION_DEFICIT_INSUFFICIENT`, несовпадение суммы — 400. Ошибка любого шага откатывает физическое поступление, изменения резерва, размещение, статус, аудит и ключ запроса целиком.

Ответ размещения дополнен блоком `reservation`: `order`, `orderId`, `reservationId`, `receivedQuantity`, `restoredQuantity`, `increasedQuantity`, `deficitQuantity`, `warnings`. `order` и `warnings` используют DTO Reservations, включая `ORDER_CLOSED`. Блок хранится в `reservationSnapshot`, возвращается в истории размещений и при replay без пересчёта по текущим справочникам или резерву. Для обычного размещения блок отсутствует. Выбранное распределение входит в hash ключа; изменение его составляющих с прежним ключом даёт 409.

`warehouse.receipts.place` разрешает резервирование только количества разрешённого размещения; дополнительных прав ручного управления резервами пользователь не получает. В резервном AuditLog сохраняется `receipt: {receiptId,receiptLineId,restoredQuantity,increasedQuantity}`, а аудит прихода содержит полный результат размещения. Изменение физического остатка аудитируется Stock в той же транзакции.

Положительное поступление само по себе допускает физическое расхождение с резервами. Если менеджер не может обеспечить выбранное резервирование даже после поступления, вся операция отклоняется его штатной ошибкой; проверки менеджера не обходятся. Импортированные строки 1С сохраняют прежнее поведение: внешний `orderSnapshot` не становится внутренним `orderId` и не создаёт резерв автоматически.

### Сопоставление

Номенклатура: `{ "itemId": "15" }` либо `{ "create": { "article": "6204", "name": "Подшипник", "unit": "шт" } }`.

Связь сохраняется по `(sourceSystem, externalId)`, не по артикулу. Несколько внешних записей могут указывать на один товар ESoft после явного подтверждения. Создание при занятом артикуле не объединяет товары автоматически. Единицы должны совпадать; пересчёт упаковок не реализован. Подтверждённая связь не переназначается этим API: объединение уже использовавшихся канонических товаров — отдельная будущая задача.

Связь распространяется на уже загруженные строки этого источника и применяется к следующим документам. Исходные article/name/unit/type в строках не заменяются каноническими значениями.

### Связь ручного прихода с 1С

POST `/:id/reconcile`, где `:id` — документ 1С:

```json
{
  "manualReceiptId": "2",
  "lines": [{ "manualLineId": "20", "receiptLineId": "30" }]
}
```

Нужно сопоставить все строки ручного документа; он должен быть PLACED. Товар, единица и склад должны совпадать, документ 1С должен быть действующим и без конфликта. Каждая ручная строка связывается один раз, повтор той же связи безопасен. Уже размещённое количество ручного документа засчитывается в placed документа 1С. Переполнение отклоняется целиком. Повторного движения остатков нет.

### Статусы и конфликты

- RECEIVED — размещений нет.
- PLACING — размещена часть.
- PLACED — все строки размещены, заполнен placedAt.
- CANCELLED — документ отменён и не доступен для новых размещений.

Placed рассчитывается из операций размещения и подтверждённых связей ручных строк. Это не расчёт текущего Stock: последующая выдача не уменьшает историческое placed.

Новая версия без размещений может заменить состав. После размещения допустимы безопасное увеличение quantity и изменение реквизитов; уменьшение ниже placed, удаление/смена товара/единицы размещённой строки, смена склада и отмена создают конфликт. Текущие строки и Stock сохраняются; новая версия сохраняется как pendingPayload. Новые размещения заблокированы. Более новая исправленная безопасная версия снимает конфликт.

Отмена до размещения переводит в CANCELLED. Отмена после размещения создаёт `SOURCE_CANCELLED_AFTER_PLACEMENT`.

Решение конфликта требует `{ "action": "KEEP_CURRENT", "reason": "Обоснование", "sourceVersion": "3" }` либо `ACCEPT_CANCELLATION` для конфликта отмены. Первое сохраняет текущий документ и отклоняет изменение 1С по явному решению администратора; второе фиксирует отмену, сохраняя физические движения. Исходное предложение и причина остаются в аудите. Эти действия **не исправляют физический остаток**; при необходимости используется отдельная корректировка с основанием. Защита sourceVersion предотвращает решение устаревшего конфликта.

### Списки и карточки

GET списка: warehouseId, source, status (через запятую), hasConflict, hasProblems, attention, itemId, createdByUserId, createdFrom, createdTo, documentDateFrom, documentDateTo, search, page, limit. Рабочий список UI по умолчанию запрашивает `status=RECEIVED,PLACING&hasConflict=false` — незавершённые документы **без конфликтов**. Пользователь включает конфликты отдельно через виртуальное состояние `CONFLICT`: backend удаляет его из реальных статусов и объединяет выбранные статусы с любым конфликтом через OR. При пустом выборе UI запрашивает все четыре реальных статуса без ограничения `hasConflict`. Для совместимости API при отсутствии `status` сохраняет выбор RECEIVED/PLACING и документов с конфликтом; это не дефолтный запрос UI. Для истории передайте `status=PLACED,CANCELLED`. Сортировка createdAt DESC/id DESC, limit 1–100, default 50. `search` выполняет буквальный поиск без учёта регистра по номеру документа, текущему каноническому артикулу и названию связанного товара. `createdFrom/createdTo` — ISO datetime с timezone для createdAt; `documentDateFrom/documentDateTo` — даты YYYY-MM-DD для documentDate. Список не загружает placements: прогресс агрегируется SQL только для текущей страницы в RepeatableRead.

Карточка возвращает header, lineCount, placedLineCount, hasProblems, conflict и lines. Для разбора конфликта доступны sourceDocument (применённый снимок с его version) и pendingSourceDocument (предлагаемая новая версия); sourceVersion в шапке — последняя рассмотренная версия источника. receivedAt обозначает получение последней рассмотренной версии. У строк: исходные данные, itemId/null, mappingStatus, quantity/placed/remaining, order snapshot, placements с историческими снимками. У SERVICE и других типов hasProblems=true, sourceType указывает проблемную строку; разместить её нельзя. Технические requestHash и ключи размещения не публикуются.

Сведения заказа 1С сохраняются в orderSnapshot строки как исходные данные документа.
Они не создают справочник и не связываются автоматически с CustomerOrder.

## БД и история

Схема входит в исходную warehouse-миграцию, без новой миграции пакета. Для уже заполненной локальной тестовой БД выполнен отдельный контролируемый перенос: прежний проведённый приход становится PLACED, прежние строки — историческими размещениями; balances не перепроводятся. Это не универсальный production-upgrader.

Документ → строки → размещения имеют каскадное удаление только на уровне БД для будущей управляемой очистки; DELETE API отсутствует. Товары/склады/места не удаляются каскадом. Связанные ручные строки требуют согласованной политики архивирования. При будущей очистке также необходимо сохранять идентичность/версию внешних документов и идемпотентность, чтобы архив не сделал старый документ снова доступным для приёмки.

Catalog-граница дополнительно проверяется на неизменность минимального DTO, независимое подтверждение внешних ID, откат связи и гонку первого прихода со сменой единицы.

Интеграционные группы разделены: basic (размещение, snapshot, replay, гонки, rollback), import (версии, mapping, отмена, ручная связь, queries), events (реальный HTTP stub 1С, durable inbox, ошибки/retry и устаревшие события).

### Артикул для рабочего отображения

Поле lines[].article содержит только текущий канонический артикул связанного товара ESoft, полученный через публичный Catalog API. Для несопоставленной строки article=null; исходный артикул 1С не используется как запасное значение. После переименования артикула в Catalog рабочая карточка показывает новый вариант, включая повторное получение документа и replay ручного создания. Неактивность товара не мешает чтению истории.

itemArticleSnapshot, исходные документы и снимки размещений сохраняются без изменений как исторические данные; рабочий интерфейс должен использовать lines[].article, а не диагностические sourceDocument/pendingSourceDocument или снимки размещений. Карточка читается вместе с каноническими артикулами в одном RepeatableRead-снимке.

## Кандидаты для связи ручного прихода с 1С

Для фильтра `attention=MANUAL_DUPLICATE` целевые документы сначала ограничиваются остальными фильтрами списка. Проверка кандидатов выполняется пакетами по 1000 ID в том же RepeatableRead-снимке; сортировка и пагинация применяются после проверки, поэтому `total` учитывает все совпавшие документы. Совпадение номера и общая товарная позиция с датой проверяются отдельными SQL-ветками с объединением уникальных ID.

`GET /api/warehouse/receipts/:id/reconciliation-candidates` требует `warehouse.receipts.read` и `warehouse.receipts.map`. Только чтение, один RepeatableRead-снимок; БД и остатки не меняются. Для действующего документа ONE_C с сопоставленным складом возвращает до 10 кандидатов того же склада: ручные PLACING/PLACED без конфликтов и уже связанных строк.

Основание: одинаковый непустой номер документа после trim и приведения регистра (без ограничения даты) либо хотя бы одна общая каноническая позиция `itemId + unit` при датах документа в пределах ±7 дней включительно. Во втором случае обе даты должны быть заполнены; `createdAt` вместо отсутствующей даты не используется. Полное совпадение состава и количеств не требуется: `sameItems` и `sameQuantities` — признаки качества совпадения, а не обязательные условия допуска. Совпадение названий/исходных артикулов не считается идентичностью товара.

Результат `{items:[{id,status,documentNumber,documentDate,sameNumber,sameItems,sameQuantities,matchedItems,manualItems,dateDistance}]}`. `dateDistance` — число дней между датами документов или `null`, если одна из дат отсутствует; совпадение номера допускает такого кандидата. Для сравнения строки агрегируются по товару и единице с точным numeric: sameItems — полный одинаковый набор товарных позиций без несопоставленных товаров у источника; sameQuantities — также одинаковые ожидаемые количества. Это признаки похожести, не разрешение провести связь: текущая доступная ёмкость и все строки проверяются существующим reconcile в транзакции.

Порядок: совпадение номера, полного состава с количеством, полного состава, число общих позиций, близость даты, id по убыванию. При ручном источнике, отмене, конфликте или несопоставленном складе — пустой список; неизвестный ID — 404. Предложения не гарантируют обнаружения всех дублей. Частичный ручной приход сначала нужно полностью разместить; автоматического связывания нет.

`lines[].sourceArticle` — исходный артикул строки ONE_C (для MANUAL — null). Используется только как редактируемое предложение при создании номенклатуры; не является запасным значением `article` в рабочих таблицах. Изменение канонического артикула через Catalog сохраняет внутренний ID, внешние связи и исторические снимки.

Фильтр списка `hasConflict=true/false` отдельно отбирает наличие конфликта с 1С. Сочетается через AND со статусами и `hasProblems`. Последний включает также несопоставленные ссылки и неподдерживаемые типы строк.

Список и карточка возвращают `totalQuantity` и `placedQuantity` как decimal strings: суммы ожидаемого и фактически размещённого количества всех строк, включая размещения связанных ручных приходов. Счётчики lineCount/placedLineCount сохранены отдельно. UI считает процент по количеству, не по завершённым строкам; числовые количества разных единиц складываются по согласованному правилу без пересчёта единиц.

Сортировка списка выполняется на сервере: `sortBy=createdAt|receivedAt|documentNumber|warehouseNameSnapshot|status`, `sortOrder=asc|desc`. Без параметров API сортирует по createdAt DESC; UI для колонки «Получен» запрашивает receivedAt DESC — время получения последнего рассмотренного снимка документа. id в том же направлении разрешает совпадения для стабильной пагинации.

`status` в query дополнительно принимает виртуальное значение `CONFLICT`: оно не является статусом БД. Например, `status=RECEIVED,CONFLICT` выбирает RECEIVED или любой документ с конфликтом; `status=CONFLICT` — только конфликты. Совместимо с остальными фильтрами списка; явный `hasConflict=false` дополнительно исключает конфликты.

Список дополнительно возвращает `unmappedLineCount` (товарные строки без сопоставленной номенклатуры) и `hasReconciliationCandidates` (возможный ручной дубль). Проверка кандидатов выполняется пакетно на текущую страницу по тем же правилам допуска, что подробный поиск: тот же склад, ручной приход PLACING/PLACED без конфликтов и связанных строк; одинаковый номер либо общая позиция `itemId + unit` при датах документа в пределах ±7 дней включительно. Совпадение количества и полного состава не требуется, дата создания не подменяет отсутствующую дату документа. Это подсказка, связь требует подтверждения пользователя.

Фильтры `documentDateFrom` / `documentDateTo` принимают календарную дату `YYYY-MM-DD` и задают включительный период по дате накладной (`documentDate`), независимо от времени получения в ESoft. Допустима одна граница; при заданном периоде документы без даты не попадают в выборку. Обратный период и несуществующие даты отклоняются.

`attention=WAREHOUSE|ITEMS|MANUAL_DUPLICATE` выбирает документы без сопоставленного склада, с несопоставленными товарными строками либо с возможным ручным дублем. Фильтр применяется до пагинации и подсчёта total. `search` ищет по номеру документа, текущему каноническому артикулу или названию связанного товара; прочие фильтры действуют совместно через AND.

Административное согласование отмены после исправления факта: `{ "action": "RECONCILE_CANCELLATION", "reason": "Обоснование", "sourceVersion": "3", "adjustmentIds": ["12"] }`. Помимо integrations.manage требуется warehouse.adjustments.manage. Проверяются принадлежность корректировок размещённым товарам/местам, проведение после получения конфликта и отсутствие прежнего использования для согласования. Привязка корректировок, принятие отмены и аудит атомарны; повторно Stock не меняется. Движения и прежние размещения остаются в истории. Обратного запроса в 1С нет. Для изменения строк этот вариант не применяется.

После такого согласования повторный `POSTED` создаёт конфликт `SOURCE_REPOSTED_AFTER_SETTLEMENT`: приход остаётся отменённым, новый снимок сохраняется в `pendingPayload`, остатки и размещения не меняются. Администратор может выбрать `KEEP_CURRENT`; повтор того же снимка не открывает решённый конфликт заново. Новую физическую поставку оформляют отдельным приходом. Отмена до размещения не препятствует обычному повторному проведению.

Для входящих уведомлений только с objectId обработчик вызывает applySnapshot(): версия 1С не требуется, sourceVersion — внутренняя редакция последнего рассмотренного содержимого ESoft. Сравнение включает нормализованный полный документ, а не только количество. Совпадающий снимок сохраняет редакцию и административное решение KEEP_CURRENT; изменённый снимок получает следующую редакцию. Проверка склада остаётся обязательной даже при совпадении. Низкоуровневый apply() принимает уже назначенную редакцию и сохраняет прежние доменные проверки.

При совпадающем снимке `receivedAt` также сохраняется: повтор уведомления не обновляет дату «Получен» и не поднимает документ в списке. Эквивалентные количества, например `10` и `10.000`, считаются одинаковыми. Цены не входят в контракт прихода; изменение только цен в 1С при неизменном ответе GET не обновляет пользовательскую дату. Время доставки каждого уведомления отдельно сохраняется в журнале интеграций.
