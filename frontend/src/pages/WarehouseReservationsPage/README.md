# Резервы склада

`WarehouseReservationsPage` отображает заказы с положительными резервами. Маршрут `#/warehouse/reservations` и пункт меню «Склад → Резервы» доступны по `warehouse.reservations.read`; страница повторно проверяет permission перед загрузкой.

`useReservationOrders` загружает `GET /api/warehouse/reservations/orders` через общий API-клиент и `useIncrementalList`. Поиск по заказам и товарам выполняется сервером после задержки 250 мс. Фильтр `coverage` принимает ALL, DEFICIT, COVERED. Изменение поиска или фильтра начинает загрузку с первой страницы и отменяет устаревший запрос. Загруженные страницы накапливаются с уникальностью по внутреннему UUID заказа.

`ReservationOrdersTable` использует общий `DataTable` с серверным порядком и оконным рендером. Колонки показывают номер, название, число позиций и обеспеченность. Статус 1С отображает общий `OrderStatus` независимо от состояния обеспеченности. Количества товаров разных единиц не суммируются.

Поиск, настройки фильтров, выбор значения, сообщения и догрузка используют `SearchToolbar`, `AdminModal`, `SelectField`, `Notice` и `ListLoadMore`. Ошибка загрузки допускает повтор; пустая выборка различает отсутствие резервов и отсутствие совпадений по условиям. Адаптивные стили остаются на той же таблице, без отдельной мобильной бизнес-логики.

## Резервы заказа

Нажатие строки или номера заказа открывает `ReservationOrderModal` поверх списка без изменения маршрута. Поиск, фильтры и загруженные страницы списка сохраняются. Доступ определяется `warehouse.reservations.read`, независимо от права `orders.read`. `useReservationOrder` получает шапку и счётчики через `GET /api/warehouse/reservations/orders/:orderId/summary`, затем постранично загружает положительные резервы через `GET /api/warehouse/reservations?orderId=…&quantityState=POSITIVE`. Закрытие окна отменяет незавершённые запросы. Счётчики охватывают все позиции, независимо от числа загруженных страниц.

Окно использует общий `AdminModal`, `SearchToolbar`, `CheckboxFilterModal` и `OrderStatus`. Шапка и поиск расположены вне прокручиваемого списка. Настройки поиска открываются стандартной кнопкой фильтров `SearchToolbar`; фильтр дефицита находится в общем `CheckboxFilterModal`. Поиск по артикулу и названию передаётся серверу с задержкой 250 мс, фильтр дефицита — параметром `deficit=true`. Смена условий отменяет предыдущий запрос, сбрасывает пагинацию и положение списка.

`ReservationItemRow` отображает название и артикул через общий `WarehouseItemIdentity`, обеспеченное и полное количество, дефицит и число положительных распределений. Нажатие строки раскрывает места под ней; одновременно можно раскрыть несколько резервов. Размещения используют общий `WarehouseLocationSummary`, а дефицит выводится отдельной строкой «Не обеспечено». Раскрытие не делает HTTP-запросов. Состояние хранится по UUID резерва; скрытые поиском строки не отображаются. Закрытие заказа сбрасывает локальное состояние. Изменение естественной высоты окна использует штатную анимацию `AdminModal`, с учётом общих правил мобильных диалогов и `prefers-reduced-motion`.

`ReservationItemsList` сохраняет серверную догрузку через `ListLoadMore` и оконный рендер. `useReservationWindow` использует общий расчёт `getGridWindow`, измеряет строки через `ResizeObserver` и кэширует высоты по UUID и состоянию раскрытия. При изменении ширины измерения сбрасываются. Изменение высот над видимой позицией компенсируется в `scrollTop`, чтобы сохранить позицию чтения, включая сворачивание ранее измеренных строк вне окна. Прокрутка слушается на контейнере модалки, а не на странице. Новые зависимости не требуются.

Количества сохраняются строками Decimal и форматируются через `warehouse-quantity`; вычисления складских количеств через JavaScript number не выполняются. Данные распределений соответствуют загруженному снимку позиции. Закрытые заказы доступны для просмотра.

## Управление резервами

`ReservationOrderModal` принимает эффективные `permissions`. Создание и уменьшение потребности доступны по `warehouse.reservations.manage`, изменение обеспеченности — по `warehouse.reservations.coverage.manage`. Действия размещены вне кнопки раскрытия строки.

`ReservationOperationForm` использует общие поля, выбор номенклатуры и места хранения. `useReservationOperation` валидирует положительные количества с точностью до трёх знаков через BigInt, формирует Decimal-строки и отправляет существующие команды API. Окончательная проверка свободного остатка выполняется сервером. Уменьшение потребности передаёт выбранные размещения и отдельно необеспеченную часть; комментарий обязателен для изменения существующего резерва.

После сохранения обновляются строки и счётчики текущего заказа и основной список. Поиск, фильтр и набор раскрытых UUID сохраняются. При обновлении повторно загружается ранее просмотренное число страниц; контейнер списка сохраняется для удержания прокрутки. Если позиция перестаёт соответствовать серверному фильтру, она исчезает из выборки.

Физические перемещения выполняются из окна «Переместить остаток» модуля «Остатки». Управление резервами заказа содержит только команды потребности и обеспеченности.

Создание, уменьшение и команды обеспеченности не имеют ключа идемпотентности в серверном контракте. После неопределённого ответа их повтор в текущей форме блокируется. Пользователю предлагается получить актуальные данные перед дальнейшими действиями. Ошибки серверной валидации отображаются без подмены успешным результатом.

Справочники мест и номенклатуры используют существующие read API Stock и Catalog; для их загрузки нужны соответствующие права чтения. Наличие разрешения на команду не заменяет серверную проверку доступа к справочнику.

При создании и восстановлении резерва `useReservationPlaces` загружает все страницы положительных физических остатков выбранной номенклатуры через `GET /api/warehouse/stock`. В выборе остаются активные места активных складов. До выбора товара поле недоступно; смена товара очищает выбранное место и отменяет устаревшие запросы. Свободное количество повторно проверяется при сохранении сервером.
