# Приход

В ручном приходе «Создать номенклатуру» открывает форму черновика с артикулом, названием и единицей. Проверка артикула при вводе учитывает каталог, неактивные позиции и другие черновики. Новый товар можно выбрать в нескольких строках и редактировать. До отправки прихода он существует только в форме; закрытие формы ничего не создаёт. При сохранении `newItems: [{ draftId, item: { article, name, unit } }]` и строки с `draftId` отправляются вместе с обычными строками с `itemId`. Backend создаёт товары, приход и аудит одной транзакцией. Дубли и ошибки откатывают всё; повтор запроса с прежним `requestKey` возвращает сохранённый приход. Для новых товаров дополнительно требуется `warehouse.catalog.manage`. Физические остатки меняются при размещении.

Пункт склада `#/warehouse/receipts` использует `warehouse.receipts.read`. Карточка — `#/warehouse/receipts/:id`, ручной ввод — `#/warehouse/receipts/new` (дополнительно `warehouse.receipts.manage`). BigInt ID остаются строками.

Список по умолчанию получает незавершённые документы без конфликтов. «Документы» разделяет «В работе», «Конфликты» (все статусы) и «Все»; hasConflict передаётся в серверный фильтр. Поиск по номеру выполняется сервером с задержкой 250 мс, подгрузка порциями по 50 документов через общий useIncrementalList/ListLoadMore; таблица использует оконный рендер DataTable.windowed, кнопок страниц и общего обновления списка нет. Фильтры склада, источника, проблем и «Все» находятся в стандартной модалке поиска. Неактивные склады доступны в фильтре истории, для новых операций выбираются только активные справочники.

Ручной документ содержит до 100 строк; поиск номенклатуры использует `q` и первые 50 совпадений, не загружает весь каталог. Создание документа не меняет остатки. Размещение выполняется через существующий API с ключом запроса. Перед отправкой ключ и payload записываются в sessionStorage текущей вкладки отдельно для пользователя и операции; после потери ответа повтор, закрытие формы и перезагрузка страницы сохраняют ту же операцию. Пока результат не подтверждён, данные отправки нельзя менять. При недоступности хранилища новая операция не отправляется. Та же схема применяется к ручному созданию. Закрытие самой вкладки завершает срок хранения: перед новым вводом нужно проверить историю документов. Синхронный ref предотвращает повторный submit. Quantity сравнивается в тысячных через bigint; переиспользуются общие складские функции и генератор UUID, работающий в HTTP LAN.

Карточка показывает размещённое и оставшееся количество, историю мест и исходные версии. Размещение блокируется при конфликте, отмене, отсутствии связей, неподходящем типе и связанном ручном документе. Сопоставление товара требует также `warehouse.catalog.links.manage`; создание товара и внешней связи остаётся в backend Catalog. Reconcile явно сопоставляет все строки полностью размещённого ручного документа того же склада; суммарное количество проверяется по каждому получателю, окончательная валидация и атомарность принадлежат backend.

Разбор конфликта требует `integrations.manage`, передаёт sourceVersion и обязательную причину. Сохранение текущего документа и принятие отмены не корректируют физический остаток.

В «Пользователях» вкладка «Интеграции» доступна по `integrations.manage`, независимо от права управления учётными записями. Она содержит настройки источников и потоков, выпуск и отзыв API-ключей, журнал событий и ручной повтор обработки. Полный API-ключ показывается один раз после создания; после закрытия окна доступны только сведения о ключе. Секрет ESoft → 1С вводится скрытым полем и обратно не загружается. При редактировании источника пустой `authorization` сохраняет текущий секрет, непустой заменяет его. Настройки отделены от рабочего экрана кладовщика.

Переиспользуются SearchToolbar, DataTable/AppTable, AdminModal, SelectField, TextField/AdminFormControls, Notice, LoadingIndicator, Switch, ConfirmationProvider и общее бизнес-время. Изменений БД и backend для экранов не требуется. Обновление документов выполняется кнопкой; SSE/автоподписки не добавлены.

В карточке 1С пользователь с правами сопоставления открывает «Действия» → «Связать с ручным приходом». Кнопка доступна для документа с выбранным складом, без конфликта и не в статусе CANCELLED. Она открывает модальное окно `ReceiptReconcileDialog`; непосредственно в карточке списка возможных совпадений нет. В окне можно искать по номеру и выбирать полностью размещённые ручные приходы того же склада, по 25 документов на страницу. Автоматические рекомендации до 10 кандидатов и признаки совпадения состава/количеств здесь не отображаются. После выбора документа пары строк подставляются только при однозначном совпадении itemId/unit; при неоднозначности пользователь выбирает строку 1С сам. Ошибки загрузки и связывания отображаются в окне. До явного «Сохранить» записи и остатки не меняются; backend повторно проверяет допустимость связи. Связывание не увеличивает остатки повторно.

В таблице прогресс считается по totalQuantity/placedQuantity: например 2 из 50 = 4%, даже если ни одна позиция ещё не завершена. Процент вычисляется через bigint в тысячных, до одной десятой процента с усечением, без преждевременного округления до 100%. При нулевом ожидаемом количестве — 0%. Суммируются числовые количества всех единиц, без их конвертации.

Колонка состояния убрана из списка. В фильтрах используется общий SelectField multiple: RECEIVED, PLACING, PLACED, CANCELLED и виртуальное состояние CONFLICT. По умолчанию выбраны RECEIVED/PLACING без конфликтов. Пустой выбор — все состояния; несколько выбранных состояний объединяются через OR. CONFLICT включает конфликты любого фактического статуса, остальные фильтры применяются через AND.

## Формы операций

`ReceiptActionDialog` содержит общую модалку, заголовок и выбор формы по действию. Размещение, сопоставление номенклатуры, разрешение конфликта и отмена реализованы в отдельных `Receipt*Form`. Каждая форма выполняет свой API-вызов и локальную валидацию. Общий `useReceiptActionForm` управляет ошибкой, состоянием сохранения и защитой от повторной отправки; `ReceiptPlaceForm` отдельно сохраняет идемпотентную отправку через `useReceiptSubmission` и обрабатывает изменение доступного остатка.
