# Установка пакетов БД

Ядро, оборудование и СИЗ имеют отдельные SQL-пакеты в `backend/prisma/packages`. Все устанавливаются в одну PostgreSQL-базу. Общая `_prisma_migrations` фиксирует применение каждого SQL. Установщик использует только выбранные пакеты; отдельного архива старого init и inventory в проекте нет.

Пакеты используют схему PostgreSQL `public`. Другое значение `schema` в DATABASE_URL отклоняется.

База должна использовать UTF8 и поддерживать приведение кириллицы к нижнему регистру. Для PostgreSQL 17 используйте, например, ICU `ru-RU` (SQL создания приведён в installation.md). До миграций установщик проверяет это свойство; неподходящая локаль libc `C` отклоняется. Это необходимо для поиска и индексов уникальности по `lower(name)`.

## Состав поставки

Корневой `database-packages.json` задаёт дополнительные модули:

```json
{ "modules": ["equipment", "ppe"] }
```

Ядро подключается всегда. Для установки без СИЗ задайте `["equipment"]` и не поставляйте `backend/prisma/packages/ppe`. Для одного ядра задайте `[]`. Неизвестные имена, дубликаты, отсутствующий выбранный пакет и несовпадающие контрольные суммы отклоняются до SQL.

Это состав БД, а не переключатель frontend/backend. Текущий backend ещё не адаптирован к отсутствию таблиц модулей. До разделения прикладного кода обычная установка приложения должна включать оба модуля. Полная Prisma-схема и Client пока остаются общими; генерация Client сама по себе таблиц не создаёт.

## Новая установка

Подготовьте `.env`, PostgreSQL и MinIO. Укажите операторский DATABASE_URL. Из корня выполните `npm ci`, `npm run setup:prod`, затем `npm run build`.

setup использует пакетные команды миграций и запускает seed стран, календаря и должности администратора. Типы обслуживания создаются только при выбранном equipment. Повторный seed безопасен для этих начальных данных.

До запуска backend верните прикладные реквизиты БД и проверьте права согласно installation.md. Весь setup и seed выполняйте при остановленном backend. Миграции получают файловую блокировку установки; SQL-операция дополнительно защищена advisory lock на уровне БД от параллельного запуска из другого checkout. Это не исключает ручные SQL-операции и не является единой транзакцией всей процедуры setup/seed.

## Позднее подключение

Пример: установлены core и equipment, нужен СИЗ.

1. Остановите backend, создайте согласованную резервную копию по регламенту.
2. Добавьте пакет `backend/prisma/packages/ppe` с manifest и миграциями.
3. Добавьте `ppe` в `database-packages.json`, сохранив ранее установленные пакеты.
4. С операторскими реквизитами выполните `npm run setup:prod`.
5. Проверьте `npm run db:migrate:status`, верните прикладные реквизиты и только затем запускайте совместимый backend.

init СИЗ создаст отдельную таблицу ppe_employee_sizes с пятью nullable полями размеров и CHECK размера обуви. employee_id — первичный и внешний ключ на employees с каскадным удалением. Общая таблица employees не меняется. Строка размеров создаётся при первом сохранении; до этого API возвращает ppeSizes: null. Размеры возвращаются внутри ppeSizes; верхнеуровневых полей размеров нет. В общей Prisma-модели Employee остаётся только необязательная связь ppeSizes: обычные запросы `Employee`, не запрашивающие relation `ppeSizes`, работают без установленного PPE; запрос `ppeSizes` при отсутствии модуля приведёт к ошибке отсутствующей таблицы.

Отключение функций не удаляет таблицы или историю. Если модуль раньше был установлен, его SQL-пакет остаётся в материалах обслуживания и в выборе БД. Убирать из поставки можно пакет, который в этой БД никогда не устанавливался. Полная деинсталляция — отдельная будущая процедура.

## Команды и новые изменения

- `npm run db:generate`: генерация полного Prisma Client.
- `npm run db:migrate:status`: сверка manifest, истории/checksum и штатный Prisma status. Ожидающие миграции дают ненулевой код, ничего не применяют.
- `npm run db:migrate:deploy`: проверка manifest/истории, подготовка набора выбранных пакетов и штатный Prisma deploy.
- `npm run db:seed`: seed выбранных пакетов; backend должен быть остановлен.

Установщик создаёт временный набор в `.local/migration-set-*`, не изменяет SQL и удаляет набор после завершения. Строка подключения передаётся дочернему процессу через окружение, не записывается в Prisma config. При аварийном завершении набор может остаться; он не является источником миграций.

Прямые `prisma migrate ...` и `prisma db push` через основной config заблокированы: они обходят пакетный контроль. Для применения и проверки доступны только пакетные deploy/status. Новое изменение оформляется отдельным SQL в пакете-владельце, с уникальным стабильным именем, SHA-256 в manifest и проверкой на изолированной БД. Для создания SQL можно использовать Prisma diff в специально подготовленной среде, затем обязательно проверить ручные объекты. Не генерируйте изменения из полной схемы против частичной БД.

Применённые SQL не редактируются. `.gitattributes` сохраняет байты SQL миграций при checkout. Контрольные суммы обнаруживают изменения, но не подтверждают доверенность источника пакета.

После сбоя миграции часть DDL может сохраниться. Установщик блокирует последующие status/deploy; автоматического отката или автоматического исправления истории нет. Оператор сначала восстанавливает согласованное состояние и использует штатный Prisma migrate resolve с отдельным операторским config. Обычный основной config намеренно не обходит проверки пакетов.

## Проверка пакетов

Перед выпуском или изменением миграций рекомендуется выполнить реальные интеграционные проверки на изолированном PostgreSQL.

Проверяются:

- установка `core`, `core + equipment`, `core + ppe` и полного состава;
- позднее подключение каждого модуля и сохранение существующих данных;
- повторный deploy и seed;
- контрольные суммы, история миграций и блокировки;
- ограничения, триггеры и ручные SQL-объекты;
- запросы `Employee` без PPE и контракт `ppeSizes`;
- права PostgreSQL и backup/restore;
- обработка неуспешной миграции и rollback при ошибке аудита.

Тесты используют временные PostgreSQL-кластеры без чтения рабочего `.env` и не должны обращаться к рабочей БД.

```powershell
$env:ESOFT_MODULAR_MIGRATION_TEST = '1'
try {
  npm run build:backend
  node --test `
    tests/scripts/infrastructure/prisma/package-schema.real.integration.test.mjs `
    tests/scripts/infrastructure/prisma/package-behavior.real.integration.test.mjs `
    tests/scripts/infrastructure/prisma/package-production.real.integration.test.mjs
} finally {
  Remove-Item Env:ESOFT_MODULAR_MIGRATION_TEST
}
```

Требуются `initdb`, `pg_ctl`, а для backup/restore — `pg_dump` и `pg_restore`.

По умолчанию используется PostgreSQL 17 из `C:/Program Files/PostgreSQL/17/bin`. Другой путь задаётся через `ESOFT_TEST_PG_BIN`.

Обычный `test:scripts` не запускает эти проверки без opt-in.
