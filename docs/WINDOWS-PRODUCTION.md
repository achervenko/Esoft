# Подготовка Esoft к production на Windows

В репозитории находятся шаблоны, а не установленное окружение. Они не устанавливают службы, не меняют firewall, DNS или сертификаты. Администратор копирует и адаптирует их вне checkout. Бинарные файлы WinSW, Caddy и MinIO поставляются отдельно с зафиксированными версиями и проверенными контрольными суммами.

## Схема запуска

PostgreSQL и MinIO работают как отдельные службы. `EsoftBackend` запускает непосредственно `node.exe backend/dist/src/main.js`. `EsoftProxy` раздаёт `frontend/dist` и проксирует `/api`, `/api/*` и `/health` на loopback backend. `npm run dev`, `npm start` и Vite preview не являются production-службами.

Шаблоны: [deploy/windows](../deploy/windows). Пример каталога:

- `C:\Esoft\app` — единственный checkout приложения, сборка и корневой `.env`;
- `C:\Esoft\services` — адаптированные XML, переименованные WinSW executables и Caddyfile;
- `C:\Esoft\tools` — проверенные MinIO/Caddy;
- `C:\Esoft\logs` — журналы;
- `C:\Esoft\certs` — сертификат и закрытый ключ;
- `D:\EsoftData\minio` и отдельный каталог backup — данные вне checkout.

Для каждого XML нужен WinSW executable с тем же basename: `EsoftBackend.exe` + `EsoftBackend.xml`. Команды `install`, `start`, `stop`, `status`, `uninstall` выполняются администратором при развёртывании. Замените все пути и PostgreSQL service ID; зависимость от локального MinIO/PG удаляется при использовании удалённых серверов. До установки проверьте конфигурацию выбранной версии WinSW по её документации.

Службам назначаются отдельные непривилегированные учётные записи. Backend нужны чтение приложения и `.env`, запись в `app\.local`; proxy — чтение frontend и сертификатов; MinIO — доступ к своему каталогу данных. Все службы пишут только в собственные каталоги журналов. Закрытые ключи и операторские пароли не хранятся в Git. Без отдельной настройки service account WinSW использует системную учётную запись: такой шаблон нельзя устанавливать без адаптации прав.

## Конфигурация приложения и HTTPS

### Реквизиты службы MinIO

WinSW не читает корневой `.env` приложения. При установке администратор добавляет в **локальную копию** `C:\Esoft\services\EsoftMinio.xml` два элемента непосредственно внутри `<service>`:

```xml
<env name="MINIO_ROOT_USER" value="ЗАМЕНИТЬ_НА_ROOT_LOGIN" />
<env name="MINIO_ROOT_PASSWORD" value="ЗАМЕНИТЬ_НА_СЛУЧАЙНЫЙ_ROOT_PASSWORD" />
```

WinSW передаёт эти значения только дочернему процессу MinIO. Пароль в XML хранится открытым текстом: перед заполнением ограничьте NTFS ACL файла и каталога служб администраторами и учётной записью wrapper; обычным пользователям чтение запрещено. Значения должны быть XML-экранированы, например `&` записывается как `&amp;`. Заполненный XML находится вне репозитория, не передаётся в Git и не включается в общедоступные копии конфигурации. Это отдельные root-реквизиты MinIO, а не `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` приложения. После изменения реквизитов перезапустите службу; не выводите их в команды диагностики или журналы.

Не используйте глобальные системные переменные для этих секретов: их могут наследовать другие службы. Шаблон без заполненных локальных `<env>` не является готовой конфигурацией MinIO.

В корневом `.env` задаются:

```ini
NODE_ENV=production
BACKEND_HOST=127.0.0.1
BACKEND_PORT=3000
BACKEND_URL=https://insolution-esoft.ru
FRONTEND_URL=https://insolution-esoft.ru
BETTER_AUTH_URL=https://insolution-esoft.ru
VITE_API_URL=https://insolution-esoft.ru
```

Остальные обязательные значения — по [CONFIGURATION.md](CONFIGURATION.md). При сборке frontend также требуются его listener host/port согласно профилю `frontend`; в production отдельный frontend listener не запускается. API endpoints содержат `/api`, поэтому здесь URL без `/api`.

Домен во внутреннем DNS указывает на LAN-адрес proxy. Firewall допускает HTTPS только из нужных сетей; PostgreSQL, backend, S3 API и MinIO console не публикуются в интернет. Шаблон Caddy не включает доступ к MinIO console и не раздаёт checkout целиком.

`Caddyfile.example` использует готовые PEM-файлы. Для закрытого сервера сертификат получают и продлевают через DNS-01 отдельным механизмом администратора: HTTP-публикация сервера не требуется. После замены файлов выполняется проверка и reload Caddy; контролируется срок действия сертификата. Сам шаблон не реализует продление. Альтернатива — корпоративный CA с установленным доверием на телефонах и ПК.

Hooks REG.RU и инструкция автоматического продления: [HTTPS-RENEWAL.md](HTTPS-RENEWAL.md).

Перед запуском администратор выполняет `caddy validate --config Caddyfile --adapter caddyfile`. После запуска — `npm run doctor:prod` и вход через домен. Хэш-маршруты frontend не требуют SPA rewrite; неизвестные реальные пути получают 404.

## Остановка, перезапуск и журналы

WinSW сначала пытается передать Ctrl+C непосредственно Node и ждёт до 60 секунд. Nest завершает HTTP-запросы и закрывает Prisma/S3. Принудительное завершение после timeout всё ещё возможно: на целевом сервере необходимо проверить штатный stop, завершение активного запроса и исчезновение installation lock. Не используйте `hidewindow=true`, не убедившись в доставке Ctrl+C выбранной версией wrapper.

Шаблоны предусматривают две попытки перезапуска, затем остановку. После аварийного завершения lock намеренно остаётся, и backend может не перезапуститься: оператор проверяет отсутствие старого процесса и незавершённого restore. Чужой lock и recovery marker автоматически не удаляются. Порядок восстановления описан в документации backup/restore. Service status `Running` сам по себе не гарантирует готовность API; контролируйте `/health`, `doctor:prod`, ошибки служб и свободное место.

stdout/stderr ротируются по размеру: 10 MiB, до 10 архивных файлов на поток. HTTP access log в шаблоне не включён; при необходимости его включают отдельно с ротацией и ограничением доступа, поскольку URL могут содержать пользовательские параметры.

## Резервное копирование

`Invoke-EsoftBackup.ps1` предназначен для Windows Task Scheduler: абсолютные `ProjectRoot` и `NodePath`, одна задача без параллельных запусков, отдельная операторская учётная запись. Скрипт останавливает работавший backend, запускает существующий backup, затем пытается вернуть службу в прежнее состояние. PostgreSQL и MinIO остаются работающими. Ошибка backup или запуска службы даёт ненулевой exit code. Task Scheduler должен сохранять результат и сообщать оператору о сбое; перезапуск backend проверяется также через health.

Пример действия задачи после адаптации путей и реквизитов: программа `powershell.exe`, аргументы `-NoProfile -NonInteractive -File "C:\Esoft\app\deploy\windows\Invoke-EsoftBackup.ps1" -ProjectRoot "C:\Esoft\app" -NodePath "C:\Program Files\nodejs\node.exe"`. Рабочий каталог — `C:\Esoft\app`. Не задавайте принудительный короткий timeout задачи: он может прервать backup до возврата backend. Сохраняйте stdout/stderr через внешний wrapper с ротацией; Task Scheduler хранит exit code, но сам по себе не архивирует вывод процесса.

Скрипт не переключает пароли. Перед задачей должен быть подготовлен операторский доступ к БД согласно [installation.md](installation.md), после неё возвращён прикладной `DATABASE_URL` до запуска backend. При временной смене реквизитов используйте `-LeaveStopped`: backend останется остановленным и при успешном backup, и при ошибке. Для автоматического расписания администратор должен организовать переключение в защищённом внешнем wrapper либо предоставить backup доступ без изменения runtime-реквизитов. Нельзя оставлять migrator в окружении приложения. Пока этот доступ не организован, используйте ручной backup по регламенту, а не активируйте расписание.

Рекомендуемый начальный регламент: ежедневная копия в окно обслуживания, не менее 14 успешных копий и 30 дней хранения; отдельные предрелизные и recovery-копии сохраняются до завершения проверки обновления/восстановления. Выносите копии на другой носитель и периодически проверяйте restore в изолированном окружении. Удаление выполняет администратор только для завершённых, уже вынесенных копий; `.partial`, recovery-каталоги и копия, связанная с recovery marker, не удаляются автоматически. В проекте нет автоматического prune: он не должен уничтожить единственную пригодную копию.

## Обновление и откат

1. Отключите расписание backup и автоматические действия service manager на время обслуживания. Остановите backend и proxy; PG/MinIO оставьте работающими. Убедитесь, что lock освобождён.
2. Сохраните идентификатор текущего commit/release, настройки вне Git, предыдущие сборки и необходимые версии Node/npm. Создайте проверенную согласованную копию БД + S3; запишите путь рядом с идентификатором релиза. Backup appVersion не заменяет Git commit, поскольку версия package.json может не меняться.
3. Получите выбранный release, выполните `npm ci`, `npm run db:generate` и сборку. Для миграций временно используйте migrator и выполните `npm run setup:prod`; при ошибке не запускайте приложение. Верните прикладные реквизиты.
4. Проверьте конфигурацию proxy, прикладные права, запустите backend и proxy, выполните `npm run doctor:prod` и проверку входа/ключевых операций через HTTPS. После успешной проверки верните расписание и recovery policy служб.
5. При неудаче снова остановите службы. Если схема и данные совместимы с прошлым кодом, верните прежний release и его зависимости/сборки. Если миграции изменили данные или совместимость неизвестна, используйте штатный restore предрелизной копии БД + S3, затем верните старый release. Это возвращает данные к моменту backup; не допускайте новых записей до принятия релиза.
6. После неуспешного restore не обходите recovery marker. Сначала завершите восстановление по его диагностике, затем проверяйте старый release и запускайте службы.

Это регламент одного checkout и одного backend; переключение на другой checkout создаёт другой lock и не должно использоваться для параллельной работы с той же БД/S3.
