# База данных склада

Пакет `warehouse` зависит только от `core`. Его Prisma-модели находятся в
`backend/prisma/schema/warehouse`, SQL и manifest — в `backend/prisma/packages/warehouse`.
Init-миграция: `20261016000000_warehouse_init`.

В текущем `database-packages.json` выбран `warehouse` вместе с `equipment` и `ppe`.
Пакетный deploy устанавливает его таблицы. Для других установок состав модулей
определяется их `database-packages.json`; включение склада требует сохранения
ранее установленных пакетов и выполнения пакетного deploy.
Порядок обслуживания описан в [DATABASE-PACKAGES.md](DATABASE-PACKAGES.md).

`WarehouseModule` подключается только при выбранном `warehouse`; при выключенном
модуле его складские маршруты отсутствуют. Реализованы справочник мест хранения
([Storage Locations](../backend/src/warehouse/storage-structure/README.md)) и локальная номенклатура,
отдельной страницы склада пока нет. Контракт API:
[Catalog](../backend/src/warehouse/README.md).

Исходная миграция пакета обновлена до первой установки: добавлены склады и обязательная связь мест со складом. Для уже установленного старого пакета необходима отдельная миграция обновления.

## Сущности

- `WarehouseItem` / `warehouse_items`: артикул, наименование, базовая единица измерения,
  комментарий и активность. Единица — обязательная строка до 50 символов.
- `Warehouse` / `warehouses`: уникальное наименование и активность склада.
- `WarehouseStorageLocation` / `warehouse_storage_locations`: склад, наименование и активность места хранения.
  `warehouseId` обязателен; название места уникально в пределах склада.
  Новое место активно по умолчанию; отключение сохраняет связанные данные.
- `WarehouseProject` / `warehouse_projects`: номер проекта, необязательное наименование
  и активность. Новый проект активен по умолчанию; закрытие через `isActive = false`
  сохраняет резервы и связанные документы.
- `WarehouseBalance` / `warehouse_balances`: количество номенклатуры в месте хранения;
  пара номенклатуры и места уникальна.
- `WarehouseProjectReservation` / `warehouse_project_reservations`: резерв остатка
  под проект; пара остатка и проекта уникальна.
- `WarehouseIssueSheet` / `warehouse_issue_sheets`: обязательный склад `warehouseId`,
  сведения о листе выдачи, исходном файле, статусе, создателе и обработавшем пользователе.
- `WarehouseIssueSheetLine` / `warehouse_issue_sheet_lines`: количество,
  исходные значения импорта, результат сопоставления, ошибка и номер строки.
  Номенклатура, место и проект могут отсутствовать до сопоставления.
  Место в строке — сопоставленное или предложенное место из входного файла,
  а не запись фактической выдачи. Исполнение хранится отдельно в выдачах и их позициях.
  `unitSnapshot` хранит единицу интерпретации строки; до сопоставления может быть `null`.
  Backend должен заполнить снимок до обработки листа и не пересчитывать его
  по текущему справочнику при чтении истории.
- `WarehouseIssue` / `warehouse_issues`: самостоятельная фактическая выдача,
  обязательный склад `warehouseId`, её тип, необязательный проект, связь со строкой листа,
  выдавший пользователь,
  комментарий, признак запрошенного административного режима `overrideReservations`
  и время создания. Фактический расход чужих резервов определяется по сохранённому
  `reservationUsage` и возвращается как `foreignReservationsUsed`.
  Обязательный `snapshot` (JSONB, version=1) сохраняет склад, проект, имя выдавшего,
  лист/строку и расход резервов; `searchText` хранит исторический поисковый текст.
- `WarehouseTransfer` / `warehouse_transfers`: немедленное перемещение одной номенклатуры
  между двумя местами, количество, автор, комментарий и время. Снимок товара, мест
  со складами и количеств до/после хранится в `snapshot` (JSONB).
  Уникальная пара `(created_by_user_id, request_key)` защищает от повторов;
  `request_hash` проверяет совпадение команды. В обычном режиме резервы остаются
  на исходном месте; moveReservation=true переносит резерв выбранного проекта
  вместе с товаром. Факт переноса и количества до/после сохраняются в snapshot.reservationTransfer.
  Контракт: [Transfers](../backend/src/warehouse/transfers/README.md).
- `WarehouseIssuePosition` / `warehouse_issue_positions`: остаток и количество
  конкретной выдачи. Пара `(issue_id, balance_id)` уникальна: один остаток
  встречается в выдаче не более одного раза, количества объединяются в одну позицию.
  Обязательный `snapshot` (JSONB) хранит товар, единицу и место со складом
  на момент выдачи; GET не читает текущие справочники для этих полей.

Массовый приход хранится в `WarehouseReceipt` и `WarehouseReceiptLine`: [Receipts](../backend/src/warehouse/receipts/README.md). Общий сервис и ручной API используют `Stock.receiveStock(...)`; интеграция с 1С пока не реализована.
Номенклатура склада не связана с каталогом СИЗ или оборудованием.

## Типы и связи

Складские ID — `bigint` / Prisma `BigInt`, с автоматической генерацией.
Внутри backend ID хранятся как `bigint` либо десятичные строки и никогда
не преобразуются в JavaScript `number`. В JSON API ID передаются строками.
Пользователи берутся из существующей таблицы `user`: ссылки на них имеют тип `text` / `String`.
В `User` добавлены только обратные связи; новых scalar-колонок в ядре нет.

Количество — `numeric(14,3)` / Prisma `Decimal`. Значение по умолчанию для остатков — ноль.
Количество резерва задаётся явно и должно быть строго положительным; при снятии
резерва строка удаляется. Числа следует обрабатывать десятичной арифметикой.
Все количества выражены в базовой единице номенклатуры. Конвертаций внутри склада
нет: перевод внешних упаковок в базовые единицы выполняется интеграцией до записи.
Замена базовой единицы запрещена, если на номенклатуру ссылается хотя бы один
`WarehouseBalance` (в том числе с нулевым количеством) или `WarehouseIssueSheetLine`.
Это предотвращает изменение смысла уже сохранённых количеств и исторических данных.

SQL CHECK допускают нулевой остаток и запрещают отрицательный; резерв должен
быть строго положительным; количество строки листа и позиции фактической выдачи
должно быть строго больше нуля. Возврат оформляется отдельной операцией.
Эти CHECK определены в init SQL и отмечены комментариями в Prisma: генерация
миграций не должна их удалять.

Даты событий листа и фактической выдачи — `timestamptz(6)`; `createdAt`
по умолчанию задаётся сервером БД через `now()`. Статусы листа и сопоставления — обязательные строки до 50 символов, без
предопределённого списка значений и значения по умолчанию.

Внешние ключи используют `ON DELETE RESTRICT` и `ON UPDATE CASCADE`.
Удаление связанных справочников, пользователей, листов и остатков блокируется;
связанные документы не удаляются каскадно.

Отдельной таблицы аудита склада нет. Init пакета добавляет значение `warehouse`
в общий PostgreSQL enum `audit_module`; Prisma использует `AuditModule.WAREHOUSE`.
Catalog и [Stock](../backend/src/warehouse/stock/README.md) записывают изменения
в общий аудит в одной транзакции с данными. Stock предоставляет read-only HTTP API
для просмотра физических остатков; операции изменения физического количества
остаются внутренними и вызываются бизнес-компонентами. Документы и правила
резервов реализуются отдельно.
ID складских объектов помещаются в `entityStringId`, поскольку общий
`entityId` имеет тип `integer`.

Номер строки строго положителен (SQL CHECK) и уникален внутри листа:
`(issue_sheet_id, row_number)`.
Одинаковый номер в разных листах разрешён. Остатки и резервы сохраняют
собственные автоматически генерируемые `id`; составные уникальные ключи
не заменяют их первичные ключи.

Резерв входит в физический остаток:

```text
physical = warehouse_balances.quantity
reserved = SUM(warehouse_project_reservations.quantity)
available = MAX(physical - reserved, 0)
shortage = MAX(reserved - physical, 0)
```

Новый резерв создаётся только в пределах свободного количества под блокировками
Stock. Административная корректировка может уменьшить физический остаток ниже
суммы резервов: потребность проектов сохраняется, нехватка отражается как `shortage`.
Корректировка не уменьшает и не удаляет резервы автоматически. Обычные операции
выдачи и перемещения должны учитывать существующий дефицит и не увеличивать
необеспеченность резервов. Межтабличного CHECK в БД нет. Для поиска резервов
проекта предусмотрен индекс `project_id`.

Управление текущими резервами предоставляет
[Reservations API](../backend/src/warehouse/reservations/README.md): список,
создание, изменение только количества и снятие через DELETE. Все изменения
проверяют `warehouse.reservations.manage` и записывают аудит в одной транзакции
с блокировками Stock. Проекты пока берутся из `warehouse_projects`.
Для складских форм доступен минимальный [Projects read API](../backend/src/warehouse/projects/README.md).
Это временная заглушка; полноценный Projects-модуль и импорт 1С ещё не готовы.

## Корректировки

`WarehouseStockAdjustment` хранит тип `WRITE_OFF`/`SURPLUS`, положительное количество,
остаток до и после, причину, комментарий, пользователя, время и ключ повторного запроса.
`WarehouseStockAdjustmentAttachment` связывает операцию с неизменяемыми `StorageFile`.
Ключ запроса уникален в пределах пользователя; тип и разница количеств согласованы
SQL CHECK. Корректировка, файлы, Stock и аудит сохраняются одной транзакцией.
Документы предварительно загружаются в универсальный Storage; неиспользованные
загрузки удаляются после истечения срока. Контракт: [StockAdjustments](../backend/src/warehouse/adjustments/README.md).

## Фактические выдачи

SQL CHECK разрешает два типа:

- `MANUAL`: `issueSheetLineId` отсутствует; проект может отсутствовать или быть задан.
- `ISSUE_SHEET`: `issueSheetLineId` обязателен. Проект выдачи может храниться
  отдельно как фактический проект операции; backend проверяет его соответствие строке.

Тип хранится как `varchar(50)` / Prisma `String`; добавление нового типа требует
изменения CHECK, который также связывает тип с наличием строки листа.
Одна строка листа имеет от нуля до нескольких выдач: частичное исполнение
не ограничено уникальностью по `issue_sheet_line_id`.
Одна выдача может содержать позиции из нескольких мест хранения через `balance_id`.
Все её позиции должны относиться к одной номенклатуре; это проверяет backend.

```text
required_quantity = warehouse_issue_sheet_lines.quantity
issued_quantity = SUM(warehouse_issue_positions.quantity)
                  по всем warehouse_issues этой строки
remaining_quantity = required_quantity - issued_quantity
```

Накопительный результат не хранится в строке листа. Для строки без выдач сумма
считается нулевой. Backend обязан запрещать превышение потребности, блокируя
строку листа внутри транзакции, и проверять соответствие номенклатуры позиций строке.
Межтабличного CHECK для суммы выдач нет.

`overrideReservations` по умолчанию `false`. Значение `true` фиксирует использование
режима, допускающего расход чужих резервов, но не предоставляет права на него.
Backend проверяет разрешение и требует непустое основание после удаления пробелов
по краям. SQL дополнительно требует `NULLIF(BTRIM(comment), '') IS NOT NULL`
при включённом режиме: `NULL`, пустая строка и строка только из обычных пробелов
отклоняются. CHECK не изменяет сохранённый текст комментария.

Фактическая выдача, её позиции и изменения остатков через `Stock` и резервов
фиксируются одной транзакцией. Собственный резерв проекта уменьшается по мере
использования, при полном расходовании удаляется. В принудительном режиме могут
уменьшаться резервы других проектов. Проверка физического остатка и суммы резервов
обязательна для обоих режимов; отрицательный остаток не разрешён.

API создания выдачи требует UUID `requestKey`. Защиту от повторов обеспечивает
`WarehouseIssueRequest`: составной первичный ключ `(actor_user_id, request_key)`,
hash нормализованной команды и сохранённый JSON успешного ответа. Повтор того же
запроса возвращает сохранённый результат без нового списания, расхода резервов
и аудита; другие данные с тем же ключом дают 409 `WAREHOUSE_ISSUE_REQUEST_CONFLICT`.
Запись запроса, выдача, остатки, резервы и аудит сохраняются одной транзакцией.
Актуальные права проверяются и при повторе. Подробный контракт:
[Issues](../backend/src/warehouse/issues/README.md#защита-от-повторного-проведения).
Частичные выдачи и перевод листа в обработанное состояние — разные действия;
реализованные статусы и переходы описаны в
[IssueSheets](../backend/src/warehouse/issue-sheets/README.md#жизненный-цикл).

`processedAt` и `processedByUserId` заполняются только при фактическом переходе
листа в обработанное состояние, в той же транзакции. Импорт, сопоставление
и сохранение черновика не должны заполнять эти поля.

Индексы выдач покрывают `project_id`, `issue_sheet_line_id`, `issued_by_user_id`,
`created_at` и `warehouse_id` (`idx_warehouse_issues_warehouse`).
Для истории выдач добавлены `(warehouse_id, created_at, id)`
(`idx_warehouse_issues_warehouse_created`) и GIN по `search_text`
(`idx_warehouse_issues_history_search`, gin_trgm_ops из core pg_trgm).
У листов выдачи `warehouse_id` покрыт индексом `idx_warehouse_issue_sheets_warehouse`.
Позиции индексированы по `balance_id`; уникальный индекс
`(issue_id, balance_id)` также покрывает чтение позиций конкретной выдачи.

## Проверка

Реальные тесты запускаются на временном PostgreSQL без доступа к рабочей БД:

```powershell
npm run db:generate
$env:ESOFT_MODULAR_MIGRATION_TEST = '1'
try {
  node --test tests/scripts/infrastructure/prisma/warehouse-package.real.integration.test.mjs
} finally {
  Remove-Item Env:ESOFT_MODULAR_MIGRATION_TEST
}
```

Требуются PostgreSQL `initdb` и `pg_ctl`. Каталог PostgreSQL задаётся через
`ESOFT_TEST_PG_BIN`; по умолчанию используется `C:/Program Files/PostgreSQL/17/bin`.

Выдачи и листы имеют обязательный warehouseId; правила одного склада, фильтры и DTO — [Границы складов](../backend/src/warehouse/storage-structure/WAREHOUSE-BOUNDARIES.md).
